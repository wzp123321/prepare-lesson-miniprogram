## 一、JavaScript 核心

### 1.1 var / let / const 的区别 ★

**结论**：`var` 是函数作用域、有变量提升、可重复声明；`let/const` 是块级作用域、存在「暂时性死区（TDZ）」、不可重复声明；`const` 只保证「绑定不可变」，对象内部属性仍可改。

**大白话**：`var` 有点像「整个楼层都能用的广播」，所以在哪个大括号里声明都一样，容易撞名；`let/const` 只管自己那对大括号里，出了门就没了。`const` 不是「内容不能改」，而是「这个盒子不能换」——盒子里的东西（对象属性）照样能动。

**原理展开**：

- **提升的是「声明」，不是「赋值」**：`var a = 1` 被拆成「`var a`（提升到函数顶，值为 `undefined`）」+「`a = 1`（留在原地执行）」，所以提升后读到的是 `undefined` 而不是报错。
- **`let/const` 也提升，但被「锁」在 TDZ 里**：从进入块到声明语句执行前访问会抛 `ReferenceError`。TDZ 是编译器给块级绑定加的**保护**，不代表「没有提升」。
- **块级作用域怎么实现**：`let/const` 绑定挂在**块的词法环境记录**上，块执行完即销毁。

```js
console.log(a); // undefined（提升但未赋值）
var a = 1;

console.log(b); // ReferenceError（TDZ）
let b = 2;

const obj = { x: 1 };
obj.x = 2; // OK（改属性）
obj = {}; // TypeError（改绑定）
```

**两个高频坑**：

```js
// 坑1：块内 let 与外层同名时，块内声明前访问 → TDZ 报错（不会用外层的）
let x = 1;
{
  console.log(x);
  let x = 2;
} // ReferenceError

// 坑2：块级函数声明的行为在严格 / 非严格模式下不同（严格模式下块内有效）
```

**工程建议**：默认全用 `const`，需要重新赋值才用 `let`，**永远别用 `var`**（作用域会泄漏到函数级，是 bug 温床）。

**追问点**：

- `for (var i...)` 与 `for (let i...)` 在闭包里的差异 → `var` 三个回调共享同一个 `i`（最后都是 3）；`let` **每次迭代创建一个新绑定**（引擎在每轮循环开头复制一份），所以输出 `0 1 2`。
- `const` 声明时不赋值？→ 语法错误 `Missing initializer in const declaration`。

### 1.2 闭包 ★★

**结论**：闭包 = 函数 + 它定义时所处的词法环境。本质是「函数持有对外部作用域变量的引用，使该作用域无法被回收」。

**大白话**：闭包就是「函数把出生地的变量一起打包带走了」。外层函数明明已经执行完，但内层函数还在用它的变量，这些变量就没法被清掉，只能一直留在内存里。常见的防抖、节流里存的 `timer` 就是这么一个被带走的变量。

**原理展开**：JS 用**词法作用域** —— 函数在哪里定义，就决定了它能访问哪些变量（与在哪里调用无关）。当内层函数被返回到外部、外层函数已执行完毕，被内层引用的变量**仍留在内存里**，这份「函数 + 被保留的变量」就是闭包。

**典型坑：循环里 setTimeout**

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i)); // 3 3 3
}
// 用 let（每次迭代新绑定）或 IIFE（立刻捕获当前值）修复：
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i)); // 0 1 2
}
for (var j = 0; j < 3; j++) {
  (function (k) {
    setTimeout(() => console.log(k));
  })(j); // 0 1 2
}
```

**应用**：防抖节流（用闭包保存 `timer`）、模块私有变量（IIFE 时代）、柯里化、Vue 组合式函数的内部状态（`useXxx` 里的 `ref` 被 setup 返回的函数持续引用）。

**追问点**：

- 闭包会造成内存泄漏吗？→「持有不释放」本身不是泄漏；只有**长期持有不再需要的大对象**才算。现代引擎会做**逃逸分析**，未被外部引用的变量会被优化掉。
- 闭包变量存在哪？→ 不在调用栈上，而在**堆上的词法环境对象**里，所以外层函数返回后它依然存活。

### 1.3 this 指向与绑定优先级 ★★

**结论**：优先级 `new 绑定 > 显式绑定(call/apply/bind) > 隐式绑定(obj.fn()) > 默认绑定`；箭头函数没有自己的 `this`，继承定义处外层的 `this`。

**大白话**：`this` 就是「谁在调用这个函数」。判断方法只有一条：别看函数在哪定义，看它被谁点的 —— `obj.fn()` 就是 `obj`，光秃秃地 `fn()` 就是全局（严格模式是 `undefined`）。箭头函数是例外，它没有自己的 `this`，跟定义处外层那个走，`bind` 也改不了。

**判断四步法**（拿到一段代码先这样问）：

1. 是**箭头函数**？→ 看定义处外层作用域，`bind` 也改不了。
2. 是 `new` 调用？→ 指向新实例。
3. 用了 `call/apply/bind`？→ 指向第一个参数（传 `null/undefined` 时非严格模式退回全局对象）。
4. 是 `obj.fn()` 调用？→ 指向 `obj`（只看**最后**那个点前面的对象）。
5. 都不是（裸调用 `fn()`）？→ 严格模式 `undefined`，非严格模式全局对象。

```js
const obj = {
  name: "a",
  fn: function () {
    return this.name;
  },
  arrow: () => this?.name, // 指向定义处外层的 this（模块作用域 → undefined）
};
obj.fn(); // 'a'
const f = obj.fn;
f(); // undefined（隐式绑定丢失，退回默认绑定）
```

**手写 bind（必考，注意 `new` 支持）**：

```js
Function.prototype.myBind = function (ctx, ...args) {
  const fn = this;
  return function bound(...rest) {
    // 关键：被 new 调用时 this 指向新实例，忽略 ctx
    return fn.apply(this instanceof fn ? this : ctx, [...args, ...rest]);
  };
};
```

**追问点**：

- `bind` 返回的函数再 `new`？→ `new` 优先级更高，`this` 指向新实例（原型也继承自 `fn`）。
- 箭头函数能否 `bind`？→ 不能改变 `this`，传进去的 this 被忽略。
- 为什么 `setTimeout(obj.fn, 100)` 里 this 丢了？→ 传的是函数引用，调用时是裸调用，触发默认绑定 —— 常见修法是 `obj.fn.bind(obj)` 或包一层箭头函数。

### 1.4 原型 / 原型链 ★★

**结论**：每个对象有 `__proto__`（隐式原型）指向其构造函数的 `prototype`；访问属性时沿原型链向上查找，直到 `Object.prototype`（其 `__proto__` 为 `null`）。

**大白话**：原型链就是「属性找不到就往上问爹」。跟实例要一个方法，它自己没有，就去它的原型（构造函数 `.prototype`）找，再没有继续往上，一路问到 `Object.prototype`，最后是 `null`（到头了）。所以方法挂在原型上，所有实例共用一份，省内存。

```
实例 ----__proto__----> 构造函数.prototype ----__proto__----> Object.prototype ----__proto__----> null
```

**三个概念别混**：

- `prototype`：**只有函数**才有，是「将来被 `new` 出来的实例的原型」。
- `__proto__`（标准写法 `Object.getPrototypeOf`）：**每个对象**都有，指向它的原型。
- `constructor`：原型上的属性，指回构造函数。

**属性查找规则**：**读**属性时先在自身找，找不到沿 `__proto__` 一路向上；**写**属性时只在自身创建（除非命中原型上的 setter，或修改原型上的引用类型属性）。

```js
function Person(name) {
  this.name = name;
}
Person.prototype.say = function () {
  return this.name;
};
const p = new Person("a");
p.say(); // 'a'（来自原型）
p.hasOwnProperty("say"); // false（say 在原型上）
Object.getPrototypeOf(p) === Person.prototype; // true
```

**`instanceof` 的本质**：判断「右边构造函数的 `prototype` 是否出现在左边对象的原型链上」。

```js
function myInstanceof(obj, Ctor) {
  let proto = Object.getPrototypeOf(obj);
  while (proto) {
    if (proto === Ctor.prototype) return true;
    proto = Object.getPrototypeOf(proto);
  }
  return false;
}
```

**追问点**：

- `Object.create(null)` 有什么用？→ 创建**无原型**的干净对象，当纯字典用（不怕 `__proto__` 污染），但会丢掉 `hasOwnProperty` 等方法。
- 为什么给原型加方法比在构造函数里加好？→ 所有实例**共享同一份函数**，省内存；构造函数里 `this.fn = function(){}` 每个实例都要新建一个。
- `p.__proto__ === Person.prototype`，那 `Person.prototype.__proto__` 是谁？→ `Object.prototype`。

### 1.5 事件循环 Event Loop（宏任务 / 微任务）★★★

**结论**：JS 单线程，执行栈清空后，先清空**所有微任务队列**，再取**一个宏任务**执行，如此循环。渲染时机在每个宏任务之间（`requestAnimationFrame` → 样式 → 布局 → 绘制）。

**大白话**：JS 只有一条流水线（单线程），所有活儿排队。规矩是：先把当前的同步代码干完 → 再把「插队微任务」（`Promise.then`）全部干完 → 才轮到下一个「大活儿」（`setTimeout`）。所以 `Promise` 永远比 `setTimeout` 先跑，跟写在前面还是后面无关。

| 类型             | 例子                                                                |
| ---------------- | ------------------------------------------------------------------- |
| 宏任务 macrotask | `setTimeout` / `setInterval` / `setImmediate`(Node) / I/O / UI 事件 |
| 微任务 microtask | `Promise.then` / `queueMicrotask` / `MutationObserver`              |

```js
console.log(1);
setTimeout(() => console.log(2));
Promise.resolve().then(() => console.log(3));
console.log(4);
// 输出：1 4 3 2
```

**为什么输出 `1 4 3 2`**：

1. 同步代码 `1`、`4` 先跑完（执行栈清空）。
2. 清空**微任务**队列 → 打印 `3`。
3. 取**一个宏任务** → 打印 `2`。

**完整循环（浏览器）**：

```
取一个宏任务 → 执行 → 清空微任务队列 → 是否需要渲染？
  → rAF 回调 → 样式计算 → 布局 → 绘制 → 再取下一个宏任务
```

**Node 与浏览器的差异**：Node 有多个阶段（`timers` / `poll` / `check`…），`setImmediate` 与 `setTimeout(0)` 的先后取决于当前阶段；`process.nextTick` 优先级**高于** `Promise.then`。浏览器只有「宏任务 / 微任务」一层。

**坑：微任务饿死渲染** —— 在微任务里不断 `Promise.resolve().then(...)` 会一直插队，**永远轮不到渲染**，页面卡死。

**追问点**：

- `Promise.resolve().then` 里再嵌 `setTimeout` 的执行顺序？→ 当前宏任务结束后先清微任务，嵌入的 timer 属于下一个宏任务，最后执行。
- `requestAnimationFrame` 算什么任务？→ 既不是宏也不是微任务，是**渲染前的独立回调**，每帧最多一次。

### 1.6 Promise 与 async/await ★★

**结论**：`async` 函数返回 Promise；`await` 会**暂停**当前函数执行并把后续代码放入微任务，本质是 `then` 的语法糖（但执行时机不同）。

**大白话**：`async/await` 就是「把异步写成同步的样子」。`await` 是「在这儿停一下，等结果回来再往下走」，但它只停当前这个函数，整个页面不会被卡住。注意它是「逐个等」，写在 `for` 循环里就是一个个排队（慢），要同时发起得用 `Promise.all`。

```js
async function f() {
  return 1; // 等价 Promise.resolve(1)
}
async function g() {
  const v = await f(); // 等待
  console.log(v);
  throw new Error("x"); // 等价 reject
}
g().catch(console.error);
```

**关键点**：

- `async` 函数**总是返回 Promise**：里面 `return v` → `Promise.resolve(v)`，`throw e` → `Promise.reject(e)`。
- `await` 只在**函数内部**暂停，不阻塞主线程。
- `await` 会**逐层解包 thenable**：`await` 一个 Promise 拿到的是它的值，而不是 Promise 本身。

**串行 vs 并行（高频考点）**：

```js
// ❌ 串行：总耗时 ≈ 三者之和
for (const id of ids) {
  await req(id);
}

// ✅ 并行：总耗时 ≈ 最慢的那个
await Promise.all(ids.map((id) => req(id)));

// ✅ 需要限制并发时用连接池（见 1.7 的 limitPool）
```

**错误处理**：

- `try/catch` 能捕获 `await` 的 reject。
- `async` 函数的 reject 若无人 `catch` → 触发**未处理的 Promise 拒绝**（`unhandledrejection`），可能让 Node 进程退出。
- 想在循环里跳过单个失败：用 `Promise.allSettled` 或逐个 `try/catch`。

**追问点**：

- `await` 一个非 Promise 值？→ 包装成 `Promise.resolve` 后仍让出一个微任务，所以 `await 1` 之后的代码是异步执行的。
- `await` 放在数组 `forEach` 里为什么无效？→ `forEach` 不会 await 回调，整轮同步跑完就返回；要改用 `for...of` 或 `Promise.all(arr.map(...))`。

### 1.7 手写 Promise.all / 并发控制 ★★★

**大白话**：`Promise.all` 是「等所有人到齐再开饭」，有一个人没到整桌就黄了（`reject`）。并发控制是「只开 3 个窗口，谁先办完谁去接下一个」。关键是要用函数把任务包起来（`() => 请求()`），因为 `Promise` 一旦创建就已经跑出去了，包不住就限不住。

**Promise.all**

```js
function promiseAll(promises) {
  return new Promise((resolve, reject) => {
    const arr = [...promises];
    const res = new Array(arr.length);
    let count = 0;
    if (arr.length === 0) return resolve(res);
    arr.forEach((p, i) => {
      Promise.resolve(p).then((v) => {
        res[i] = v; // 保证顺序与入参一致
        if (++count === arr.length) resolve(res);
      }, reject); // 任一失败立即 reject
    });
  });
}
```

**并发控制（限制同时 N 个请求）**

```js
async function limitPool(tasks, limit = 3) {
  const results = new Array(tasks.length);
  let cursor = 0;
  async function worker() {
    while (cursor < tasks.length) {
      const i = cursor++;
      results[i] = await tasks[i]();
    }
  }
  await Promise.all(new Array(limit).fill(0).map(worker));
  return results;
}
```

**四个方法必须秒答**：

| 方法                 | 何时 resolve                                                 | 何时 reject                           |
| -------------------- | ------------------------------------------------------------ | ------------------------------------- |
| `Promise.all`        | 全部成功，返回**有序**结果数组                               | 任一失败立刻 reject（其余结果丢弃）   |
| `Promise.allSettled` | **全部结束**（不论成败），返回 `{status, value/reason}` 数组 | 永不 reject                           |
| `Promise.race`       | 第一个**结束**者（不管成功失败）                             | 第一个结束的是失败者                  |
| `Promise.any`        | 第一个**成功**者                                             | 全部失败才 reject（`AggregateError`） |

**手写要点**：`allSettled` 就是把每个 promise 先包一层 `.then(v => ({status:'fulfilled',value:v}), e => ({status:'rejected',reason:e}))` 再走 `all`；`race` 则是在 `forEach` 里对每个都 `.then(resolve, reject)`，谁先触发谁定胜负。

**并发控制的两种写法**：上面是「N 个 worker 抢任务」；另一种是「维护 N 个执行中的 Promise，完成一个补一个」。要点都是 **不要预先创建全部 promise**。

**追问点**：为什么限流必须传「函数数组」而不是「Promise 数组」？→ `Promise` 一旦创建就**立刻开始执行**，等你 `limit` 时请求早发出去了，限流失效；必须传 `() => Promise` 的 thunk，轮到它时才调用。

### 1.8 深拷贝 ★★

**大白话**：深拷贝就是「复印一份，改副本不影响原件」。最坑的是对象自己引用自己（`a.b = a`），会无限递归，所以要拿个小本本记住「这个我已经拷过了」（`WeakMap`）。`JSON.parse(JSON.stringify(x))` 那套快捷方式会丢函数、丢 `undefined`、把日期变字符串，能上 `structuredClone` 就别用它。

```js
function deepClone(target, map = new WeakMap()) {
  if (target === null || typeof target !== "object") return target;
  if (target instanceof Date) return new Date(target);
  if (target instanceof RegExp) return new RegExp(target.source, target.flags);
  if (map.has(target)) return map.get(target); // 解决循环引用
  const clone = Array.isArray(target) ? [] : {};
  map.set(target, clone);
  for (const key of Reflect.ownKeys(target)) {
    // 含 Symbol
    clone[key] = deepClone(target[key], map);
  }
  return clone;
}
```

**几个关键设计点**：

- **`WeakMap` 存「原对象 → 克隆对象」映射**：既解决**循环引用**（再次遇到同一对象直接返回已克隆的），又因是弱引用而**不阻碍垃圾回收**。
- 用 `Reflect.ownKeys` 而非 `Object.keys`：能拿到 `Symbol` 键与不可枚举键。
- 特殊类型要单独分支：`Date` / `RegExp` / `Map` / `Set` / `ArrayBuffer` 都不是「遍历属性」能正确复制的。

```js
// Map / Set 的补充分支
if (target instanceof Map)
  return new Map(
    [...target].map(([k, v]) => [deepClone(k, map), deepClone(v, map)]),
  );
if (target instanceof Set)
  return new Set([...target].map((v) => deepClone(v, map)));
```

**更现代的方案**：

```js
const copy = structuredClone(obj); // 原生：支持循环引用 / Date / Map / Set，但不支持函数、不复制原型
```

**追问点**：

- `JSON.parse(JSON.stringify())` 的缺陷？→ 丢 `undefined`/函数/Symbol、`Date` 变字符串、`NaN/Infinity` 变 `null`、循环引用直接报错、丢原型。
- 生产环境选哪个？→ 结构简单用 `structuredClone`；要复制函数/原型/描述符才上 `lodash.cloneDeep` 或自己写。

### 1.9 防抖与节流 ★★

**大白话**：防抖是「等你停下来我才动手」（搜索框敲字），节流是「你手再快我也按固定节奏走」（滚动、拖拽）。一个保证「最后一次算数」，一个保证「固定频率响应」。两者都靠闭包存着定时器或时间戳，否则状态留不住。

```js
// 防抖：等停止触发 n 毫秒后才执行（搜索输入）
function debounce(fn, delay = 300) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

// 节流：n 毫秒内只执行一次（滚动、拖拽）
function throttle(fn, interval = 300) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= interval) {
      last = now;
      fn.apply(this, args);
    }
  };
}
```

**立即执行版防抖（首次立刻触发，之后进入冷却）**：

```js
function debounceLeading(fn, delay = 300) {
  let timer = null;
  return function (...args) {
    if (!timer) fn.apply(this, args); // 首次立刻执行
    clearTimeout(timer);
    timer = setTimeout(() => (timer = null), delay); // 冷却期内不再触发
  };
}
```

**节流的两种实现**：

- **时间戳版**（上面这版）：首次立刻触发，但**末次可能被丢弃**。
- **定时器版**：首次延迟触发，能保证**末次一定执行**。
- 生产常用「双剑合璧」：立即执行一次 + 尾部再补一次（`lodash.throttle` 的默认行为）。

**选型**：

| 场景                          | 选择                       |
| ----------------------------- | -------------------------- |
| 搜索框输入联想                | 防抖（停止输入后才发请求） |
| 按钮防连点 / 表单提交         | 防抖（leading 版）         |
| 滚动监听 / 拖拽 / 窗口 resize | 节流（保证有节奏地响应）   |
| 埋点上报                      | 节流                       |

**追问点**：

- 为什么用 `fn.apply(this, args)` 而不是 `fn(...args)`？→ 要**保留调用时的 this**（如挂在组件实例方法上）并透传参数；用箭头函数包裹会丢 this。
- 防抖的 `cancel`/`flush` 有什么用？→ 组件卸载时 `cancel()` 清掉待执行的 timer，避免卸载后回调仍触发、报错或改到已销毁的状态。

### 1.10 其他高频小点 ★

**大白话**：这一堆是「面试随口一问」的小点，不用背原理，记结论就行：比较一律用 `===`；判类型用 `typeof`（原始）/ `instanceof`（引用）/ `Object.prototype.toString.call`（精确）三件套；钱不要用小数算，换成「分」再算。

| 知识点           | 一句话结论                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------- |
| `==` 与 `===`    | `==` 做隐式类型转换（`null == undefined` 为 true，`NaN` 不等于自身）；工程上一律 `===`                        |
| `new` 的过程     | ① 创建空对象 → ② 指向构造函数原型 → ③ 执行构造函数（this 绑定）→ ④ 构造函数返回引用类型则覆盖，否则返回该对象 |
| `typeof` 的坑    | `typeof null === 'object'`（历史遗留）；判断数组用 `Array.isArray`，判断 null 用 `x === null`                 |
| 类型判断         | 原始类型用 `typeof`；引用类型用 `instanceof`；精确到 `[object Xxx]` 用 `Object.prototype.toString.call(x)`    |
| 数字精度         | `0.1 + 0.2 !== 0.3`（IEEE 754 双精度）；金额一律用「分」为整数运算，或 `decimal.js`                           |
| 内存泄漏常见场景 | 未解绑的事件监听/定时器、游离 DOM 引用、意外的全局变量、闭包长期持有大对象、Vue 中未清理的 `watch`/`observer` |

**`NaN` 的两个细节**：`NaN !== NaN` 恒为 true，所以判断用 `Number.isNaN(x)`（不用全局 `isNaN`，后者会先做类型转换，`isNaN('abc')` 也是 true）；`Number.isNaN('abc')` 才是 false。

### 1.11 手写 Promise（简易版）★★★

**结论**：面试要手写的是「状态机 + 回调队列 + 链式」三件套，不必实现 `all`/`race`（那些单独考）。

**大白话**：手写 `Promise` 就是写一个「状态机」：只有等待 / 成功 / 失败三种状态，而且只能变一次。还没结果时先把回调存起来排队，有结果了再一次性放出去。`then` 必须返回一个新的 `Promise`，这样才串得下去。

```js
class MyPromise {
  constructor(executor) {
    this.state = "pending"; // pending | fulfilled | rejected
    this.value = undefined;
    this.onFulfilledCbs = []; // 状态未定时，回调先入队
    this.onRejectedCbs = [];

    const resolve = (v) => {
      if (this.state !== "pending") return; // 状态不可逆
      this.state = "fulfilled";
      this.value = v;
      this.onFulfilledCbs.forEach((cb) => cb(v));
    };
    const reject = (e) => {
      if (this.state !== "pending") return;
      this.state = "rejected";
      this.value = e;
      this.onRejectedCbs.forEach((cb) => cb(e));
    };

    try {
      executor(resolve, reject);
    } catch (e) {
      reject(e);
    } // executor 里的同步异常要转成 reject
  }

  then(onFulfilled, onRejected) {
    // 不传回调时让「值/错误」穿透到下一个 then
    onFulfilled = typeof onFulfilled === "function" ? onFulfilled : (v) => v;
    onRejected =
      typeof onRejected === "function"
        ? onRejected
        : (e) => {
            throw e;
          };

    return new MyPromise((resolve, reject) => {
      // then 必须返回「新 Promise」才能链式
      const handle = (fn) => {
        queueMicrotask(() => {
          // 回调必须异步（微任务）
          try {
            resolve(fn(this.value));
          } catch (e) {
            reject(e);
          }
        });
      };
      if (this.state === "fulfilled") handle(onFulfilled);
      else if (this.state === "rejected") handle(onRejected);
      else {
        this.onFulfilledCbs.push(() => handle(onFulfilled));
        this.onRejectedCbs.push(() => handle(onRejected));
      }
    });
  }

  catch(onRejected) {
    return this.then(null, onRejected);
  }
}
```

**四个必考点**：

1. **状态不可逆** —— `pending` 只能转一次，所以 `resolve`/`reject` 开头要判 `state`。
2. **回调异步** —— 用 `queueMicrotask`（等价于原生微任务语义）。若不异步，`new Promise(r => r(1)).then(console.log)` 会先于同步代码打印，与原生不符。
3. **链式靠「返回新 Promise」** —— 上一个 `then` 的返回值作为下一个 `then` 的输入。
4. **错误穿透** —— 中间 `then` 没写 `onRejected` 时，错误要能穿过它到达后面的 `catch`（靠默认函数 `throw e`）。

**追问点**：`then` 里为什么 `throw e` 才会被下一个 `catch` 捕获？→ `onRejected` 正常 return 表示「错误已处理」，返回的新 Promise 会变 fulfilled；只有重新抛出，新 Promise 才继续 rejected。

### 1.12 异步编程演进 ★★

**大白话**：这是异步写法的「进化史」：回调 → 套娃太深（回调地狱）；Promise → 拍平了但还是一条条 `then`；async/await → 直接写成同步的样子。它的本质是「Generator + 自动执行器」，所以才有暂停 / 恢复的能力。

一条主线：**回调 → Promise → Generator → async/await**。

| 阶段        | 解决的问题            | 关键点                                          |
| ----------- | --------------------- | ----------------------------------------------- |
| 回调        | —                     | 多层嵌套 → **回调地狱**、错误处理分散           |
| Promise     | 扁平化嵌套            | 状态机、链式 `then`、错误沿链传递               |
| Generator   | 让函数可「暂停/恢复」 | `yield` 交出执行权，需**手动/自动执行器**驱动   |
| async/await | 写法同步化            | **async 函数 = Generator + 自动执行器**的语法糖 |

```js
// async/await 本质：Generator 自动跑完
function run(gen) {
  const it = gen();
  return new Promise((resolve, reject) => {
    (function step(val, err) {
      const { value, done } = err ? it.throw(err) : it.next(val);
      if (done) return resolve(value);
      Promise.resolve(value).then(
        (v) => step(v),
        (e) => step(undefined, e),
      );
    })();
  });
}
```

**追问点**：`await` 后面的代码被放进了微任务，为什么说它「阻塞」当前函数却不阻塞主线程？→ 阻塞的只是该 async 函数的后续执行（上下文被挂起），线程本身让给了事件循环，继续跑别的任务。

## 二、TypeScript

### 2.1 interface 与 type 的区别 ★★

| 维度       | interface                               | type                                             |
| ---------- | --------------------------------------- | ------------------------------------------------ |
| 扩展方式   | `extends`、**声明合并**（同名自动合并） | `&` 交叉，**不能**声明合并                       |
| 能描述什么 | 只能描述对象 / 函数 / 类                | 联合、元组、原始类型、条件类型、映射类型都能表示 |
| 编译性能   | 通常更利于增量编译与缓存                | 复杂组合类型编译稍慢                             |
| 报错信息   | 名字更直观、错误提示更友好              | 展开后有时难读                                   |

**结论**：描述**对象结构**、需要扩展/声明合并（如给第三方库补类型）→ `interface`；需要**联合类型、工具类型、类型别名** → `type`。

**大白话**：两者九成场景能互换，别纠结。一个记忆法：要「扩展、合并」（尤其给第三方库补类型）就用 `interface`；要写「联合、元组、条件类型」这些花活，只有 `type` 行。

```ts
// interface：声明合并 —— 同名接口自动合并（常用于扩展库的类型）
interface Window {
  myGlobal: string;
}

// type：联合类型（interface 做不到）
type Status = "idle" | "loading" | "success" | "error";
```

**工程选型**：团队统一优先 `interface`（可扩展、报错友好），遇到联合/元组/条件类型才用 `type`。

**追问点**：`interface` 能 `extends` 一个 `type` 吗？→ 可以（只要该 `type` 能表示对象结构）；反过来 `type` 也能用 `&` 交叉一个 `interface`，两者可混用。

---

### 2.2 泛型与约束 ★★

**结论**：泛型 = **类型的参数**，让同一个函数/类型适配多种类型，同时**保留类型信息**（而不是退化成 `any` 丢光检查）。

**大白话**：泛型就是「类型的占位符」。写函数时不知道将来用哪种类型，就先留个坑 `T`，谁调用谁填；填完之后 TS 还记得「就是它」，不会退化成 `any`。这里的 `extends` 是「限制 T 只能是这些」，不是面向对象的继承。

```ts
function pick<T, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  const res = {} as Pick<T, K>;
  keys.forEach((k) => (res[k] = obj[k]));
  return res;
}
const user = { id: 1, name: "a", age: 18 };
pick(user, ["id", "name"]); // → Pick<typeof user, 'id' | 'name'>
pick(user, ["notExist"]); // ❌ 编译报错（K 受 keyof T 约束）
```

**两个要点**：

- 泛型里的 `extends` 是**约束**（限制 `T` 的范围），不是面向对象的继承。
- 无约束的 `T` 是「任意类型」，**不能**随意取属性（会报「属性不存在」）—— 想取属性就得写成 `T extends { id: number }`。

**默认类型参数**：`type Foo<T = string> = ...`，调用时不传就落到默认值。

**追问点**：为什么 `pick(user, ['notExist'])` 直接报错？→ `K extends keyof T` 把 `K` 限制为**现有键的联合**，`'notExist'` 不在其中，编译期就被拦住 —— 这正是泛型约束的价值：**把运行时错误提前到编译期**。

---

### 2.3 常用工具类型 ★★

**大白话**：工具类型就是 TS 官方预置的一批「类型加工厂」：`Partial` 全变可选、`Pick/Omit` 挑字段 / 去字段、`ReturnType` 取函数返回值。不用背，知道有这些厂子、用的时候查一下就行。

| 工具类型                          | 作用                                             |
| --------------------------------- | ------------------------------------------------ |
| `Partial<T>` / `Required<T>`      | 全部变可选 / 全部变必选                          |
| `Readonly<T>`                     | 全部变只读                                       |
| `Pick<T,K>` / `Omit<T,K>`         | 取属性子集 / 去掉属性子集                        |
| `Record<K,V>`                     | 构造「键为 K、值为 V」的对象类型                 |
| `Exclude<T,U>` / `Extract<T,U>`   | 从联合里排除 / 挑出成员                          |
| `ReturnType<F>` / `Parameters<F>` | 取函数返回值 / 参数元组                          |
| `Awaited<T>` / `NonNullable<T>`   | 取 Promise 解包后的类型 / 去掉 null 与 undefined |

**能手写实现（高频）**：

```ts
type MyPartial<T> = { [K in keyof T]?: T[K] }; // 映射类型 + 可选修饰
type MyReadonly<T> = { readonly [K in keyof T]: T[K] }; // 映射类型 + readonly
type MyOmit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
type MyReturnType<F> = F extends (...args: any[]) => infer R ? R : never;
```

**追问点**：`Exclude` 与 `Omit` 的区别？→ 都基于 `Exclude`，但 `Exclude` 操作的是**联合类型**（`Exclude<'a'|'b','a'>` → `'b'`），`Omit` 操作的是**对象类型**（按 key 去掉属性）。

---

### 2.4 类型收窄与守卫 ★★★

**结论**：TS 会在分支里**自动收窄**类型（`typeof` / `instanceof` / `in` / 字面量 / 真值判断）；跨函数传递的「类型判断」要用**自定义类型守卫**（`x is T`）或**断言函数**（`asserts x is T`）。

**大白话**：类型收窄就是「进了这个 `if`，TS 就知道它是啥了」。比如 `if (typeof x === 'string')` 里面，`x` 就是 `string`。可一旦你把判断挪进独立函数，TS 就看不出来了 —— 所以要显式写 `x is string` 告诉它。

**常见收窄手段**：`typeof x === 'string'`、`x instanceof Date`、`'name' in obj`、`Array.isArray(x)`、`if (x)`（剔除 falsy）、自定义 `isXxx(x)`。

```ts
function isString(x: unknown): x is string {
  return typeof x === "string";
}

// 可辨识联合
type Shape =
  | { kind: "circle"; r: number }
  | { kind: "rect"; w: number; h: number };

function area(s: Shape) {
  switch (s.kind) {
    case "circle":
      return Math.PI * s.r ** 2;
    case "rect":
      return s.w * s.h;
    default:
      const _exhaustive: never = s;
      return _exhaustive; // 穷尽检查
  }
}
```

**穷尽检查的价值**：给联合**新增成员**时，`default` 里的 `never` 赋值会立刻报错，提醒你补全 `case` —— 这是 TS 最实用的模式之一。

**追问点**：

- `as` 与类型守卫的区别？→ `as` 是**编译期断言**，不做运行时校验（可以骗过编译器）；类型守卫是**真的运行时判断**，安全。
- `unknown` 与 `any`？→ `unknown` 是「安全版 any」，用前必须收窄；`any` 直接放弃检查，容易埋雷。

---

### 2.5 条件类型与 `infer` ★★★

**结论**：条件类型形如 `T extends U ? X : Y`，是类型层面的 `if`；`infer` 用于在条件类型里**声明一个待推断的类型变量**（相当于类型版的正则捕获）。

**大白话**：条件类型就是「类型层面的 if/else」；`infer` 是「我先占个位，等 TS 推出来再填」。比如从 `Promise<string>` 里把 `string` 抠出来：`T extends Promise<infer U> ? U : T`。

```ts
// infer 提取函数返回值
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

// infer 提取 Promise 内部类型
type Unwrap<T> = T extends Promise<infer U> ? U : T;
type A = Unwrap<Promise<string>>; // string

// 递归 + infer 提取数组元素
type ElementOf<T> = T extends (infer E)[] ? E : never;

// 分发式条件类型：裸泛型 T 遇到联合类型会「逐个分发」
type ToArray<T> = T extends any ? T[] : never;
type B = ToArray<string | number>; // string[] | number[]
```

**追问点**：

- 为什么 `ToArray<string | number>` 是 `string[] | number[]` 而不是 `(string | number)[]`？→ 因为 `T` 是**裸类型参数**，条件类型会「分发」到联合的每个成员。
- 怎么阻止分发？→ 用元组包一层：`[T] extends [any] ? ...`。

---

### 2.6 TS 在接口层的实战封装 ★★

**结论**：类型系统最大的价值是**让后端契约和前端使用对齐**，一处改、全局报错。

**大白话**：接口层的类型不是为了好看，是为了「后端字段一改，前端编译就红」，把联调时才暴露的错提前到写代码时。`request<T>` 里那个 `T`，就是让调用处自动推出 `data` 的类型。

```ts
// 统一后端返回结构
interface ApiResult<T> {
  code: number;
  message: string;
  data: T;
}

// 请求函数泛型化：调用处自动推 data 类型
async function request<T>(url: string, data?: unknown): Promise<T> {
  const res = await fetch(url, { method: "POST", body: JSON.stringify(data) });
  const json = (await res.json()) as ApiResult<T>;
  if (json.code !== 0) throw new Error(json.message);
  return json.data; // 自动是 T
}

// 调用处：student 自动推导为 Student
const student = await request<Student>("/api/student/get", { id: 1 });
```

**追问点**：`any` / `unknown` / `never` 的区别？→ `any` 放弃检查（危险）；`unknown` 是「安全版的 any」，用前必须收窄；`never` 是「永不存在」的类型，用于穷尽检查与不可能分支。

## 三、CSS 与布局

### 3.1 盒模型 ★

**大白话**：盒模型就是「一个盒子由四层组成：内容 + 内边距 + 边框 + 外边距」。争议只在 `width` 算到第几层：`content-box` 只算内容（加 padding 就变大），`border-box` 连 padding 和边框一起算（加 padding 不变大）。工程上一律用 `border-box` 省心。只有 margin 特殊：相邻的上下的间距会「合并取大的」。

- `content-box`（标准）：`width` 只含内容，`padding/border` **另加** → 总宽 = `width + padding + border`。
- `border-box`（IE 盒模型）：`width` **含** `padding + border` → 改 padding 不会撑大元素。
- 工程上一律 `* { box-sizing: border-box }`，布局更符合直觉。

**外边距合并（margin collapse）**：相邻兄弟的上下 margin 取**较大者**；父子的上 margin 也会合并（父元素无 border/padding/BFC 时）。加 **BFC、padding 或 border** 可阻止。

**`width: 100%` 与盒模型**：`border-box` 下 `width:100%` 再加 padding 不会溢出；`content-box` 下会溢出。

**追问点**：`height: 100%` 为什么常常不生效？→ 百分比高度需要**父元素有确定高度**；父级是 `height: auto`（按内容撑开）时，`100%` 失去参照，等于没设。

---

### 3.2 BFC（块级格式化上下文）★★

**结论**：BFC 是一块**独立渲染区域** —— 内部布局不影响外部，外部也不影响内部。

**大白话**：BFC 就是给一块区域「划个圈，里面的事外面别管，外面的事别进来」。最实用的两个作用：圈里全是浮动元素时圈不会被压塌；圈内外的 margin 不会互相合并。触发方式里最干净的是 `display: flow-root`。

**触发条件**（记 4 类）：`overflow != visible`、`float != none`、`position: absolute/fixed`、`display: flow-root / inline-block / flex / grid / table-cell`。

**三大作用**：

1. **包含内部浮动** → 父元素不再高度塌陷（清除浮动）。
2. **阻止 margin 合并** → 隔开相邻或父子的外边距。
3. **阻止被浮动元素覆盖** → 两栏自适应（左浮动 + 右 BFC）。

```html
<!-- 父元素高度塌陷：父没有 BFC，子元素浮动后不撑开父高 -->
<div class="parent">
  <div class="float">float</div>
</div>
```

```css
.parent {
  display: flow-root;
} /* 最干净的修复 */
```

**追问点**：为什么推荐 `display: flow-root` 而不是 `overflow: hidden`？→ 它**只创建一个 BFC、不改变其他行为**；`overflow: hidden` 会把溢出内容裁掉（如下拉框被切、阴影被切），是副作用。

---

### 3.3 Flex 与 Grid 场景区分 ★★

**大白话**：Flex 是「排一排或者排一列」（一维），Grid 是「画格子」（二维）。日常导航、卡片内对齐用 Flex，整页框架、图片墙用 Grid。`flex: 1` 记得展开是 `1 1 0%` —— 它平分的是「剩余空间」，不按内容宽度分。

- **Flex**：**一维**布局（一行或一列），适合导航栏、工具栏、卡片内部对齐、表单一行多个控件。
- **Grid**：**二维**布局（行列同时控制），适合整体页面框架、仪表盘、图片墙。

```css
/* Flex 水平垂直居中 */
.center {
  display: flex;
  justify-content: center;
  align-items: center;
}

/* Grid 三栏：中间自适应，两侧固定 */
.layout {
  display: grid;
  grid-template-columns: 240px 1fr 320px;
  gap: 16px;
}

/* Grid 自适应卡片墙：无需媒体查询，列数随宽度自动增减 */
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(240px, 1fr));
  gap: 16px;
}
```

**`flex: 1` 展开**：`flex-grow:1; flex-shrink:1; flex-basis:0%` —— `basis:0%` 意味着**平分剩余空间**（内容宽度不参与计算）。

**追问点**：

- `flex: 1` 与 `flex: auto` 的区别？→ `flex:1` = `1 1 0%`（平分空间），`flex:auto` = `1 1 auto`（先按内容宽度分配，再分剩余）。
- `min-width: 0` 干嘛用？→ flex 子项默认 `min-width: auto`，长文本/`nowrap` 会撑破容器；加 `min-width: 0` 才能正常收缩，`text-overflow: ellipsis` 也才会生效。

---

### 3.4 常见居中方案 ★

**大白话**：居中方案挑最省事的一把就行：一整块内容用 flex（`justify-content` + `align-items`）；一行文字让 `line-height` 等于容器高；必须兼容老浏览器再上绝对定位。`translate(-50%,-50%)` 里的百分比是相对**元素自己**的宽高，所以不定宽高也能居中。

```css
/* 1. 绝对定位 + transform（不定宽高都能居中） */
.a {
  position: absolute;
  top: 50%;
  left: 50%;
  transform: translate(-50%, -50%);
}
/* 2. 绝对定位 + margin auto（需定宽高） */
.b {
  position: absolute;
  inset: 0;
  margin: auto;
  width: 100px;
  height: 100px;
}
/* 3. flex / grid（最推荐，无需知道尺寸） */
.c {
  display: flex;
  justify-content: center;
  align-items: center;
}
.d {
  display: grid;
  place-items: center;
}
/* 4. 单行文字：text-align + line-height（line-height 等于容器高） */
.e {
  text-align: center;
  line-height: 40px;
}
/* 5. flex 子项 margin: auto（局部居中，不影响其他兄弟） */
.f {
  display: flex;
}
.f > .target {
  margin: auto;
}
```

**怎么选**：

| 场景             | 推荐                                  |
| ---------------- | ------------------------------------- |
| 弹层 / 任意内容  | flex 或 grid（`place-items: center`） |
| 单行文字         | `text-align` + `line-height`          |
| 需要兼容老浏览器 | 绝对定位 + `transform`                |

**追问点**：`transform: translate(-50%,-50%)` 的 `%` 相对谁？→ 相对**元素自身**的宽高（不是父元素），所以不定尺寸也能居中；代价是可能**子像素模糊**、并会创建新的层叠上下文。

### 3.5 层叠上下文与 z-index ★★

**结论**：`z-index` 只在**同一个层叠上下文（stacking context）内**比较；跨上下文时先比上下文的层级，再看内部 `z-index`。

**大白话**：`z-index` 不是全局排行榜，而是「各小组内部排名」。父元素一旦加了 `transform`、`opacity` 这类属性，就会被单独划成一个新「小组」，子元素在组里就算 `z-index` 一万，也压不过别的组 —— 弹窗被遮住多半就是它。解法是用 `Teleport` 把弹层挂到 `body` 下。

**会创建新层叠上下文的属性**（记常用的几个）：`position` 非 `static` + `z-index` 非 `auto`、`opacity < 1`、`transform / filter / perspective` 非 none、`will-change`、`isolation: isolate`、`flex/grid` 子项且 `z-index` 非 auto。

**经典坑**：父元素加了 `transform`（或 `opacity: 0.99`）后，子元素 `z-index: 9999` 也**压不过父层之外的弹层** —— 移动端「弹窗被遮住」多半是这个原因。

```css
/* 症状：B 想盖住 A，却盖不住 */
.a {
  transform: translateZ(0);
} /* 创建了新上下文 → 把内部层级圈住了 */
.b {
  position: fixed;
  z-index: 9999;
}
/* 修法：把 B 挂到 body（Vue 里用 <Teleport to="body">），或去掉 A 上的 transform */
```

**追问点**：定位元素的 `z-index` 默认值？→ `auto`（**不**创建上下文，按 DOM 顺序排）；只有赋了**整数**才创建新上下文。

### 3.6 移动端适配 ★★

**大白话**：移动端适配就三件事：尺寸用什么单位（vw / rem）、别被刘海和底部横条压住（`env(safe-area-inset-*)`）、1px 边框怎么在 2 倍屏上不显粗。别迷信某一种方案：vw 最省事，rem 适合「大屏时想限制最大宽度」的场景。

- **rem + 动态 font-size**：按设计稿宽度（如 375）动态设置 `html` 的 `font-size`，元素尺寸用 rem。
- **vw/vh**：`100vw` = 视口宽，配合 `postcss-px-to-viewport` 自动换算，配置简单。
- **flex + 百分比**：做弹性骨架，配合 `max-width/min-width` 控制边界。
- **安全区**：`padding-bottom: env(safe-area-inset-bottom)` 处理 iPhone 底部横条。
- **1px 边框**：`transform: scaleY(0.5)` 的伪元素方案（dpr=2），或 `border-image`、`box-shadow`。
- **`viewport` meta**：`<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` —— `viewport-fit=cover` 是 `env(safe-area-inset-*)` 生效的前提。

**rem 还是 vw**：纯 H5 单页用 vw 更省事（不必 JS 动态改根字号）；需要「大屏时限制最大宽度」用 rem + `max-width`。

**追问点**：`dpr`（设备像素比）是什么？→ `物理像素 / CSS 像素`，iPhone 常见 2 或 3。高清屏图片用 `srcset` + `w` 描述符按 dpr 取图，避免糊掉或浪费带宽。

---

### 3.7 position 五种定位 ★

**大白话**：记住每个定位「参照谁、走不走」就够了：`relative` 参照自己原来的位置（还在原地占位）；`absolute` 参照最近的已定位祖先；`fixed` 参照浏览器窗口。`sticky` 最容易失败，两种原因 —— 祖先有 `overflow`（滚动容器变了），或者你没写 `top/left` 阈值。

| 值         | 参照物                                                | 是否脱离文档流         | 典型用途                 |
| ---------- | ----------------------------------------------------- | ---------------------- | ------------------------ |
| `static`   | 无（默认）                                            | 否                     | 普通流                   |
| `relative` | 自身原位置                                            | **否**（原位置仍占位） | 微调、给子元素当定位参照 |
| `absolute` | **最近的已定位祖先**，无则 `initial containing block` | 是                     | 弹层、角标、自定义下拉   |
| `fixed`    | 视口                                                  | 是                     | 悬浮按钮、固定顶栏       |
| `sticky`   | 最近的滚动祖先                                        | 否（达到阈值前仍占位） | 吸顶表头、吸底栏         |

**`sticky` 的两个常见失效原因**：① 祖先元素有 `overflow: hidden/auto`（滚动容器变了，粘不住）；② 没设置 `top/bottom/left/right` 阈值。它本质是「relative 与 fixed 的结合」：在阈值内表现为 relative，越过后吸附。

### 3.8 响应式设计 ★★

**大白话**：响应式就是「同一套代码适配不同屏幕」。媒体查询按「窗口宽度」切换，容器查询按「父容器宽度」切换（更组件化）。能不用媒体查询的就用 `clamp()` 这类弹性函数，一行写清 min～max。

- **媒体查询**（`@media (max-width: 768px)`）：按视口宽度断点切布局，最通用。
- **容器查询**（`@container`）：按**父容器**尺寸响应，适合「同一个卡片组件放在窄栏/宽栏里表现不同」，比媒体查询更组件化（现代浏览器已支持）。
- **相对单位**：`rem`（根字号）、`em`（父字号，易踩坑）、`%`、`vw/vh`、`clamp(min, 理想值, max)`。
- **`min()` / `max()` / `clamp()`**：无需媒体查询就能做弹性尺寸，如 `width: clamp(300px, 50vw, 600px)`。
- **移动优先**：先写小屏样式，再用 `min-width` 递进增强。

**追问点**：`1px` 在 dpr = 2 的屏幕上怎么做到物理 1px？→ `transform: scaleY(0.5)` 伪元素，或 `border-image`，或 `box-shadow` 描边。

## 四、浏览器与网络

### 4.1 从输入 URL 到页面渲染 ★★★

**一句话**：分「网络（找到服务器拿到 HTML）+ 渲染（把字节画成像素）」两大阶段。

**大白话**：这条链路要分两半背。前半是「东西怎么到手」：解析 URL → 查缓存 → DNS 找到服务器 → TCP/TLS 握手 → 请求回 HTML。后半是「怎么画出来」：HTML 变 DOM、CSS 变 CSSOM → 合成渲染树 → 布局算位置 → 绘制 → 合成上屏。最容易考的插入点：脚本会阻塞解析（`async/defer` 的区别）、CSS 会阻塞渲染。

**① 网络阶段**

1. **解析 URL**：判断协议、是否合法、是否当搜索词处理。
2. **缓存检查**：强缓存命中直接用；否则带协商缓存头发请求。
3. **DNS 解析**：浏览器缓存 → 系统 hosts → 本地 DNS → 递归/迭代查到根与顶级域名（可 `dns-prefetch` 预解析）。
4. **TCP 三次握手**（HTTPS 再加 TLS 握手，多 1~2 个 RTT）。
5. **发送 HTTP 请求**，服务端返回 HTML。

**② 渲染阶段**

6. **解析**：HTML → DOM 树；CSS → CSSOM；**遇到没有 `async/defer` 的 `<script>` 会阻塞解析**。
7. **渲染树**（Render Tree）= DOM + CSSOM 合并（**不含 `display:none` 的节点**）。
8. **布局 Layout（回流）** → 计算几何位置。
9. **绘制 Paint** → 生成绘制指令。
10. **合成 Composite** → 分层、GPU 合成上屏。
11. **事件**：`DOMContentLoaded`（DOM 解析完，不等图片）→ `load`（所有资源加载完）。

**追问点**：

- `defer` 与 `async` 的区别？→ `defer`：**按顺序**、DOM 解析完后执行（适合有依赖的脚本）；`async`：**加载完立即执行、顺序不定**（适合独立脚本，如统计）。
- 为什么 CSS 放 `<head>`、JS 放 `</body>` 前？→ CSS 阻塞渲染树构建；JS 会阻塞 DOM 解析，放后面能避免首屏白屏。
- 渲染阻塞的三件事？→ CSSOM 构建阻塞渲染、同步脚本阻塞解析、`document.write` 危险。

---

### 4.2 回流（重排）与重绘 ★★

**大白话**：改尺寸 / 位置 → 要重新算布局（回流，最贵）；只改颜色 / 背景 → 只要重画（重绘）；只改 `transform`、`opacity` → 连重画都不用，直接交给显卡（最便宜）。最坑的是「写一下样式又读一下尺寸」，浏览器被迫每次提前算一遍布局，所以要先全部读、再全部写。

- **回流（reflow）**：几何属性变化（尺寸、位置、显隐）→ 重新计算布局，**代价最高**，可能引发整棵树的连锁重排。
- **重绘（repaint）**：外观变化（颜色、背景、阴影）→ 重新绘制，代价较低。
- **只触发合成（composite）**：`transform`、`opacity`（走 GPU，动画首选，既不回流也不重绘）。

**会触发回流的操作**：改 `width/height/padding/margin`、插入/删除 DOM、改字体，以及 `offsetWidth` / `getBoundingClientRect()` 这类**读操作**（若夹在写操作之间会触发**强制同步布局**）。

```js
// ❌ 读写交替 → 每轮都强制同步布局（layout thrashing）
boxes.forEach((b) => {
  b.style.width = box.offsetWidth + 10 + "px";
});

// ✅ 读写分离：先全部读，再全部写
const widths = boxes.map((b) => b.offsetWidth);
boxes.forEach((b, i) => {
  b.style.width = widths[i] + 10 + "px";
});
```

**其他手段**：`documentFragment` / 离线 DOM 批量插入；先 `display:none` 再操作再显示（只回流两次）；`will-change: transform` 提升为独立图层；动画放 `requestAnimationFrame` 里。

**追问点**：为什么 `transform` 做动画比 `left/top` 快？→ `left/top` 改的是**布局属性**，每帧都触发回流；`transform` 只影响合成层，直接在 GPU 上做变换。

---

### 4.3 强缓存与协商缓存 ★★

**大白话**：强缓存是「我信本地这份，别问了」（不发请求）；协商缓存是「我带着凭证问一句：变了吗？没变就用旧的」（发请求但只回 304）。最容易记错的是 `no-cache` —— 它不是「不缓存」，而是「每次都要问一遍」；真的不想存是 `no-store`。

| 类型             | 相关响应头                                            | 行为                                             |
| ---------------- | ----------------------------------------------------- | ------------------------------------------------ |
| 强缓存           | `Cache-Control: max-age=31536000`（`Expires` 已过时） | 有效期内**不发请求**，直接用本地副本（最快）     |
| 协商缓存（ETag） | `ETag` / `If-None-Match`                              | 发请求比对内容指纹，未变 → `304` 复用            |
| 协商缓存（时间） | `Last-Modified` / `If-Modified-Since`                 | 精度到秒，文件秒级连续改动会漏判，不如 ETag 精确 |

**优先级**：`Cache-Control` > `Expires`；`ETag` > `Last-Modified`。

**常见 `Cache-Control` 指令（易考）**：

| 指令                 | 含义                                                         |
| -------------------- | ------------------------------------------------------------ |
| `no-store`           | **完全不缓存**（敏感数据/一次性接口）                        |
| `no-cache`           | **可以缓存，但每次都要跟服务器确认**（注意：不是「不缓存」） |
| `max-age=N`          | 强缓存 N 秒                                                  |
| `immutable`          | 有效期内**连协商都不用**（配内容 hash 使用）                 |
| `private` / `public` | 只允许浏览器缓存 / 代理服务器也可缓存                        |

**工程实践**：`index.html` 用 `no-cache`（协商，保证拿到最新入口）；带 hash 的静态资源（`app.abc123.js`）用 `immutable, max-age=1年`（内容变则 hash 变，天然失效）。

**追问点**：`no-cache` 与 `no-store` 的区别（高频）？→ `no-cache` 是「**每次都要跟服务器确认**」（会走 304）；`no-store` 是「**根本不存**」。名字容易误解，务必答准。

---

### 4.4 跨域与 CORS ★★

**结论**：浏览器**同源策略**（协议 + 域名 + 端口全同才算同源）限制的是「源不同」的 `ajax`/`fetch` **读取**；请求本身可能已经发出去了，只是**响应被浏览器拦下**。

**大白话**：同源是「协议 + 域名 + 端口全一样才算自己人」。跨域限制的其实是「JS 能不能读响应」，不是「请求能不能发出去」—— 简单请求服务端确实收到了，只是浏览器不把结果交给前端。所以别指望前端绕过它：要么服务端加响应头（CORS），要么走代理（对浏览器来说仍是同源）。

**解决方案**：

1. **CORS**（推荐）：服务端设 `Access-Control-Allow-Origin`。
2. **代理**：开发用 Vite `server.proxy`，生产用 Nginx 反向代理（对浏览器而言同源）。
3. JSONP（只支持 GET，已淘汰）、`postMessage`、WebSocket（不受同源限制）。

**带 Cookie 的 CORS 必须同时满足**：`Access-Control-Allow-Credentials: true`、`Allow-Origin` **不能是 `*`**（必须是具体域名）、前端 `fetch` 加 `credentials: 'include'`。

**预检（preflight）**：非简单请求会先发一个 `OPTIONS`，服务端返回允许的方法/头，浏览器才发真实请求。

**简单请求判定**：方法为 `GET/HEAD/POST`，且 `Content-Type` 属于 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded`，且**无自定义请求头**。

**追问点**：

- 跨域请求到底有没有到服务端？→ 简单请求**到了**（只是响应被拦），所以**不能拿「是否跨域」当安全边界**，服务端该做的校验一个都不能少。
- 为什么加个自定义 header 就触发预检？→ 它不属于「CORS 安全列表请求头」，浏览器必须先用 `OPTIONS` 探测服务端是否允许。

---

### 4.5 HTTP 版本演进 ★★★

**大白话**：1.0 每问一次握一次手；1.1 保持连接，但一条连接同时只跑一个请求，前面卡住后面全等；2.0 上了多路复用，一条连接能并行多个请求，可底下还是一条 TCP，丢包仍然全体等；3.0 换成 UDP 上的 QUIC，每条流各管各的，这才彻底不堵。

| 版本     | 关键特性                                                                      |
| -------- | ----------------------------------------------------------------------------- |
| HTTP/1.0 | 短连接，每个请求一次 TCP 握手                                                 |
| HTTP/1.1 | 长连接 `keep-alive`、管道化（鸡肋）、**应用层队头阻塞**                       |
| HTTP/2   | 二进制分帧、**多路复用**、HPACK 头压缩、服务端推送、仍存在 **TCP 层队头阻塞** |
| HTTP/3   | 基于 **QUIC（跑在 UDP 上）**，0-RTT 建连，彻底解决队头阻塞                    |

**两层队头阻塞要分清**：

- **HTTP/1.1 的 HOL**：一个连接同时只能处理一个请求，前一个慢就把后面全堵住 → 浏览器靠**多开连接（6 个）**缓解，治标不治本。
- **HTTP/2 的 HOL**：多路复用解决了应用层，但底层仍是**一条 TCP**，一个包丢了整条连接上的所有流都要等重传。

**追问点**：

- 为什么 HTTP/3 改用 UDP？→ 用 QUIC 在**用户态**实现可靠传输，各流独立重传，一条流丢包不影响其他流，还能 0-RTT 恢复连接。
- HTTP/2 服务端推送为什么没普及？→ 推送时无法感知客户端已有缓存，容易推重复内容反而浪费带宽；现代多改用 `103 Early Hints` + 预加载。

---

### 4.6 存储方案对比 ★★

**大白话**：选存储就看三点：能放多大、活多久、要不要跟着请求自动发给服务端。Cookie 只有 4KB 且每次请求都带上（所以只放凭证）；`localStorage` 大且永久，但写起来是同步的、会卡主线程；要存大量结构化数据、还要建索引查询，就上 IndexedDB。

| 方案           | 容量           | 生命周期               | 随请求自动发送     | 典型场景                      |
| -------------- | -------------- | ---------------------- | ------------------ | ----------------------------- |
| Cookie         | 4KB            | 可设过期               | **是**（拖慢请求） | 会话凭证（`HttpOnly` 防 XSS） |
| localStorage   | 5–10MB         | **永久**（除非手动清） | 否                 | 少量持久配置、主题            |
| sessionStorage | 5–10MB         | 标签页关闭即失效       | 否                 | 单次会话的表单草稿            |
| IndexedDB      | 很大（配额制） | 永久                   | 否                 | 结构化大数据、离线缓存        |
| Cache Storage  | 很大           | 永久                   | 否                 | Service Worker 缓存静态资源   |

**要点**：

- `localStorage` 是**同步 API**，大数据量读写会**阻塞主线程**（别往里塞大 JSON）。
- 跨标签页通信：`storage` 事件（只在**其他**标签页触发）或 `BroadcastChannel`。
- 均受**同源**限制，且都能被 JS 读取（`HttpOnly` Cookie 除外）。

**追问点**：什么时候用 IndexedDB 而不是 localStorage？→ 需要存**大量结构化数据**、要建索引查询、或不想阻塞主线程时（IndexedDB 是**异步** API）。

---

### 4.7 XSS 与 CSRF ★★★

**大白话**：两者的区别在「骗谁」：XSS 是「你的页面信了用户输入的内容」，把脚本当内容渲染执行了；CSRF 是「你的浏览器信了自动带 Cookie 的规矩」，被诱导着用你的身份发请求。防御也一一对应：XSS 靠输出转义 + CSP + 别乱用 `v-html`；CSRF 靠 Token + `SameSite`。

**XSS（跨站脚本注入）**：把恶意脚本注入页面并执行，**在受害者浏览器里以站点身份运行**。

| 类型   | 触发方式                                                          |
| ------ | ----------------------------------------------------------------- |
| 存储型 | 恶意内容存进数据库（评论、昵称），**所有访问者中招**（危害最大）  |
| 反射型 | 恶意参数经 URL 回显到页面（钓鱼链接诱导点击）                     |
| DOM 型 | 前端 JS 直接把 `location.hash` 等写进 `innerHTML`，**不经服务端** |

**XSS 防御**：

- **输出转义**（按上下文：HTML 文本 / 属性 / URL / JS 规则不同）—— 根本手段。
- `Content-Security-Policy`（CSP）限制脚本来源、禁用 `unsafe-inline`。
- 避免 `innerHTML` / `v-html` 直接渲染用户输入（Vue 的 `{{ }}` 插值**已自动转义**，安全）。
- 敏感 Cookie 设 `HttpOnly`，即使被注入也偷不到凭证。

**CSRF（跨站请求伪造）**：诱导**已登录**用户向目标站点发起非预期请求（利用浏览器**自动携带 Cookie**）。

**CSRF 防御**：CSRF Token（服务端下发、请求回传、一次性校验）、`SameSite=Lax/Strict` Cookie、校验 `Origin/Referer`、关键操作二次验证。

**一句话区分**：**XSS 是「信任了用户的输入」，CSRF 是「信任了浏览器的自动带凭证」**。

**追问点**：

- 为什么说 XSS 比 CSRF 更危险？→ XSS 得手后攻击者**在页面内**可任意操作（含读取并提交 Token），CSRF 只能冒用身份发请求、拿不到响应数据。
- `v-html` 的风险？→ 会渲染原始 HTML，等于把 XSS 入口交给数据源；确需使用时必须先用 DOMPurify 之类做**白名单过滤**。

### 4.8 HTTP 状态码与方法语义 ★

**大白话**：状态码按段位记就够：2 是成功、3 是重定向（304 是缓存命中，不是错误）、4 是客户端的问题、5 是服务端的问题。最常被追问的是 401 与 403：401 是「不知道你是谁」（去登录），403 是「知道你是谁，但你不许干这个」（去要权限）。

| 段位 | 含义       | 高频码                                                                                 |
| ---- | ---------- | -------------------------------------------------------------------------------------- |
| 1xx  | 信息       | 101 Switching Protocols（WebSocket 升级）                                              |
| 2xx  | 成功       | 200 OK、201 Created、204 No Content                                                    |
| 3xx  | 重定向     | 301 永久（会被缓存）、302/307 临时、**304 Not Modified（命中协商缓存）**               |
| 4xx  | 客户端错误 | **400** 参数错误、**401** 未认证、**403** 已认证但无权限、**404** 不存在、**429** 限流 |
| 5xx  | 服务端错误 | 500 内部错误、502 网关错误、503 服务不可用、504 网关超时                               |

**方法语义**：`GET` 查询（**幂等**、可缓存）、`POST` 新增（不幂等）、`PUT` 全量更新（幂等）、`PATCH` 局部更新（不保证幂等）、`DELETE` 删除（幂等）。

**追问点**：401 与 403 的区别？→ 401 是「你是谁不知道」（未登录/凭证失效），403 是「知道你是谁但不让干」（权限不足）。工程上 401 触发跳登录，403 提示无权限。

---

### 4.9 Cookie 属性详解 ★★

**大白话**：Cookie 的属性各管一件事：`HttpOnly` 让 JS 读不到（防 XSS 偷），`Secure` 只在 https 下发送，`SameSite` 管跨站带不带（防 CSRF）。所以比较安全的组合是：token 放 `HttpOnly` Cookie，再用 `SameSite` + CSRF Token 兜底。

| 属性                  | 作用                                                          |
| --------------------- | ------------------------------------------------------------- |
| `HttpOnly`            | 禁止 JS 读取（`document.cookie` 取不到）→ **防 XSS 窃取**     |
| `Secure`              | 只在 HTTPS 下发送                                             |
| `SameSite=Strict`     | 完全禁止跨站携带 → **防 CSRF 最强**，但影响外部链接跳转登录态 |
| `SameSite=Lax`        | 默认值；顶层导航 GET 可携带，跨站 POST 不携带                 |
| `SameSite=None`       | 允许跨站，但**必须同时 `Secure`**                             |
| `Domain` / `Path`     | 限定可携带的域名与路径                                        |
| `Max-Age` / `Expires` | 有效期；不设则为「会话 Cookie」，关浏览器即失效               |

**追问点**：为什么把 token 放 `HttpOnly` Cookie 比放 `localStorage` 安全？→ `localStorage` 可被任何 JS 读取，一旦 XSS 就被偷；`HttpOnly` Cookie JS 读不到。但 Cookie 天然带 CSRF 风险，需要 `SameSite` + CSRF Token 兜底。

### 4.10 事件流与事件委托 ★★

**结论**：DOM 事件流分三阶段 —— **捕获（从 window 向下）→ 目标 → 冒泡（向上）**。

**大白话**：事件像水里的气泡：从最外层一路下沉到目标元素（捕获），再从目标一路往上冒（冒泡），默认在冒泡阶段处理。利用「往上冒」这一点，把监听挂在父元素上、用 `e.target` 判断点的到底是谁 —— 新增的子元素不用重新绑，性能也更好。

```js
// 默认在冒泡阶段触发；第三参数 true 则改在捕获阶段
el.addEventListener("click", handler, true); // 捕获
el.addEventListener("click", handler, false); // 冒泡（默认）
```

**事件对象常用**：`e.target`（实际触发者）vs `e.currentTarget`（绑定监听者）；`e.stopPropagation()` 阻止继续传播；`e.preventDefault()` 阻止默认行为（如链接跳转）。

**事件委托**：把子元素的监听挂到**父元素**上，利用冒泡，通过 `e.target` 判断真正触发者。

```js
list.addEventListener("click", (e) => {
  const item = e.target.closest(".item"); // 向上找最近的 .item
  if (!item) return;
  console.log(item.dataset.id);
});
```

**为什么用**：① 只绑一个监听（性能好）；② **动态新增的子元素自动生效**，无需重新绑定。这也是 Vue 里「列表项事件不用写在每个 item 上」的底层原理。

**追问点**：React 的合成事件为什么曾经把监听挂在 `document` 上？→ 统一跨浏览器差异 + 事件池复用。React 17 起改为挂在根容器，解决多版本 React 混用与原生事件冒泡冲突。

## 五、Vue3 核心原理

### 5.1 Vue3 相比 Vue2 的核心变化 ★★

**大白话**：Vue3 最大的变化一句话说完 —— 侦测数据的方式从「提前给每个属性装好钩子」换成了用 `Proxy` 把整个对象包起来站岗。所以以前新增属性、改数组下标侦测不到（要 `$set`），现在都能侦测到。另外，组合式 API 的真正价值不是少写代码，而是「把一个功能的代码聚在一起」。

| 维度          | Vue2                                                                           | Vue3                                           |
| ------------- | ------------------------------------------------------------------------------ | ---------------------------------------------- |
| 响应式        | `Object.defineProperty`（初始化时递归挂 getter/setter，侦测不到增删/索引赋值） | **`Proxy`**（惰性代理、能侦测增删与索引）      |
| 组织方式      | Options API                                                                    | **Composition API**（逻辑关注点聚合、TS 友好） |
| 虚拟 DOM diff | 双端比较，遍历较全                                                             | 编译优化 + patchFlag + 最长递增子序列          |
| 体积          | 全量打包                                                                       | **Tree-shaking** 友好（未用的 API 会被摇掉）   |
| TS 支持       | 一般（要配 `vue-class-component` 等）                                          | 源码 TS 重写，原生友好                         |
| 新特性        | —                                                                              | Fragments、Teleport、Suspense、多 `v-model`    |

**为什么 Vue2 必须用 `$set`**：`Object.defineProperty` 只能在**初始化时**为已知属性挂 getter/setter，**新增属性**和**数组索引赋值**都侦测不到；`Proxy` 代理的是整个对象，任何操作都能被拦截。

**追问点**：Composition API 真正解决的是什么？→ 不是「少写代码」，而是**逻辑关注点聚合** —— 一个功能的 `ref`/`computed`/`watch`/生命周期写在一起，而不是散落在 `data`/`methods`/`mounted` 各处；同时天然更好做类型推导与逻辑抽离（`useXxx`）。

---

### 5.2 Vue3 响应式原理（Proxy）★★★

**结论**：用 `Proxy` 包裹对象拦截 `get/set/deleteProperty`，配合 `Reflect` 操作原对象。依赖收集用 `effect` + `track`（get 时收集） / `trigger`（set 时派发）。

**大白话**：响应式的本质是「谁用了我的数据，我就记住谁」。读数据时（`get`）把当前正在跑的那个函数记到小本本上，改数据时（`set`）翻小本本，把记下的人全叫起来重跑一遍。小本本是三层的：哪个对象 → 哪个属性 → 有哪些函数在用。

```js
// 简化实现
function reactive(target) {
  return new Proxy(target, {
    get(obj, key, receiver) {
      track(obj, key); // 收集依赖
      return Reflect.get(obj, key, receiver);
    },
    set(obj, key, value, receiver) {
      const res = Reflect.set(obj, key, value, receiver);
      trigger(obj, key); // 触发更新
      return res;
    },
  });
}
```

**依赖存储结构**（WeakMap 三级）：

```
WeakMap<target, Map<key, Set<effect>>>
```

**相比 Vue2 的优势**：

1. 可监听**数组索引**和**对象新增/删除**属性（Vue2 需 `$set`）；
2. **懒代理**：只有访问到嵌套对象时才递归代理，初始化性能更好；
3. 无需重写数组方法。

**为什么用 `Reflect` 而不是 `obj[key]`**：`Reflect.get/set` 能把 `receiver` 正确透传给原型链上的 getter/setter，保证 `this` 指向**代理对象**（否则继承场景下依赖收集会指向错误对象）。

**`effect` 与依赖收集**：`effect` 是被包装的函数 —— **渲染、`computed`、`watch` 底层都是 effect**。执行时把「当前 activeEffect」压栈；`get` 时 `track` 把它收进依赖表；`set` 时 `trigger` 找出对应 effect，**交给调度器排队**（见 5.15）。

**追问点**：`reactive` 的局限？→ 对**基本类型**无效（要用 `ref`）、直接解构会**丢失响应式**（要用 `toRefs`）、`Proxy` **不支持 IE**；另外 `reactive` 对象整体替换会丢响应式。

---

### 5.3 ref 与 reactive ★★

| 维度       | `ref`                              | `reactive`          |
| ---------- | ---------------------------------- | ------------------- |
| 类型       | 任意（基本 + 引用）                | 仅对象/数组/Map/Set |
| 访问       | `.value`（模板自动解包）           | 直接访问            |
| 实现       | `RefImpl`（对象内部转 `reactive`） | `Proxy`             |
| 替换整个值 | 支持                               | 丢失响应式          |

**结论**：优先 `ref`（心智负担小、类型好推、可整体替换），需要一组强关联状态用 `reactive`。

**大白话**：纠结 `ref` 还是 `reactive`，记两句就够：`ref` 什么都能装、模板里不用写 `.value`、整体替换也不丢响应式；`reactive` 只能装对象、不能整体替换、解构出来就废了。所以默认用 `ref` 更省心。

**原理**：`ref` 内部是 `RefImpl`，用 `get value()` / `set value()` 拦截；值若是对象，`.value` 内部再用 `reactive` 包一层。`reactive` 直接返回 `Proxy`。

**为什么 `reactive` 解构会丢响应式**：解构拿到的是**当时那个值**（基本类型直接拷贝、对象脱离 `Proxy` 拦截），不再走 get/set。要保住响应式得用 `toRefs` 把每个属性转成 `ref`。

**追问点**：

- `ref` 在模板里为什么不用写 `.value`？→ 模板编译对**顶层 ref 自动解包**（`setup` 返回的 ref 会经 `proxyRefs` 处理）。注意：**嵌套在 props、数组、`reactive` 对象里的 ref 不会自动解包**。
- `shallowRef` / `shallowReactive` / `toRef` / `toRefs` / `unref` 各自用途？→ 前两个只做**浅层**响应（深层变化不触发）；`toRef(s)` 转成 ref 以保住解构后的响应式；`unref(x)` = `isRef(x) ? x.value : x`。

---

### 5.4 computed / watch / watchEffect ★★

**大白话**：`computed` 是「算出来的值」，有缓存，依赖不变就不重算；`watch` 是「盯着变化去干别的事」，比如发请求、打日志。一句话分工：**要产生数据用 computed，要干副作用用 watch**。`watchEffect` 省去了写依赖，代价是拿不到旧值。

| API           | 语义     | 特性                                                        |
| ------------- | -------- | ----------------------------------------------------------- |
| `computed`    | 派生值   | 有缓存、依赖不变不重算；默认惰性                            |
| `watch`       | 侦听源   | 惰性（默认不立即）、可拿新旧值、可配 `deep/immediate/flush` |
| `watchEffect` | 自动追踪 | **立即执行**、自动收集依赖、拿不到旧值                      |

```js
const total = computed(() => price.value * count.value); // 缓存
watch(total, (n, o) => console.log(n, o), { immediate: true });
watchEffect(() => console.log(count.value)); // 立即跑一次
```

**`computed` 的缓存原理**：内部是「带 `dirty` 标记的 effect」—— 依赖变化时只把 `dirty = true`，**下次访问才重算**；依赖没变就直接返回缓存值。

**`watch` 的可侦听源**：`ref` / `reactive` 对象 / `getter` 函数 / 数组（多个源同时监听）。

**追问点**：

- `watch` 监听 `reactive` 对象默认**是深层**的（自动 deep），监听 `ref` 对象则需显式 `deep: true`。
- `flush: 'post'` 让回调在 DOM 更新后执行（想读新 DOM 时用）。
- 什么时候用 computed 而不是 watch？→ **派生数据用 computed，副作用用 watch**（改别的状态、发请求、打日志）。
- `watch(() => obj.a, cb)` 能侦测到 `obj.a` 内部变化吗？→ 不能，只能侦测 `a` 的**引用**变化；要深层要加 `{ deep: true }`，或写成 `() => obj.a.b`。

---

### 5.5 Vue3 生命周期 ★★

**大白话**：生命周期就是组件的「出生到销毁」。Vue2 的 `created` 现在等于 `setup` 顶层的同步代码，`destroy` 改名成了 `unmount`。高频考点是父子顺序：挂载时**子组件的 `mounted` 先跑完，父的才跑**（父要等子装好）；卸载时反过来。

`setup` → `onBeforeMount` → `onMounted` → `onBeforeUpdate` → `onUpdated` → `onBeforeUnmount` → `onUnmounted`；另有 `onActivated/onDeactivated`（keep-alive）、`onErrorCaptured`。

**与 Vue2 的对应**：`beforeCreate` / `created` → `setup`；`beforeDestroy` → `onBeforeUnmount`；`destroyed` → `onUnmounted`。

**父子生命周期顺序（高频）**：

- 挂载：父 `onBeforeMount` → 子 `onBeforeMount` → 子 `onMounted` → **父 `onMounted`**（父的晚于子）。
- 卸载：父 `onBeforeUnmount` → 子 `onBeforeUnmount` → 子 `onUnmounted` → 父 `onUnmounted`。

**追问点**：

- `setup` 里为什么拿不到 DOM？→ `setup` 执行早于 `beforeCreate`，组件实例尚未挂载；要操作 DOM 用 `onMounted`（必要时 + `nextTick`）。
- 组合式 API 里没有 `created`？→ 写在 `setup` 顶层的同步代码就等价于 `created` 时机。

---

### 5.6 组件通信方式 ★★

**大白话**：通信方式按「关系远近」选：父子用 `props/emit`（最正统），跨好几层用 `provide/inject`，全局用 Pinia，父组件想直接调子的方法用 `ref` + `defineExpose`。`v-model` 本质就是 `props` + `emit` 的语法糖（`:modelValue` + `@update:modelValue`）。

| 方式                         | 适用场景     | 说明                                      |
| ---------------------------- | ------------ | ----------------------------------------- |
| `props` / `emit`             | 父子         | 最基础的**单向数据流**                    |
| `v-model` / 多个 `v-model`   | 父子双向     | 本质 `:modelValue` + `@update:modelValue` |
| `provide` / `inject`         | 跨多层级     | 祖先提供给后代，避免 props 逐层透传       |
| `ref` + `defineExpose`       | 父调子方法   | 命令式调用（打开弹窗、重置表单）          |
| `$attrs` / `v-bind="$attrs"` | 属性透传     | 二次封装组件时把未知 props/事件透给内层   |
| Pinia / store                | 全局/跨页面  | 跨路由、跨组件的共享状态                  |
| `mitt` 事件总线              | 无关联组件   | 轻量解耦，但要小心事件泄漏                |
| 作用域插槽                   | 子给父传数据 | 父决定渲染方式，子提供数据                |

**追问点**：

- `v-model` 的本质？→ `:modelValue` + `@update:modelValue`；Vue3 支持 `v-model:title` 具名双向绑定（一个组件可挂多个）。
- `provide/inject` 传递的数据是响应式的吗？→ 传 `ref`/`reactive` 才是；传普通值只是一次性快照。且 inject 拿到的**不是**响应式代理时，子组件改不动父的数据。

---

### 5.7 nextTick 原理 ★★★

**结论**：`nextTick` 把回调放进一个微任务队列，等本轮「响应式更新引起的 DOM 变更」全部 flush 完再执行。

**大白话**：改数据不会立刻改 DOM，Vue 会把同一轮里的多次修改攒起来一次渲染完（所以改 100 次也只渲染 1 次）。那改完马上想读新 DOM 怎么办？`await nextTick()` 就是「等这一批渲染干完再往下走」。

- Vue3 用 `Promise.then`（微任务）实现；降级顺序：`Promise` → `MutationObserver` → `setImmediate` → `setTimeout`。
- **同一 tick 内的多次数据变更会合并成一次 DOM 更新**（异步批量更新），所以拿到的是最终 DOM。

```js
count.value++;
await nextTick();
console.log(el.textContent); // 已更新
```

**为什么用微任务而不是宏任务**：微任务在当前宏任务末尾就执行，能拿到**最新且完整**的一批 DOM 变更；用宏任务会拖到下一帧，体验更差。

**`nextTick` 与调度器的关系**：`nextTick(fn)` 等价于把 `fn` 挂到「本轮 flush 的 Promise」后面，所以它一定晚于**本次所有 effect 执行完**。

**追问点**：

- 为什么改完数据立刻读 DOM 拿到的是旧值？→ 更新是异步批量的，DOM 还没 patch。
- 连续 `count.value++` 三次要调几次 `nextTick`？→ 一次就够，三次变更会被合并成同一次 flush。

---

### 5.8 虚拟 DOM 与 diff 算法 ★★★

**大白话**：虚拟 DOM 就是用 JS 对象描述界面，改完先比对新旧对象，只动真正变化的 DOM。Vue3 的做法是先在头尾把相同的部分刨掉，中间乱序的那段用「最长递增子序列」找出「本来就不用动的那些」，剩下的才移动 —— 这样 DOM 挪动次数最少。

**核心流程**：`patch` 对比新旧 vnode，同类型节点走 `patchElement`，子节点走 diff。

**Vue3 diff 关键点**：

1. **编译时优化**：静态节点被打上 `HOISTED` 提升、动态属性记 `patchFlag`（只比动态部分）、`Block Tree` 减少遍历范围。
2. **子节点 diff**：
   - 先处理**头部相同**（i 向后）与**尾部相同**（新后向前）的节点；
   - 剩下乱序部分，为**旧节点建 key → index 映射**，遍历新节点求「最长递增子序列（LIS）」，**LIS 中的节点保持不动**，其他节点移动/新增/删除，最小化 DOM 移动次数。

**Vue2 双端比较 vs Vue3 LIS**：Vue2 用「头头 / 尾尾 / 头尾 / 尾头」四指针两两比较；Vue3 在乱序段建映射后求**最长递增子序列**，LIS 内的节点**原地不动**，只移动其余节点 —— **DOM 移动次数最少**。

**追问点**：为什么需要 `key`？→ 帮助 diff 精确识别节点身份，避免**就地复用**导致的「状态错乱」（如输入框内容串行）。

---

### 5.9 key 的作用与坑 ★★

**结论**：`key` 是 vnode 的**唯一标识**，让 diff 能正确匹配新旧节点、决定谁复用谁重建。

**大白话**：`key` 就是给列表每一项发张身份证。没有身份证（或拿下标当身份证），插入 / 删除之后 Vue 会认错人、就地复用，结果就是输入框里的字串行、动画乱跳。用后端返回的唯一 id 就没这问题。

- 用**索引当 key**：列表中间插入/删除时会导致**就地复用错位**（输入框内容、组件内部状态、动画串行）。
- 用**随机数/时间戳当 key**：每次渲染 key 都变 → **全量重建**，性能更差。
- 正确做法：用**稳定唯一 id**（后端返回的主键）。

```html
<!-- ❌ 索引 key：在头部插入一项后，所有项的输入框内容都错位 -->
<li v-for="(item, i) in list" :key="i">{{ item.name }}</li>
<!-- ✅ 唯一 id -->
<li v-for="item in list" :key="item.id">{{ item.name }}</li>
```

**追问点**：什么时候可以用索引当 key？→ 列表**只做尾部追加、不重排、不删除中间项**，且项内无状态（无输入框、无动画）时可以用；只要涉及重排/插删，就必须用唯一 id。

---

### 5.10 v-if 与 v-show ★

**大白话**：`v-if` 是「真的删掉 / 重新造」，`v-show` 是「藏起来（`display: none`）」。所以切得勤的用 `v-show`（便宜），条件基本不变、或者一开始就不该渲染的用 `v-if`（比如权限模块）。

| 维度     | `v-if`                                | `v-show`               |
| -------- | ------------------------------------- | ---------------------- |
| 原理     | **销毁 / 重建** DOM（真实的条件渲染） | 切换 `display: none`   |
| 初次渲染 | **惰性**，条件为假时不渲染            | 一定渲染（哪怕不显示） |
| 切换开销 | 高（触发组件生命周期、重建）          | 低（只改 style）       |
| 适用     | 运行时条件**很少变**                  | 需要**频繁切换**       |

**怎么选**：权限节点、只在特定角色出现的模块 → `v-if`；tab 切换、折叠展开、频繁显隐 → `v-show`。

**追问点**：`v-if` 与 `v-for` 不要同用（Vue3 中 `v-if` 优先级更高，取不到 `v-for` 的变量）→ 正确做法是用 computed 先过滤，或把 `v-if` 挪到外层 / 内层 `<template>` 上。

---

### 5.11 keep-alive 原理 ★★

**结论**：`<keep-alive>` 缓存组件实例，避免重复销毁 / 重建。内部维护 `cache`（key → vnode）与 `keys` 数组，命中就复用实例并触发 `activated`；切走时触发 `deactivated`（**不销毁**）。

**大白话**：`keep-alive` 就是把组件「存起来不扔」，切回来直接复用，所以滚动位置、表单内容都还在。坑是：被存着的组件不会再走 `mounted/unmounted`，所以「每次进来都要刷新数据」的逻辑必须写到 `onActivated` 里。

- `include` / `exclude`（按组件 `name` 匹配）、`max`（超出后按 **LRU** 淘汰最久未用的）。

**注意**：被缓存的组件**不会**再触发 `onMounted` / `onUnmounted`，所以「每次进入都要刷新数据」的逻辑必须写进 `onActivated`。

**追问点**：

- 被缓存的组件如何强制刷新？→ 动态改 `key` 让它重建、`include` 里临时移除、或用 `activated` 里重新拉数据。
- keep-alive 与多标签页后台管理什么关系？→ 典型用法：缓存 tab 打开的页面，切 tab 不丢状态（滚动位置、表单、查询条件）；关闭 tab 时把它的 name 从 `include` 移除即可销毁。

### 5.12 逻辑复用：组合式函数（composables）★★★

**结论**：把有状态的逻辑抽成 `useXxx()` 函数，内部用 `ref/computed/watch`，返回响应式引用，实现「逻辑复用」而非「选项复用」（解决了 Vue2 mixin 的命名冲突、来源不清、隐式依赖问题）。

**大白话**：composable 就是「把一段有状态的逻辑打包成一个 `useXxx` 函数」，谁要用就调一下。变量从哪来一眼看清、重名也不打架（这两点比 mixin 强）。注意里面写的 `ref` 每次调用都是新的一份，想全局共享得把它提到模块作用域。

```ts
export function useRequest<T>(fetcher: () => Promise<T>) {
  const data = ref<T>();
  const loading = ref(false);
  const error = ref<unknown>();
  const run = async () => {
    loading.value = true;
    try {
      data.value = await fetcher();
    } catch (e) {
      error.value = e;
    } finally {
      loading.value = false;
    }
  };
  return { data, loading, error, run };
}
```

**相比 Vue2 mixin 的优势**：**来源清晰**（变量谁引入的一眼看到）、**无命名冲突**（同名变量各自独立）、**依赖显式**（传参而非隐式 this）、**可 tree-shaking**。

**带生命周期的 composable**：内部直接调 `onMounted` / `onUnmounted` 是合法的（只要在 `setup` 同步执行期调用），这也是「定时器/监听器自动清理」的标准写法。

**追问点**：

- composable 里的响应式状态是「每个调用各一份」还是共享？→ 函数内 `ref` 每次调用新建（各一份）；要共享需把状态提到**模块作用域**（模块单例，如 `utils/aiDrawer.ts` 那种写法）。
- 什么时候不该抽 composable？→ 只被一处使用、或纯粹是「无状态工具函数」时 —— 后者直接写 `utils/*.ts` 就行，不必套 composable 壳。

### 5.13 其他 Vue3 特性 ★★

**大白话**：这几个特性「知道是什么、能说出用途」就够了。最实用的是 `Teleport`：把弹窗挂到 `body` 下，一口气摆脱父级 `overflow` 和层叠上下文的坑。`Suspense` 管异步组件的加载态，`defineAsyncComponent` 做懒加载减首屏体积。

- **Teleport**：把子节点渲染到 DOM 其他位置 —— 弹窗、Modal 挂到 `body` 下，**摆脱父级 `overflow: hidden` 与层叠上下文的限制**（对应 3.5 那个坑）。
- **Suspense**：等待异步组件 / `async setup`，统一处理加载态与错误（配 `defineAsyncComponent` 用）。
- **自定义指令**：`v-focus`、`v-permission`、`v-lazy`；钩子 `created / beforeMount / mounted / beforeUpdate / updated / beforeUnmount / unmounted`。
- **`defineAsyncComponent`**：路由与重型组件懒加载（首屏减重）。
- **Fragments**：模板可返回**多个根节点**（Vue2 必须单根）。
- **`v-memo`**：显式跳过子树更新，长列表/大表格里少见的性能利器。
- **样式特性**：`<style scoped>`、`v-bind()` 在 CSS 里绑定响应式变量、`:deep()` 深度选择器。

**追问点**：Teleport 有什么代价？→ 逻辑上仍是父组件的子组件（props/事件照常），但 **DOM 位置被移走**，所以**样式（scoped 属性）与事件冒泡/DOM 查询**要重新考虑。

### 5.14 模板编译流程与编译时优化 ★★★

**结论**：Vue3 的「快」一半靠 `Proxy` 响应式，另一半靠**编译时把信息提前算好**，让运行时 diff 少干活。

**大白话**：Vue3 快的一半功劳在编译阶段 —— 编译时就把话说死了：哪块永远不变（静态提升，只创建一次）、哪块是动态的（打上 `patchFlag` 标记）。运行时就不用漫无目的地全量比对，只比标记过的地方。

**编译三步**（`@vue/compiler-core`）：

```
template 字符串
  → parse     生成 AST（模板语法树）
  → transform 遍历 AST 做转换（v-if/v-for、静态提升、patchFlag 标记）
  → generate  生成 render 函数（可执行字符串 / 编译时）
```

**关键优化手段**：

| 优化                         | 作用                                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------------------- |
| **静态提升 Static Hoisting** | 纯静态节点只创建一次，`render` 里直接复用（`_hoisted_1`），不参与 diff                   |
| **patchFlag 靶向更新**       | 动态节点打标记（`1` 文本 / `8` props / `16` class...），`patchElement` 只比标记的那部分  |
| **Block Tree**               | `v-if`/`v-for` 会「开洞」收集动态节点成扁平数组，diff 时**只遍历动态节点**，跳过静态结构 |
| **静态节点缓存**             | 大量静态内容（如超长表格）不重复创建 vnode                                               |
| **v-once / v-memo**          | 显式告诉编译器「这块不会变 / 只有这些依赖变时才更新」                                    |

```html
<!-- 编译后大致：class 是动态的 → patchFlag = 1（TEXT）或 8（PROPS） -->
<div :class="cls">静态文字{{ msg }}</div>
```

**追问点**：为什么 `v-for` 的 `key` 对 Block Tree 更重要？→ 动态子节点被拍平进 Block 数组，若无稳定 key，diff 会错位复用。用索引 key 在这类结构里更容易出问题。

### 5.15 响应式调度器 Scheduler ★★★

**结论**：改数据**不会立刻**重渲染 —— Vue3 内部有个**调度器**把副作用排队，用微任务批量 flush。

**大白话**：改数据不是马上重渲染，而是「先记到待办清单」，同一个渲染任务只记一次，然后在一个微任务里统一执行。这就解释了三件事：改 100 次只渲染 1 次、马上读 DOM 读到的是旧值、父组件总是先于子组件更新。

```
数据变更 → trigger 找到 effect → 该 effect 入队
        → 去重（同一 effect 只入一次）
        → queueMicrotask 排一次 flush
        → flushJobs 按 id 升序执行（父组件先于子组件）
        → patch DOM
```

**这解释了三件事**：

1. **同一 tick 改 100 次数据只渲染 1 次**（effect 去重 + 批量 flush）。
2. **同步读 DOM 拿到旧值**（更新还没 flush）→ 用 `await nextTick()`。
3. **父子更新顺序**：组件的 effect id 按创建顺序递增，父先创建 → 父先更新，天然保证子组件能看到新 props。

**追问点**：`watch` 的 `flush` 选项？→ `pre`（默认，DOM 更新前）、`post`（DOM 更新后，等价于想读新 DOM 时用）、`sync`（同步触发，慎用，会拖慢）。

## 六、Vue 工程实践

### 6.1 Pinia 与 Vuex 的区别 ★★

| 维度    | Vuex                      | Pinia                    |
| ------- | ------------------------- | ------------------------ |
| 形态    | 单一 store 树 + mutations | 多个独立 store（可组合） |
| 修改    | `commit` mutation         | 直接改 state             |
| TS 支持 | 弱                        | **原生友好**             |
| 异步    | `actions`                 | `actions`（同）          |
| 体积    | 大                        | 小，去掉了 mutation      |

**结论**：Pinia 是 Vue3 官方推荐的状态管理，本质是「**多个可组合的独立 store + 原生 TS 推导**」。

**大白话**：Pinia 相比 Vuex 最大的变化是「去掉了 mutation 这层中间商」，直接改 `state` 就行，devtools 照样能追踪；而且每个模块是独立的 store，不再是拧在一起的一棵大树，TS 推导也更准。注意解构 store 会丢响应式，得用 `storeToRefs`。

```ts
// Setup Store 写法（组合式风格，推荐）
export const useUserStore = defineStore("user", () => {
  const profile = ref<User | null>(null);
  const isLogin = computed(() => !!profile.value);
  async function fetchProfile() {
    profile.value = await api.getUser();
  }
  return { profile, isLogin, fetchProfile };
});
```

**常用要点**：

- 解构 store 会**丢响应式**，要用 `storeToRefs(store)`（方法直接解构没问题）。
- 两种写法：**Setup Store**（`ref`/`computed`/函数，等价于组合式组件）与 **Option Store**（`state`/`getters`/`actions`）。
- 持久化：配 `pinia-plugin-persistedstate` 落到 `localStorage`。

**追问点**：

- 为什么去掉了 mutations？→ 单一职责冗余，actions 已能承担所有变更；直接改 state 在 devtools 里同样可追踪。
- 什么时候不该上 Pinia？→ 只在一个页面/组件树内共享的状态，用 `provide/inject` 或模块单例 `ref` 就够，别为状态管理而状态管理。

### 6.2 路由守卫与权限设计 ★★★

**大白话**：路由守卫就是「进门前先刷卡」。两个坑要记牢：一是别把守门逻辑也套在登录页上，否则自己拦自己转圈；二是守卫里如果异步拉用户信息，这段时间页面是白的，得先给个 loading。还有最重要的一句：前端权限只管体验，真正的校验必须在后端。

```js
router.beforeEach(async (to, from, next) => {
  const userStore = useUserStore();
  if (to.meta.public) return next();
  if (!userStore.isLogin) {
    await userStore.tryRestoreSession();
    if (!userStore.isLogin)
      return next({ name: "Login", query: { redirect: to.fullPath } });
  }
  if (to.meta.roles && !to.meta.roles.includes(userStore.role)) {
    return next({ name: "Forbidden" });
  }
  next();
});
```

**要点**：

- **路由级懒加载**：`component: () => import(...)`，按页面拆 chunk。
- **`meta` 存权限与标题**：`meta.public` / `meta.roles`，一个守卫统一处理。
- **动态 `addRoute`**：登录后按后端返回的菜单**动态注入路由**（未登录时这些路由根本不存在，比"隐藏菜单"安全）。
- **`afterEach` 收尾**：进度条、埋点、滚动复位。

**极易踩的两个坑**：

- **死循环**：守卫里跳登录页时，登录页若也命中守卫 → 必须放行 public 路由（或用 `next()` 而非重定向）。
- **白屏**：守卫是异步的（拉用户信息），期间要**先 `next()` 放行或给 loading**，否则用户看到空白。

**追问点**：**前端权限只是体验层，真正的安全校验必须在后端** —— 前端藏起来的接口，攻击者照样能直接调用。

---

### 6.3 请求层封装 ★★

**大白话**：请求层封装就是把「每个页面都在重复写的那些事」收口到一处：统一 baseURL 和超时、自动带 token、统一判业务码并弹错误、剥掉外层只返回 `data`。封一层拦截器，业务代码自然就干净了。

**要点**：

- **统一 baseURL / 超时 / 鉴权头**：token 注入、401 无感刷新（见 10.6）。
- **响应拦截**：业务码判断（`code !== 0` 视为失败）、错误统一 `message`、剥掉外层只返回 `data`。
- **请求拦截**：加 token、加 traceId、过滤空参数。
- **取消重复请求**：同一接口在途时用 `AbortController` 取消前一个（防搜索框竞态）。
- **并发控制 / 重试**：见 1.7；重试要区分可重试错误。
- **TS 泛型约束**返回结构，调用处自动推 `data` 类型。

```ts
const service = axios.create({ baseURL: "/api", timeout: 10000 });
service.interceptors.response.use(
  (res) => {
    const { code, data, message } = res.data;
    if (code !== 0) {
      Message.error(message);
      return Promise.reject(new Error(message));
    }
    return data;
  },
  (err) => Promise.reject(err),
);
```

**追问点**：

- 为什么业务错误不用 HTTP 状态码而用 `code` 字段？→ HTTP 200 + `code` 能区分「网络层成功」与「业务层失败」，且能承载更细的业务子码；但要注意别把 500 也包成 200（会让监控失效）。
- 拦截器里 `return data` 有什么副作用？→ 响应类型被"剥壳"，TS 里要给 `service.request<T>` 补泛型，否则调用处拿到的类型不对。

---

### 6.4 大表单 / 大表格优化 ★★★

**大白话**：大表单的思路是「别一次全渲染、别一次全校验」—— 分段挂载 + 只校验当前字段；大表格的思路是「别把几千行真 DOM 全铺出来」—— 能分页就分页，必须滚动就虚拟滚动，只画看得见的那几行。

**大表单（几百个字段）**：

- **动态组件拆分**：按步骤/分组用 `<component :is>` 或 `v-if` 分段渲染，**只挂载当前可见部分**。
- **按需校验**：`el-form` 的 `validateField` 局部校验，别每次全量 `validate()`。
- **受控统一**：字段统一走 `modelValue` + `update:modelValue`，便于回填与联动。
- **本地草稿**：大表单存 `sessionStorage`，防误刷丢失。

**大表格（几千~几万行）**：

- **虚拟滚动**（`el-table-v2` / `vue-virtual-scroller`）—— 只渲染视口内的行。
- **分页 + 服务端筛选/排序**（能分页就别硬扛前端）。
- **列冻结 / 列懒渲染**：横向滚动时只渲染可视列。
- **`v-memo` 缓存静态行**、`requestAnimationFrame` 批量提交 DOM。

**红线**：**不要**一次性渲染几千行真实 DOM；也不要给每一行都挂一堆事件监听（用事件委托）。

---

### 6.5 组件设计原则 ★★

**结论**：好组件的标准是「**职责单一、接口清晰、状态归属正确**」。

**大白话**：好组件的标准就三句：一件事只干一件事、对外接口一眼看懂、数据归谁管要明确。落到代码上就是：`props` 只读，想改就 `emit` 让父组件改；能自定义的内容用插槽，别堆一堆 `xxxText` 这种 props。

- **单向数据流**：props 只读，子组件想改就 `emit` 让父改 —— 别在子组件里直接改 props（Vue 会警告，且破坏数据流向可预测性）。
- **受控 vs 非受控**：受控组件（值由外部 `v-model` 控制）便于表单联动、校验、回填；非受控（组件自己管状态）用起来轻。**表单类组件优先受控**。
- **`v-model` 设计**：默认 `modelValue` + `update:modelValue`；复杂组件可拆多个具名 `v-model`（如 `v-model:visible` / `v-model:page`）。
- **插槽而非配置**：能用插槽表达的自定义内容，别堆 `xxxText`、`xxxRender` 这类 props。
- **`defineProps` / `defineEmits` 必写类型**，`defineExpose` 只暴露必要方法。

```vue
<script setup lang="ts">
const props = defineProps<{ modelValue: string; placeholder?: string }>();
const emit = defineEmits<{ "update:modelValue": [v: string] }>();
</script>
<template>
  <input
    :value="props.modelValue"
    :placeholder="props.placeholder"
    @input="
      emit('update:modelValue', ($event.target as HTMLInputElement).value)
    "
  />
</template>
```

**追问点**：为什么不要 `v-model` 直接绑定 props？→ props 单向只读，双向绑定等于子组件偷偷改父数据，数据来源不清、难以排查。

---

### 6.6 单元测试与组件测试 ★★

**大白话**：单测测的是「组件从输入到输出的表现」—— 给它什么 props、点了之后 `emit` 什么。别去测内部实现细节（内部变量叫什么、私有方法调了几次），不然一重构测试就全红。工具上用 Vitest + `@vue/test-utils`。

- **Vitest**：与 Vite 同配置、极快，替代 Jest 做 Vue 项目单测首选。
- **`@vue/test-utils`**：`mount`（完整渲染）/ `shallowMount`（子组件打桩），断言 DOM 与 emit。
- **测什么**：纯函数工具、composable、组件的**输入 → 输出**（props/emit/插槽），别测实现细节。
- **不测什么**：别断言内部 `ref` 的名字、别断言私有方法调用次数 —— 重构就红。

```ts
import { mount } from "@vue/test-utils";
it("点击后 emit update:modelValue", async () => {
  const w = mount(MyInput, { props: { modelValue: "" } });
  await w.find("input").setValue("hi");
  expect(w.emitted("update:modelValue")![0]).toEqual(["hi"]);
});
```

**追问点**：E2E（Cypress / Playwright）与单测的边界？→ 单测覆盖逻辑分支（快、稳），E2E 覆盖关键业务链路（慢、真实但脆弱），比例通常金字塔形（单测多、E2E 少）。

## 七、前端工程化

### 7.1 Vite 与 Webpack 的区别 ★★★

**大白话**：Vite 开发时为什么快？因为「不打包」—— 浏览器原生支持 ESM，要哪个模块现要现编译，所以启动时间与项目大小基本无关（Webpack 得先整个打完才能起来）。第三方依赖用 esbuild 提前转成 ESM 备好，避免几百个小请求的瀑布。

| 维度   | Webpack                 | Vite（开发）                               | Vite（生产） |
| ------ | ----------------------- | ------------------------------------------ | ------------ |
| 原理   | 打包成 bundle 再启动    | **原生 ESM 按需编译** + esbuild 预构建依赖 | Rollup 打包  |
| 冷启动 | 慢（依赖越多越慢）      | 极快（不预先打包）                         | —            |
| HMR    | 基于 bundle，随规模变慢 | 基于模块图，与模块数解耦                   | —            |

**Vite 快的根本原因**：

- **不做全量打包**：开发时浏览器直接请求 ESM 模块，服务端按需编译单文件，启动时间与项目规模**解耦**。
- **依赖预构建**：用 esbuild 把 CJS/UMD 依赖（如 `lodash`）转成 ESM 并合并，解决"几百个模块请求"的瀑布问题。

**追问点**：

- Vite 生产为什么用 Rollup 而非 esbuild？→ Rollup 的 **tree-shaking、代码分割、插件生态**更成熟（esbuild 打包能力相对弱）。
- 为什么 Vite 开发快、但生产构建仍可能慢？→ 生产要走完整打包 + 压缩 + 产物优化，规模大时依然耗时。

---

### 7.2 HMR 原理 ★★

**结论**：Dev Server 与浏览器建 **WebSocket**；文件变更时服务端沿**模块依赖图**找到受影响模块边界，只把变更模块推给浏览器，浏览器动态 `import` 新模块并替换。

**大白话**：HMR 就是「改哪个模块只换哪个模块，页面不刷新、状态不丢」。服务端用 WebSocket 推一条消息告诉浏览器「这个文件变了」，浏览器重新 `import` 一下替换掉。如果改的是没人接得住的文件（入口、全局 store 定义），就只能整页刷新。

**完整链路**：

```
chokidar 监听文件 → 变更 → 沿 import 图找「接受热更新的边界」
  → 通过 WebSocket 推送 { type:'update', path }
  → 浏览器 import 新模块 → 执行 HMR accept 回调替换
  → 若无人 accept（如入口变了）→ 整页 reload
```

**Vue SFC 怎么做到热替换**：编译时把 `<template>` / `<script>` / `<style>` 拆成独立模块，各自注册 `import.meta.hot.accept` —— 改样式只替换样式、改模板只重渲染，**组件实例状态得以保留**。

**追问点**：什么情况下 HMR 会退化成整页刷新？→ 改动了「没有接受热更新的模块」（如 `main.ts`、全局 store 定义、新增文件未被引用）；这时框架只能全量 reload。

---

### 7.3 打包优化 ★★

**大白话**：打包优化的正确姿势是「先看再砍」—— 用分析工具找出到底哪个包最大，再针对性地拆包 / 外链 / 换更小的库。顺序一般是：拆包（懒加载 + vendor 分包）→ 压缩（gzip/brotli）→ 图片优化。别一上来瞎加配置。

| 手段                | 做法                                                   | 效果                 |
| ------------------- | ------------------------------------------------------ | -------------------- |
| **代码分割**        | 路由懒加载、`manualChunks` 拆 `vendor`                 | 首屏只加载必要 chunk |
| **Tree-shaking**    | 用 ESM、`sideEffects: false`、避免 `import * as`       | 摇掉未用代码         |
| **压缩**            | `Terser` / `esbuild` 压缩 + gzip / **brotli**          | 传输体积大降         |
| **CDN / externals** | 大依赖外链到 CDN                                       | 减小产物、利用缓存   |
| **图片优化**        | 压缩、`webp/avif`、`srcset` 按需                       | 图片常是首屏最大头   |
| **分析定位**        | `rollup-plugin-visualizer` / `webpack-bundle-analyzer` | 先量后优化，别瞎猜   |

**正确顺序**：先用分析工具**看大包在哪**，再动手 —— 优化没度量就是瞎加配置。

---

### 7.4 浏览器兼容与 Polyfill ★★

**大白话**：兼容分两种：语法不支持靠构建降级（babel 把新语法翻译成老的），API 缺失靠 polyfill 补（core-js 帮你实现 `Promise.allSettled`）。polyfill 会实打实占体积，所以要么按 `browserslist` 精准引，要么干脆放弃老浏览器。

- **`browserslist`**：声明目标浏览器范围，是所有工具（babel / autoprefixer / postcss）的**共同输入**。
- **`@vitejs/plugin-legacy`**：为老浏览器额外产出 legacy bundle + `SystemJS` + polyfill（现代浏览器走正常包，不背包袱）。
- **core-js**：补齐运行时缺失的 API（`Promise`、`Array.prototype.flat` 等）。

**两种"兼容"要分清**：

- **语法兼容**（如 `??`、可选链）→ 靠 **babel/构建降级**。
- **API 兼容**（如 `Promise.allSettled`）→ 靠 **polyfill**（core-js），polyfill 会在生产包里占体积。

**追问点**：polyfill 有什么代价？→ 会增加包体积与启动开销，所以要么按 `browserslist` **精准引入**（`useBuiltIns: 'usage'`），要么干脆放弃老浏览器（现代 Vite 默认只面向支持 ESM 的浏览器）。

---

### 7.5 包管理与 Monorepo ★★

**大白话**：包管理器之争的关键是 `node_modules` 怎么摆。npm 把依赖全拍平放在一起，于是你能 `import` 到「没在自己 `package.json` 里声明的包」（幽灵依赖），别人一升级你就莫名报错。pnpm 用硬链接 + 严格目录结构，从根上禁掉这件事。

- **npm**：把依赖摊平成嵌套/扁平 `node_modules`，同一包可能被装多份；锁文件 `package-lock.json`。
- **yarn**：早期靠 `yarn.lock` 保证安装确定性，后来也做 PnP（不再生成 node_modules）。
- **pnpm**：**硬链接 + 内容寻址存储**，同一版本在全盘只存一份；`node_modules` 用**符号链接**结构，天然**杜绝幽灵依赖**（没在 `package.json` 里声明的包 import 不到）。

**幽灵依赖是什么**：`npm` 把依赖摊平后，你没声明却能 `import` 到别人的依赖 —— 一旦那个包升级/移除，你的代码就莫名报错。`pnpm` 的严格结构从源头禁掉它。

**monorepo 方案**：`pnpm-workspace.yaml` 声明 `packages/*`，内部包互相引用；发布用 `changesets` 管理版本与 changelog。

**追问点**：monorepo 的代价？→ 构建/CI 复杂度上升、依赖版本要统一（否则出现多份 React/Vue）、仓库变大变慢；**只有真正共享代码的多个包**才值得上。

---

### 7.6 代码规范工具链 ★★

**大白话**：分工别搞混：ESLint 管「代码有没有写错、有没有隐患」，Prettier 只管「排版好不好看」，两者冲突就用 `eslint-config-prettier` 把格式规则关掉。Husky + lint-staged 的作用是「提交前只对改动过的文件跑一遍检查」，快。

| 工具                    | 职责                                                       |
| ----------------------- | ---------------------------------------------------------- |
| **ESLint**              | 代码质量与潜在 bug（未使用变量、`==`、hook 依赖缺失）      |
| **Prettier**            | 纯粹格式化（缩进、引号、换行），与 ESLint 分工，别互相打架 |
| **`vue-tsc`**           | 对 `.vue` 做类型检查（`vue-tsc --noEmit`，CI 必跑）        |
| **Husky + lint-staged** | 提交前只对**暂存文件**跑 lint/format，快                   |
| **commitlint**          | 约束 commit message 规范（`feat:` / `fix:`）               |

**追问点**：`ESLint` 与 `Prettier` 冲突怎么办？→ 用 `eslint-config-prettier` 关掉 ESLint 里所有与格式相关的规则，让 Prettier 独占格式化，ESLint 只管质量。**CI 里必须加 `vue-tsc --noEmit` 与 `eslint` 卡点**，否则规范形同虚设。

### 7.7 环境变量与多环境部署 ★★

**大白话**：Vite 里只有 `VITE_` 开头的变量才给前端用，而且**它会原样打进产物** —— 所以密钥、token 放前端环境变量等于公开。部署最常踩的坑是 history 路由刷新 404，根因是服务端找不到 `/user/1` 这个物理文件，要靠 Nginx `try_files` 把它交给 `index.html`。

- **Vite 约定**：只有 `VITE_` 前缀的变量才暴露给客户端（`import.meta.env.VITE_API_BASE`）。
- **多环境**：`.env.development` / `.env.production`，`vite build --mode staging` 自定义模式。
- **安全红线**：环境变量会**被打进产物**，任何密钥/Token 都**不能**放前端环境变量（等于公开）。
- **部署产物**：`base` 配置子路径、`build.assetsDir`、Nginx 配 `try_files ... /index.html`（history 路由刷新不 404）。

**追问点**：history 路由刷新 404 的根因？→ 服务端只认物理文件，`/user/1` 无对应文件 → 交给 `index.html` 由前端路由接管（Nginx 用 `try_files`）。

## 八、性能优化

### 8.1 核心性能指标 ★★★

**大白话**：三个核心指标其实就是「用户最不爽的三件事」：LCP = 主要内容多久出来（慢），INP = 点了多久有反应（卡），CLS = 页面元素乱跳（晃）。优化方向也就三条：加载的东西砍小、长任务拆碎、给图片和字体留好固定尺寸。

**三大核心指标（记指标 + 含义 + 目标值）**：

| 指标                      | 衡量什么                                      | 好 / 需改进       |
| ------------------------- | --------------------------------------------- | ----------------- |
| **LCP**（最大内容绘制）   | **加载性能**：视口内最大元素何时渲染完        | < 2.5s / > 4s     |
| **INP**（交互到下次绘制） | **响应性**：所有交互的延迟（2024 起替代 FID） | < 200ms / > 500ms |
| **CLS**（累计布局偏移）   | **视觉稳定性**：页面元素意外位移量            | < 0.1 / > 0.25    |

**辅助指标**：FCP（首次内容绘制）、TTFB（首字节时间）、TBT（总阻塞时间）。

**三者对应的优化方向**：LCP 差 → 优化首屏资源与服务器响应；INP 差 → 减少长任务、拆包、用 `requestIdleCallback`；CLS 差 → 给图片/广告设固定尺寸、字体加载别引起回流。

**测量工具**：Lighthouse（本地跑分）、Chrome Performance 面板（定位长任务）、`PerformanceObserver`（代码里采集）、Web Vitals 库、RUM 平台（真实用户数据）。

**追问点**：为什么 INP 取代了 FID？→ FID 只测「**第一次**交互的**输入延迟**」，漏掉了处理时间和渲染时间；INP 覆盖**整页所有交互**的端到端延迟，更贴近真实体验。

---

### 8.2 首屏优化手段 ★★

**大白话**：首屏优化按这个顺序想：能少加载就少加载（懒加载）→ 该提前的提前（preload / preconnect）→ 能缓存就缓存（CDN + 强缓存）→ 先让用户看到骨架（骨架屏 / SSR）→ 别让东西挡住渲染（`defer`、`lazy`、`swap`）。注意 `preload` 与 `prefetch` 别用反，会抢首屏带宽。

| 方向         | 手段                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------- |
| **少加载**   | 路由/组件懒加载（`() => import()`）、按需引入组件库、tree-shaking                               |
| **提前加载** | `<link rel="preload">`（关键资源）、`prefetch`（下一跳）、`preconnect/dns-prefetch`（提前握手） |
| **不加载**   | HTTP 缓存 + CDN + gzip/brotli；`immutable` 静态资源                                             |
| **先看到**   | SSR/SSG（Nuxt）、骨架屏、关键 CSS 内联、非关键 CSS 异步                                         |
| **别阻塞**   | 图片 `loading="lazy"`、字体 `font-display: swap`、脚本 `defer`                                  |
| **传输更小** | 图片 webp/avif + 合适尺寸、按需 polyfill                                                        |

**抓手顺序（实战）**：① 先用 Lighthouse 定位瓶颈；② 大包 → 分割/外链；③ 图片 → 压缩/webp；④ 服务器慢 → CDN/SSR；⑤ 交互卡 → 拆长任务。

**追问点**：`preload` 与 `prefetch` 的区别？→ `preload` 是**当前页面**急需的资源（高优先级、马上用）；`prefetch` 是**下一个页面**可能用到的资源（低优先级、空闲时下载）。用错会抢带宽、反而拖慢首屏。

---

### 8.3 虚拟列表 ★★★

**结论**：只渲染**视口内**的元素。核心是「**假滚动**」—— 用一个高容器撑出真实滚动条高度，里面只挂可视区那几条，靠 `transform: translateY` 或 padding 把可视区顶到正确位置。

**大白话**：虚拟列表就是「假滚动」—— 外面用一个很高的空盒子把滚动条撑到真实长度，里面只挂用户看得见的那十几行，滚动时靠 `translateY` 把这几行挪到正确位置。所以十万条数据，DOM 里也只有十几行。

```js
const start = Math.floor(scrollTop / itemHeight);
const end = start + Math.ceil(viewportHeight / itemHeight);
const visible = list.slice(start, end);

// 容器总高 = 数据量 × 行高（撑出滚动条）
// 可视区偏移 = start × 行高（绝对定位 / 或者撑高的占位 div）
```

**三个必备细节**：

- **缓冲/预渲染**：渲染 `[start - buffer, end + buffer]`，滚动时不至于白屏。
- **滚动节流**：用 `requestAnimationFrame` 更新，而不是每次 `scroll` 都 setState。
- **`key` 必须唯一**：避免复用错位（同 5.9）。

**追问点**：

- 不定高列表怎么处理？→ **预估高度 + 动态测量 + 缓存偏移量**（`vue-virtual-scroller` / `vueuc` 的做法）：先按预估值铺位，`ResizeObserver` 量到真实高度后**修正总高与偏移表**。
- 为什么不用 `scrollTop` 直接算还行不行？→ 行高不等时 `start` 会算错，必须靠**前缀和/位置表**二分查找。

### 8.4 内存泄漏排查实战 ★★

**结论**：排查靠 Chrome DevTools 的 **Memory 面板**，先确认「是否真泄漏」，再定位「谁持有」。

**大白话**：排查内存泄漏的方法论就两步：先拍两张内存快照（操作前 / 反复操作后）对比，看哪种对象只涨不落，确认「真漏了」；再顺着它的「引用链」往上找，看是谁一直抓着它不放。前端常见元凶：定时器没清、事件没解绑、ECharts 这类实例没 `dispose`。

**步骤**：

1. 打开 Memory → **Heap snapshot** 拍一张（基线）。
2. 反复执行可疑操作 N 次（如反复打开/关闭弹窗、切换路由）。
3. 再拍一张；用 **Comparison** 视图对比，看哪种对象**持续净增长**且不被回收。
4. 选中可疑对象 → 看 **Retainers（保留链）**，找到「谁引用了它」→ 定位泄漏点。

**前端常见泄漏源**：

- `setInterval` / `setTimeout` 未清（尤其组件卸载后仍在跑）。
- 全局事件 / `window.resize` / `scroll` 未 `removeEventListener`。
- Vue：`watch` / `watchEffect` 未随组件销毁（组合式 API 内创建的会自动停，但**手动 `addEventListener`、第三方实例不会**）。
- 游离 DOM：已从文档树移除，但 JS 仍持有引用 → 无法回收。
- 闭包 + 大对象长期驻留；`Map`/`Set` 当缓存却永不清理（应上 LRU）。

**追问点**：Vue3 里什么情况下需要手动清理？→ 组件卸载时的 `onBeforeUnmount` 里清：定时器、`AbortController`、`ResizeObserver`/`IntersectionObserver`、ECharts 等第三方实例的 `dispose()`。

### 8.5 长列表渲染方案对比 ★★★

**大白话**：选型口诀：能分页就分页（最省事）；必须一直滚、又要上万条，才上虚拟滚动；行的内容几乎不变，顺手加个 `v-memo` 少做点对比。虚拟滚动的老大难是「行高不定」，只能先估一个高度、量到真高再修正，否则滚动条会跳。

| 方案                           | 原理                 | 适用               | 代价                   |
| ------------------------------ | -------------------- | ------------------ | ---------------------- |
| 直接渲染                       | 全量 DOM             | 几百条以内         | 数据一多就卡           |
| **分页**                       | 一次一屏             | 后台表格、可翻页   | 用户不能全局滚动       |
| **虚拟滚动**                   | 只渲染视口 ± 缓冲    | **上万条、不定高** | 实现复杂、测量成本     |
| **`content-visibility: auto`** | 浏览器跳过屏幕外渲染 | 静态长内容         | 兼容性与滚动条跳动     |
| **`v-memo` / 冻结**            | 缓存静态行 vnode     | 行内容很少变       | 只减 diff，不减 DOM 数 |

**选型口诀**：能分页就分页；必须滚动又要万级 → 虚拟滚动；行内容几乎不变 → 顺手加 `v-memo`。

**追问点**：虚拟滚动里「滚动白屏 / 抖动」怎么解决？→ 滚动时用**预估高度占位**，真实高度测量后用「偏移量修正表」补偿，避免滚动条跳动；配合 `requestAnimationFrame` 节流计算。

## 九、手写题 / 算法

### 9.1 手写 call / apply / bind ★★★

**大白话**：三者就三个区别：`call` 是参数一个个传，`apply` 是参数打包成数组，`bind` 不立刻执行、返回一个新函数（还能先预设几个参数）。手写 `call` 的窍门是「把函数临时挂到目标对象上再调用」—— 这样 `this` 自然就指向它了，用完记得删掉，别污染对象。

**三者区别先答清**：`call(thisArg, a, b)` 参数逐个传；`apply(thisArg, [a, b])` 参数用数组；`bind(thisArg, a)` **返回新函数**且不立即执行（可预设参数，即"偏函数"）。

```js
Function.prototype.myCall = function (ctx, ...args) {
  ctx = ctx == null ? globalThis : Object(ctx); // 处理 null/undefined/基本类型
  const key = Symbol("fn"); // Symbol 防止覆盖已有属性
  ctx[key] = this; // 挂到 ctx 上 → 调用时 this 指向 ctx
  const res = ctx[key](...args);
  delete ctx[key]; // 用完即删，别污染 ctx
  return res;
};

Function.prototype.myApply = function (ctx, args = []) {
  return this.myCall(ctx, ...args);
};

Function.prototype.myBind = function (ctx, ...args) {
  const fn = this;
  return function bound(...rest) {
    // 支持 new 调用：new 时 this 是 bound 的实例 → 用 this，忽略 ctx
    return fn.apply(this instanceof bound ? this : ctx, [...args, ...rest]);
  };
};
```

**三个关键点**：

- **为什么用 `Symbol` 当 key**：字符串 key 可能覆盖 `ctx` 上的同名属性；`Symbol` 唯一且不可枚举。
- **`Object(ctx)` 的意义**：基本类型（`myCall(1)`）要包成对象才能挂属性；`null/undefined` 退回全局对象（非严格模式语义）。
- **`bind` 里为什么判 `this instanceof bound`**：区分「普通调用」与「`new` 调用」—— `new` 时 `this` 必须指向新实例。

**追问点**：`bind` 出来的函数被 `new` 时，原型怎么办？→ 严格实现要把 `bound.prototype` 设为 `Object.create(fn.prototype)`，否则 `实例 instanceof fn` 会断开。

### 9.2 手写 new ★★

**大白话**：`new` 就干了四件事：造个空对象 → 把它的原型指向构造函数的 `prototype` → 拿它当 `this` 跑一遍构造函数 → 看构造函数返回了什么（返回对象就用它的，返回基本类型就忽略）。手写 `new` 就是照这四步抄一遍。

**`new` 干了四件事**：① 创建一个空对象；② 把它的原型指向构造函数的 `prototype`；③ 以它为 `this` 执行构造函数；④ 若构造函数返回**引用类型**则用它，否则返回该对象。

```js
function myNew(Ctor, ...args) {
  if (typeof Ctor !== "function") throw new TypeError("not a constructor");
  const obj = Object.create(Ctor.prototype); // 步骤 ①②：建对象 + 连原型
  const res = Ctor.apply(obj, args); // 步骤 ③：绑 this 执行
  // 步骤 ④：返回引用类型才生效，返回基本类型忽略
  return res && (typeof res === "object" || typeof res === "function")
    ? res
    : obj;
}
```

**追问点**：构造函数里 `return 1` 与 `return {}` 有什么区别？→ 返回**原始值**被忽略（仍返回新实例）；返回**对象**则覆盖实例。这也是有些库用 `return this` 做兼容的原因。

### 9.3 手写 instanceof ★★

**大白话**：`instanceof` 就是「顺着原型链一层层往上找，看能不能碰到右边的 `prototype`」。所以原始值（`1`、`'a'`）永远是 `false` —— 它们根本不在原型链上。它还有个硬伤：跨 iframe 时构造函数是两份不同的引用，会判断失败。

**原理**：沿 `left` 的原型链向上找，看能否命中 `right.prototype`。

```js
function myInstanceof(left, right) {
  if (left == null || typeof left !== "object") return false; // 原始类型直接 false
  let proto = Object.getPrototypeOf(left);
  const target = right.prototype;
  while (proto) {
    if (proto === target) return true;
    proto = Object.getPrototypeOf(proto); // 沿原型链上溯
  }
  return false;
}
```

**追问点**：

- 为什么原始类型返回 false？→ `1 instanceof Number` 也是 false，原始值不在原型链上（`Object(1)` 才是对象）。
- `instanceof` 有什么局限？→ ① **跨 iframe/不同全局环境**失效（构造函数引用不同）；② 原型链可被 `Object.setPrototypeOf` 篡改，不可靠。判断数组用 `Array.isArray`，判断具体类型用 `Object.prototype.toString.call`。

### 9.4 LRU 缓存 ★★★

**结论**：LRU（最近最少使用）用 **`Map` 保持插入顺序** —— `get` 命中后「删掉再重插」移到最新端，`put` 超容量时删掉队首（最旧）。

**大白话**：LRU 就是「最久没用过的先淘汰」（手机清理后台就是这个策略）。用 `Map` 实现特别短：`Map` 天然按插入顺序排列，所以「用过一次」就把它删掉重新插到队尾，容量满了就删队首那一项。

```js
class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.map = new Map(); // Map 天然保持插入顺序
  }
  get(key) {
    if (!this.map.has(key)) return -1;
    const val = this.map.get(key);
    this.map.delete(key);
    this.map.set(key, val); // 删除后重插 → 移到队尾（最新）
    return val;
  }
  put(key, val) {
    if (this.map.has(key)) this.map.delete(key); // 已存在先删，避免 size 虚高
    this.map.set(key, val);
    if (this.map.size > this.capacity) {
      this.map.delete(this.map.keys().next().value); // 淘汰队首（最旧）
    }
  }
}
```

**复杂度**：`get` / `put` 均 **O(1)**（`Map` 的增删查 O(1)，且迭代有序）。

**追问点**：不用 `Map` 怎么实现？→ **哈希表 + 双向链表**：哈希存 `key → 节点`，链表维护使用顺序（头最新、尾最旧），增删都是 O(1)。为什么必须**双向**？→ 删除节点要拿到它的 `prev`，单向链表做不到 O(1)。

### 9.5 高频算法题清单 ★★

**大白话**：这一页是「高频算法清单」，不用死磕，记住每题的套路就行：去重 / 扁平化用 `Set` 或递归，两数之和用哈希表换时间，最长子串用滑动窗口，乱序一定用 Fisher-Yates（`sort(() => Math.random() - 0.5)` 是不等概率的错解）。

| 题目                                 | 核心思路                                    | 复杂度          |
| ------------------------------------ | ------------------------------------------- | --------------- |
| 数组去重 / 扁平化                    | `Set` / 递归 / 栈（防爆栈）                 | O(n)            |
| 两数之和                             | 哈希表存「差值 → 下标」                     | O(n) / O(n)     |
| 无重复字符最长子串                   | **滑动窗口** + 哈希记位置                   | O(n)            |
| 快速排序 / 归并排序                  | 分治（快排原地、归并稳定）                  | 均摊 O(n log n) |
| 二叉树遍历                           | 前中后序（递归/栈）、层序（队列）           | O(n)            |
| 数组乱序                             | **Fisher-Yates**（`sort(random)` 不等概率） | O(n)            |
| 柯里化 / `compose` / `pipe`          | 闭包收集参数 / 函数组合                     | —               |
| 版本号比较、大数相加、字符串反转单词 | 双指针 / 字符串进位                         | O(n)            |

**追问点**：快排最坏什么时候 O(n²)？→ 每次选到最大/最小元素当 pivot（如已排序数组取首元素）；改进用**随机 pivot** 或三数取中。归并排序**稳定**但需 O(n) 额外空间。

### 9.6 高频手写补充 ★★

**大白话**：这四个手写题的共同点是「用闭包存中间状态」：扁平化是一路递归收集；柯里化是「参数够了才执行、不够继续收集」；洗牌是倒着遍历随机换位；`compose/pipe` 是把一串函数串起来依次执行。

**① 数组扁平化（控制深度）**

```js
function flatten(arr, depth = Infinity) {
  return arr.reduce((acc, cur) => {
    if (Array.isArray(cur) && depth > 0) {
      acc.push(...flatten(cur, depth - 1));
    } else {
      acc.push(cur);
    }
    return acc;
  }, []);
}
// 原生：arr.flat(Infinity)；栈实现可避免递归深度限制
```

**② 柯里化**

```js
function curry(fn) {
  return function curried(...args) {
    // 参数够了就执行，不够就继续收集
    return args.length >= fn.length
      ? fn.apply(this, args)
      : (...rest) => curried.apply(this, [...args, ...rest]);
  };
}
const add = curry((a, b, c) => a + b + c);
add(1)(2)(3); // 6
add(1, 2)(3); // 6
```

**③ Fisher-Yates 洗牌（保证等概率）**

```js
function shuffle(arr) {
  for (let i = arr.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [arr[i], arr[j]] = [arr[j], arr[i]];
  }
  return arr;
}
// ⚠️ arr.sort(() => Math.random() - 0.5) 不是等概率，别用
```

**④ `compose` / `pipe`（函数组合）**

```js
const pipe =
  (...fns) =>
  (x) =>
    fns.reduce((acc, fn) => fn(acc), x);
const compose =
  (...fns) =>
  (x) =>
    fns.reduceRight((acc, fn) => fn(acc), x);
```

**追问点**：柯里化有什么用？→ 参数复用、延迟执行、配合 `compose` 做函数组合（`map(prop('name'))` 这类），也是函数式编程的基础工具。

## 十、场景设计题

### 10.1 大文件上传 / 断点续传 ★★★

**大白话**：核心就一句「切成小块，一块块传」。额外那几件事都是为体验服务的：算 hash 是为了秒传（服务端已经有这个文件就直接给地址）；查已传过的分片是为了断点续传；限并发是为了别把带宽打满。hash 计算很吃 CPU，必须放 Web Worker，否则页面直接卡死。

**要点**：

1. **分片**：`File.slice(start, end)` 按固定大小（如 2MB）切块，逐个上传。
2. **算 hash**：用 `spark-md5` 增量计算整文件指纹；放在 **Web Worker** 里算，避免卡 UI。
3. **秒传**：上传前先问服务端该 hash 是否已存在 → 存在则直接返回文件地址。
4. **断点续传**：上传前查「已上传分片列表」，只传缺失的；`localStorage` 记上传进度。
5. **并发控制**：同时传 3~5 个分片（用 1.7 的 `limitPool`），别一次全发把带宽打死。
6. **合并**：分片全部传完后请服务端合并，并校验最终文件 hash。

```js
// 分片 + 并发上传的骨架
const chunks = Array.from(
  { length: Math.ceil(file.size / CHUNK) },
  (_, i) => () => uploadChunk(file.slice(i * CHUNK, (i + 1) * CHUNK), i),
);
await limitPool(chunks, 3);
await mergeRequest({ hash, total: chunks.length });
```

**追问点**：

- 进度条怎么算？→ `已成功分片数 / 总分片数`；按**数据量加权**更准（最后一片通常不满）。
- 分片失败了怎么办？→ 记录失败分片下标，只重试失败的那些 + **指数退避**；接口层面用「分片级幂等」（同 hash + index 重复上传直接覆盖）。
- 为什么要在 Worker 里算 hash？→ 大文件 MD5 是 CPU 密集操作，主线程算会卡死页面、进度条不动。

---

### 10.2 前端埋点 / 监控 ★★★

**大白话**：埋点分两类：用户行为（曝光、点击、停留时长）和异常（报错、性能）。两个重点：上报用 `sendBeacon`（页面关闭时也能发出去，`fetch` 会被掐断）；线上错误要靠 SourceMap 还原成源码位置，否则拿到一堆压缩后的行列号根本没法看。

**埋点类型与实现**：

| 类型            | 实现                                       |
| --------------- | ------------------------------------------ |
| **曝光**        | `IntersectionObserver` 判断元素进入视口    |
| **点击 / 行为** | 事件委托统一收集，或自定义指令 `v-track`   |
| **页面停留**    | `visibilitychange` + `beforeunload` 计时   |
| **性能**        | `PerformanceObserver` 采集 LCP / INP / CLS |

**上报方式**：

- `navigator.sendBeacon(url, data)`：**页面卸载时也能可靠发出**且不阻塞卸载（首选）。
- 图片 `1x1` GET（跨域不触发预检，老方案）。
- **批量 + 采样**（高流量按比例上报），并给 `sendBeacon` 做失败兜底。

**错误监控**：

- `window.onerror`（同步错误）、`addEventListener('error')`（资源加载失败）、`unhandledrejection`（Promise 未捕获）、Vue 的 `app.config.errorHandler` / `onErrorCaptured`。
- **SourceMap 还原**：上报压缩后的行列号 + 构建版本号，服务端用对应 SourceMap 反解出源码位置。

**追问点**：为什么用 `sendBeacon` 而不是 `fetch`？→ 页面正在卸载时 `fetch`/XHR 会被中断，`sendBeacon` 由浏览器**排队保证发出**且不阻塞；代价是不能自定义头、也读不到响应。

### 10.3 移动端弹窗 / 滚动穿透 ★★

**大白话**：滚动穿透就是「在弹窗上滑，底下的页面跟着滑」。最常见的解法是打开弹窗时给 body 加 `position: fixed` 锁住 —— 但一定记得把当前 `scrollTop` 存下来、关闭时还回去，否则页面会跳回顶部。

**滚动穿透**：弹窗打开后，在弹窗上滑动，底下页面也跟着滚。三种修法：

```js
// ① 锁 body（最常用，必须记录并恢复 scrollTop，否则关闭时页面会跳到顶部）
const top = window.scrollY;
document.body.style.cssText = `position:fixed; top:${-top}px; width:100%`;
// 关闭时：document.body.style.cssText = ''; window.scrollTo(0, top);

// ② 阻止 touchmove 冒泡（仅适用于弹窗自身可滚动时）
modal.addEventListener("touchmove", (e) => e.stopPropagation(), {
  passive: false,
});
```

```css
/* ③ 现代方案：overscroll-behavior 打断滚动链 */
.modal-mask {
  overscroll-behavior: contain;
}
```

**其他移动端弹窗坑**：

- **键盘顶起 / 遮挡输入框**：监听 `visualViewport.resize` 调整位置 —— iOS 上 `window.innerHeight` **不随键盘变化**，不能靠它判断。
- **层级被遮**：配合 `Teleport` 把弹层挂到 `body`，避开父级 `transform` 造成的层叠上下文（见 3.5）。
- **iOS 橡皮筋回弹**：慎用 `-webkit-overflow-scrolling: touch`，它可能引发新的穿透问题。

**追问点**：为什么「锁 body」必须记 `scrollTop`？→ `position: fixed` 会让 body 滚回顶部，不还原的话关闭弹窗后页面会跳到最高处。

### 10.4 主题换肤 / 暗黑模式 ★★

**大白话**：换肤的本质就是「把颜色全抽成 CSS 变量，只改变量的值」。唯一需要额外处理的是「首屏闪白」：得在 HTML 里内联一段同步脚本，在 CSS 生效前就把 `data-theme` 设好，不然暗色用户会先看到一瞬白。

**核心思路**：把所有颜色收敛到 **CSS 变量**，只切换变量值，组件代码一行不改。

```css
:root {
  --color-bg: #fff;
  --color-text: #222;
}
html[data-theme="dark"] {
  --color-bg: #111;
  --color-text: #eee;
}
.card {
  background: var(--color-bg);
  color: var(--color-text);
}
```

```js
// 切换 + 持久化 + 跟随系统
function setTheme(t) {
  document.documentElement.dataset.theme = t;
  localStorage.setItem("theme", t);
}
const prefersDark = matchMedia("(prefers-color-scheme: dark)");
setTheme(
  localStorage.getItem("theme") ?? (prefersDark.matches ? "dark" : "light"),
);
```

**三个要点**：

- **首屏闪白（FOUC）**：主题判断要在 HTML 里**内联一段同步脚本**，在 CSS 生效前就设好 `data-theme`，否则暗色用户会先闪一瞬白。
- **跟随系统**：监听 `matchMedia` 的 `change`；用户手动选过就存 `localStorage`，优先级更高。
- **组件库适配**：Element Plus 支持 CSS 变量覆盖（`--el-color-primary` 等）+ `html.dark` 类。

**追问点**：怎么避免主题闪白？→ 在 `<head>` 里内联同步脚本（早于 CSS 与 Vue 挂载）读取偏好并设置 `data-theme`。

### 10.5 微前端 ★★★

**结论**：把多个**可独立开发/部署**的应用组合成一个整体（典型：老后台里嵌新模块，或按团队拆应用）。

**大白话**：微前端就是「几个能独立开发、独立上线的小应用拼成一个大站点」。好处是解耦和独立部署，代价是路由、通信、样式隔离、JS 沙箱这些都得额外处理。所以单团队、单技术栈、没有独立发布需求时别上 —— 纯亏。

| 方案                  | 原理                                                                              | 隔离强度     | 体验                     |
| --------------------- | --------------------------------------------------------------------------------- | ------------ | ------------------------ |
| **qiankun**           | 基于 `single-spa`，`import-html-entry` 取子应用 HTML 执行，**JS 沙箱 + 样式隔离** | 中           | 好                       |
| **Module Federation** | Webpack 5 运行时远程共享模块（等价"运行时 npm"）                                  | 弱（靠约定） | 好                       |
| **iframe**            | 天然隔离                                                                          | **最强**     | 差（弹窗/路由/通信受阻） |

**必须处理好的四件事**：

1. **路由**：主应用管路由，子应用设 `base` 前缀（history 模式需配）。
2. **通信**：`props` 下发 + 全局事件总线 + 共享 store。
3. **样式隔离**：`scoped` / Shadow DOM / 给子应用样式加前缀沙箱。
4. **JS 沙箱**：快照或 `Proxy` 沙箱隔离 `window` 上的全局变量。

**追问点**：什么时候**不该**上微前端？→ 单团队、单技术栈、模块之间无独立发布需求时 —— 微前端带来的**构建/通信/调试成本远大于收益**，改用 monorepo 或单应用拆包更划算。

### 10.6 前端登录态与会话保持 ★★★

**结论**：核心是「**短期 access token + 长期 refresh token**」，前端负责无感续期与并发去重。

**大白话**：登录态的核心是「短期票 + 长期票」：`accessToken` 短命，过期了就用 `refreshToken` 悄悄换一张，用户没感知。最容易考的是并发去重 —— 页面同时发 5 个请求都返回 401，不能刷新 5 次，要拿一个「正在刷新的 Promise」占位，其他请求都等它。

**要点**：

1. **存储**：`accessToken` 存内存（最安全）或 `sessionStorage`；`refreshToken` 存 `HttpOnly` Cookie（JS 拿不到，防 XSS）。
2. **无感刷新**：请求头带 `accessToken`；接口返回 401 → 用 `refreshToken` 换新 token → **重放原请求**。
3. **并发去重（关键）**：页面同时发 5 个请求都 401，不能刷新 5 次 —— 用一个「刷新中的 Promise」占位，其他请求 `await` 同一个 Promise。
4. **刷新失败**：清 token → 跳登录 → 记录 `redirect` 参数，登录后回跳。
5. **多标签页同步**：`localStorage` 的 `storage` 事件或 `BroadcastChannel` 同步登出。

```ts
let refreshing: Promise<string> | null = null;

async function ensureToken() {
  if (refreshing) return refreshing; // 已有刷新在跑 → 复用
  refreshing = doRefresh().finally(() => (refreshing = null));
  return refreshing;
}

// 响应拦截里
service.interceptors.response.use(undefined, async (err) => {
  const cfg = err.config;
  if (err.response?.status === 401 && !cfg._retried) {
    cfg._retried = true;
    const token = await ensureToken();
    cfg.headers.Authorization = `Bearer ${token}`;
    return service(cfg); // 重放原请求
  }
  return Promise.reject(err);
});
```

**追问点**：为什么不用 `localStorage` 存 accessToken？→ XSS 可读；内存存储 + refresh Cookie 是更安全的组合。代价是刷新页面 accessToken 丢失，需用 refresh 静默换回。

### 10.7 拖拽排序实现原理 ★★

**大白话**：拖拽就三件事：按下时记住拖的是谁；移动时用坐标判断「该插到哪个兄弟的前面还是后面」（用占位元素让位）；松手时落到占位处。生产上别自己写，直接用 Sortable.js / `vuedraggable` —— 自己写容易栽在移动端和空容器上。

**两条路线**：

- **原生 HTML5 Drag & Drop**：`draggable="true"` + `dragstart/dragover/drop`；缺点是移动端支持差、`drag` 事件样式限制多、`dataTransfer` 兼容坑。
- **Pointer Events 自实现 / 用库**：`pointerdown → pointermove → pointerup` 自己算位置；生产直接用 **Sortable.js / vuedraggable**（底层就是 Pointer/Mouse 事件 + 占位元素 + 碰撞检测）。

**核心算法（flip 思路）**：

1. 拖起时记录被拖元素与「落点容器」。
2. `pointermove` 中，用坐标判断**光标落在哪个兄弟元素的前/后半区**，把**占位符**插到对应位置（视觉上就是「让位」）。
3. 松手时把被拖元素插入占位符位置，重新计算索引。
4. **用 `transform` 做位移动画**（不触发回流），收尾 `FLIP`（First-Last-Invert-Play）动画。

**追问点**（结合制卷台的真实坑）：

- **克隆拖拽**时，`clone` 必须取自**拖拽源**那一侧的配置（vuedraggable 里 `_underlying_vm_` 用的是源列表的 `clone` 函数），两侧数据类型不同就要两侧都挂同一个 `clone` 包装。
- **空容器拖不进**：容器高度塌成 0 → 命中不到落点，要给空态 `min-height`。
- 拖拽数据落库前要 `normalize`，防止裸元素（缺字段）混进列表导致渲染报错。

## 十一、项目与软技能

### 11.1 项目介绍：STAR 法则 ★

**大白话**：STAR 就是讲项目的模板：什么背景、我负责啥、我具体做了哪些事、最后拿到什么可量化的结果。最常犯的错是全程说「我们」，面试官听不出你干了什么 —— 多用「我」，重点讲你做的判断和取舍。

- **S**ituation：背景与规模（团队、用户量、业务复杂度）。
- **T**ask：你负责什么、目标是什么。
- **A**ction：你**具体怎么做**的（技术选型、难点攻克、协作）。
- **R**esult：量化结果（性能提升 X%、开发效率提升、缺陷率下降）。

**示例（30 秒版）**：

> S：这是个内部管理后台，20+ 页面，日活 300。T：我负责前端架构与性能优化。
> A：发现首屏 4.5s，用 Lighthouse 定位到大包与图片；做了路由级代码分割 + 依赖外链 CDN + 图片 webp。
> R：首屏降到 1.8s，LCP 从 3.9s → 2.1s。

**常见坑**：

- 只说「我做了 XX 功能」而**没有你的判断**（选型、取舍）。
- 结果**不可量化**（"提升明显"），不如给数字。
- 全程说「我们」，面试官听不出你的贡献。

> 面试官只想听「**你**做了什么」，不是团队做了什么 —— 多用「我」，并说清**你在哪一环做了决定**。

### 11.2 高频行为问题 ★

**大白话**：行为面就两个原则：给结论也给取舍（面试官想看你怎么想的，不是标准答案）；不会就说不会（硬编会被一路追问到穿帮）。

| 问题                      | 回答思路（骨架）                                                                        |
| ------------------------- | --------------------------------------------------------------------------------------- |
| 你解决过最难的 bug？      | 现象 → **定位手段**（断点 / 二分 / 日志 / 复现）→ 根因 → 修复 → **预防**（加测试/监控） |
| 技术选型怎么做的？        | 列候选 → 按维度（生态 / 性能 / 团队熟悉度 / 维护成本）打分 → 决策 → 说清**放弃了什么**  |
| 和产品 / 后端意见不一致？ | 摆数据与事实 → 找共同目标 → 给方案 A/B 让对方选，别争对错                               |
| 你怎么保证代码质量？      | 规范（ESLint / TS strict）、CR、单测、CI 卡点、灰度                                     |
| 最近在学什么？            | 结合岗位说**真实的、能讲深**的点，并说清「为什么学」                                    |

**两条通用原则**：

- **给结论 + 给取舍**：面试官在意的是你的**判断过程**，不是标准答案。
- **别装**：不会就说「没深用过，但我理解它的思路是…」，硬编会被一路追问穿帮。

**追问点**：被问「如果重来你会怎么做」怎么答？→ 说一个**真实存在的改进点** + 具体做法（哪怕当时方案已经不错），体现你有复盘习惯。

### 11.3 反问面试官 ★

**大白话**：反问不是走过场，是「用问题判断这家公司值不值得去」：团队做什么、这个岗位最看重什么能力、代码质量靠什么保障。挑 2～3 个问，最好接着面试里聊过的话题问，显得你在认真听。

**按目的分三类**（挑 2~3 个问，别连珠炮）：

| 目的             | 可问的问题                                                                       |

### 11.4 自我介绍与「讲项目」模板 ★

**大白话**：自我介绍按「我是谁 → 我做过什么（挑跟岗位最匹配的那个项目）→ 我为什么来」三段说，一分钟足够，别背简历。讲技术难点时用六步：背景 → 难点 → 方案 A/B → 我为什么选这个（代价是什么）→ 结果 → 复盘。

**自我介绍（1 分钟，三段式）**：

1. **我是谁**：几年经验、主力技术栈（一句话，别背简历）。
2. **我做过什么**：挑 1 个最匹配岗位的项目，讲**你的角色 + 技术亮点**（不是罗列功能）。
3. **我为什么来**：一句真实动机（业务方向 / 技术栈匹配），自然收尾。

**讲项目难点的「六步法」**（比 STAR 更适合技术深挖）：

```
背景（一句话）→ 难点（为什么难）→ 方案候选（有 A/B）
→ 我的选择（为什么选它，代价是什么）→ 结果（量化）→ 复盘（还能怎么更好）
```

**面试官最想听的三个东西**：① 你**独立做的判断**（选型/取舍）；② 你**踩过并解决的坑**；③ 你能**量化结果**。

**追问点**：被问「这个方案有什么缺点」怎么答？→ 主动承认边界（如「虚拟滚动对不定高有抖动，我们靠预估高度缓解，极端情况仍不如固定高度」）。**知道自己方案的边界**，比硬吹更能加分。

## 十二、AI 相关面试题

> 答题心法：**不背概念，讲你真实用过、踩过的坑**。句式 = 「我们项目里这么做 → 遇到什么问题 → 怎么解」。

### 12.1 AI 工具使用经验 ★（几乎必问）

**结论**：面试官只想知道两件事 —— 你**真在用**，以及你有**判断力**。

**大白话**：这题的关键不是报工具名，而是讲一个「场景 → 做法 → 收益 → 坑」的完整故事。最能加分的是「我踩过什么坑、怎么修的」（AI 编不存在的 API、偷偷改了无关代码）；最能减分的是「AI 写的我直接用了」。

**该说的**：

- 具体场景：写业务组件、补单测、重构、**读陌生代码**、定位报错、写正则/配置。
- 提效的量化：某模块开发时间、CR 返工率、单测覆盖率的变化。
- **踩过的坑**（最能加分）：幻觉不存在的 API/属性、悄悄改了无关逻辑、测试只覆盖 happy path、对项目约定无感（命名、目录、状态管理方式）。

**不该说的**：

- 只报工具名（「我用 Cursor」）就结束 —— 等于没答。
- 说「AI 写的我不看直接用」—— 直接减分。

**怎么「讲」才算答好**：别只列工具名，按「**场景 → 做法 → 收益 → 坑**」讲一个具体例子，比如「用 AI 把 20 个页面的表单校验从手写抽成配置，返工率从 X 降到 Y」。

**追问点**：

- AI 生成的代码你怎么审？→ 先看**边界与异常**，再看是否遵守项目约定，最后跑测试；**安全相关（鉴权、XSS 入口、正则、依赖版本）必手审**。
- 怎么防止 AI「悄悄改坏无关代码」？→ 小步提交、改动范围先 review diff、关键路径加测试兜底。
- 团队不让用外部 AI 怎么办？→ 讲你怎么在内网/私有化模型下工作（脱敏、只贴必要上下文、不传业务数据）。

### 12.2 流式输出：SSE / ReadableStream ★★★

**结论**：AI 对话的核心是**真流式**。用 `fetch` + `ReadableStream` 逐块读取，`TextDecoder` 解码，边收边渲染。

**大白话**：流式输出就是「不等服务端算完，来一块渲染一块」。读法是 `fetch` 拿到 `ReadableStream`，循环 `reader.read()` 一段段取。两个必踩的坑：中文会变乱码（一个汉字被切成两半，要 `decode(value, { stream: true })`）；偶尔 JSON 解析失败（网络分块与换行不对齐，收到半行，要用 `buffer` 缓存残行）。

```ts
async function streamChat(
  prompt: string,
  onChunk: (text: string) => void,
  signal: AbortSignal,
) {
  const res = await fetch("/api/chat", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ prompt, stream: true }),
    signal,
  });
  if (!res.body) throw new Error("no stream");

  const reader = res.body.getReader();
  const decoder = new TextDecoder("utf-8");
  let buffer = "";

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    // ⚠️ stream:true —— 处理「一个多字节字符被切成两块」的情况
    buffer += decoder.decode(value, { stream: true });

    const lines = buffer.split("\n");
    buffer = lines.pop() ?? ""; // 最后一行可能不完整，留到下一轮再拼

    for (const line of lines) {
      if (!line.startsWith("data:")) continue; // SSE 还可能有 event:/id: 行
      const data = line.slice(5).trim();
      if (data === "[DONE]") return; // OpenAI 风格的结束标记
      try {
        onChunk(JSON.parse(data)?.choices?.[0]?.delta?.content ?? "");
      } catch {
        /* 半截 JSON，丢弃或缓存重试 */
      }
    }
  }
}
```

**两个必踩的坑**：

| 坑                  | 原因                                         | 解法                                     |
| ------------------- | -------------------------------------------- | ---------------------------------------- |
| 中文出现乱码/半个字 | `TextDecoder` 默认按块解码，多字节字符被切断 | `decode(value, { stream: true })`        |
| 偶发 JSON 解析失败  | 网络分块与 `\n` 不重合，收到半行             | 用 `buffer` 缓存残行，按 `\n` 切完再解析 |

**追问点**：

- `EventSource` 和 `fetch` 流选哪个？→ `EventSource` 只支持 GET、不能带自定义头、不能 POST body，所以**对话接口基本都用 `fetch` 流**；`EventSource` 适合简单的服务端推送。
- 后端返回的是 `data:` 分块还是一整段 JSON？→ 看协议，别假设。

### 12.3 打断生成与 AbortController ★★

**结论**：用户点「停止」要真取消请求，不是只停渲染。

**大白话**：点「停止」要用 `AbortController` 真把请求掐掉，不然模型还在后面烧钱。坑是主动掐断也会走到 `catch` 里，必须判断 `e.name === 'AbortError'` 区分开，否则用户点停止会看到「生成失败」的报错。

```ts
const controller = new AbortController();

async function send(text: string) {
  controller.abort(); // 发新消息前，先取消上一条
  const ctrl = new AbortController();
  currentController = ctrl;
  try {
    await streamChat(text, append, ctrl.signal);
  } catch (e: any) {
    if (e.name === "AbortError") return; // 主动取消 → 静默，不要弹错误提示
    throw e;
  }
}

function stop() {
  currentController?.abort();
}
onBeforeUnmount(() => currentController?.abort()); // 卸载必清，否则泄漏
```

**追问点**：

- 为什么主动 `abort()` 会走到 `catch`？→ `abort` 会以 `AbortError` reject，必须**和真错误区分开**，否则用户点停止也弹报错。
- 中断后已经收到的内容要不要保留？→ 通常**保留**（用户看到的部分回答仍是有效信息），并标记为「已停止」。
- 中断的请求后端还在跑怎么办？→ 前端只能取消连接；要省算力得靠后端感知断连（`AbortController` 传到下游）或计费口径兜底。

### 12.4 流式 Markdown 渲染与性能 ★★★

**结论**：流式渲染有两个专属难题 —— **半截语法** 与 **高频重渲染**。

**大白话**：流式渲染 Markdown 有两个专属麻烦：一是流到一半，代码块的 ``` 只有开头没结尾，解析器会把后面全当成代码，画面乱跳（给它补一个闭合就好）；二是每个 token 都重新解析渲染会卡死，要按帧节流把同一帧的多个 chunk 合并成一次渲染。

**问题 1：未闭合的代码围栏**
流到一半时 ` ``` ` 只有开头没有结尾，Markdown 解析器会把后面全部当代码块，画面抖动。

````ts
function closeOpenFence(md: string): string {
  const count = (md.match(/```/g) || []).length;
  return count % 2 === 1 ? md + "\n```" : md; // 奇数个围栏 → 补一个闭合
}
````

**问题 2：每个 token 都渲染 = 卡死**
按帧节流，把同一帧内的多个 chunk 合并成一次渲染：

```ts
let pending = false;
function scheduleRender(md: string) {
  if (pending) return;
  pending = true;
  requestAnimationFrame(() => {
    pending = false;
    html.value = renderMarkdown(closeOpenFence(md));
  });
}
```

**进阶**：只对**最后一个正在增长的消息**做实时渲染；历史消息渲染一次后缓存 HTML（`v-memo` 或直接存字符串），不要每次全量重解析。

**追问点**：

- 代码高亮（`highlight.js` / `shiki`）在流式下很贵怎么优化？→ 只高亮**已闭合**的代码块，未闭合的保持纯文本；或用 `shiki` 的按需懒加载 + 节流。
- XSS 怎么办？→ `marked` + `DOMPurify` 净化，**绝不**直接把模型输出丢进 `v-html` 不做处理。

### 12.5 多轮会话与上下文管理 ★★★

**结论**：模型**本身无状态**，上下文要么前端回传，要么后端按会话 id 存。

**大白话**：模型自己是「没记性的」，每问一次都得把之前的对话重新塞给它。所以前端要管三件事：把会话存下来（量大用 IndexedDB）、历史太长要裁剪（只带最近 N 轮或做摘要）、token 大概估一下别超了窗口。

**前端的活**：

1. **会话列表**：本地（IndexedDB 更合适，量大）持久化会话 id + 标题。
2. **历史裁剪**：上下文窗口有限，超了要裁 —— 保留 `system` + 最近 N 轮，或做摘要压缩。
3. **token 估算**：中文约 1 字 ≈ 0.6~1 token（不同模型不同），给个粗估防止超限报错。
4. **幂等与重发**：重发要能替换上一条，而不是追加成新的一轮。

```ts
function buildMessages(history: Msg[], system: string, maxTurns = 8) {
  return [
    { role: "system", content: system },
    ...history.slice(-maxTurns), // 只带最近 N 轮
  ];
}
```

**追问点**：

- 为什么不用 `ChatMemory` 放服务端？→ 看架构；单机/无状态部署时前端回传最简单，也能让用户「编辑历史重新提问」。
- 多标签页同时对话怎么办？→ 会话数据要按 id 隔离，`BroadcastChannel` 同步状态。

### 12.6 Tool / Function Calling 的前端呈现 ★★★

**结论**：Agent 类产品的前端难点是**中间态可见**。模型调用工具不是一瞬间，用户必须看得见「在调什么、成功没、拿到什么」。

**大白话**：Agent 类前端的难点是「中间态要可见」。模型调工具不是一瞬间的事，用户得看到「正在查什么、成功没、返回了什么」，所以要把工具调用渲染成可折叠的卡片，而不是把一坨 JSON 直接甩出来。

**要渲染的状态机**：

```
思考中 → 调用工具（名称 + 入参）→ 执行中 → 成功/失败（出参，可折叠）→ 继续生成
```

**要点**：

- **可折叠**：默认收起，只显示「已调用 `queryLessons`」，点开看完整入参与返回。
- **失败可重试**：工具失败要给用户「重试」按钮，而不是干等。
- **别把中间 JSON 裸露**：要映射成人类可读的卡片（如「查询 3 月 5 日 10:00 的时段」）。
- **流式事件要分类型**：`text_delta` / `tool_call` / `tool_result` / `done`，前端按 `type` 分发。

**追问点**：如果模型一次调多个工具怎么办？→ 并行展示多个卡片，各自独立状态。

### 12.7 SSE vs WebSocket 选型 ★★

| 维度 | SSE                              | WebSocket                |
| ---- | -------------------------------- | ------------------------ |
| 方向 | 服务端 → 客户端**单向**          | **双向**                 |
| 协议 | HTTP（文本 `text/event-stream`） | 独立 `ws://` 升级        |
| 重连 | 浏览器**自动重连**               | 需自己实现               |
| 场景 | 大模型流式输出、日志、通知       | 协作编辑、实时语音、游戏 |

**结论**：**AI 对话默认 SSE**（够用、简单、走 HTTP 基础设施）；需要**双向**才上 WebSocket。

**大白话**：选型就看「要不要双向」：AI 对话是服务端单向推给前端，SSE 够用，还自带断线重连；要双向（协作编辑、游戏）才上 WebSocket，代价是重连得自己写、还得处理心跳保活。

**SSE 的几个实用细节**：

- **断线重连**：标准 `EventSource` 会带 `Last-Event-ID` 自动重连；用 `fetch` 流实现时要**自己做重连 + 续写**（记录已收 `seq`）。
- **心跳保活**：长时间无数据时，网关可能掐连接 —— 服务端定期发注释行 `: ping` 保活。
- **不能 POST**：`EventSource` 只支持 GET，所以对话接口一律用 `fetch` + `ReadableStream` 自己解析 SSE 格式。

**追问点**：SSE 走 HTTP/1.1 时有 6 连接数限制 → HTTP/2 多路复用可缓解；同域下别开太多长连接。

### 12.8 RAG 与多模态的前端职责 ★★

**大白话**：模型能力在服务端，前端的活是「把不确定性好好呈现出来」：RAG 要展示引用来源和解析进度；多模态要处理图片压缩、预览、语音录制；模型返回的 JSON 要容错解析（可能被围栏包着、前后带解释文字、甚至半截），解析成功要变成表格 / 卡片，而不是一坨原文。

**核心一句话**：模型的能力在服务端，**前端的活是「把不确定性妥帖地呈现出来」**。

- **RAG（检索增强）**：检索结果要**展示引用来源**（文件名 + 页码/片段），支持点开原文定位；置信度低的答案要**明确标注**，别让用户当成事实。上传文档要有**解析进度**（解析中 / 切片中 / 已完成）与失败重试。
- **多模态**：图片上传（前端压缩 + 预览 + `FileReader`/`createObjectURL`）、语音输入（`MediaRecorder` + 波形可视化）、图片与文件在对话流中的渲染。
- **结构化输出**：模型返回 JSON 时前端要**容错解析** —— 可能被 ```json 围栏包裹、可能前后带解释文字、可能半截被截断（流式未结束）。解析失败要有兜底（展示原文 + 重试），成功则**映射成表格 / 卡片**而不是 `<pre>` 原文。
- **引用与溯源**：把「模型说的」和「文档里写的」视觉上区分开，避免用户混淆来源。

**追问点**：流式返回的 JSON 怎么渲染成卡片？→ 不能边流边 `JSON.parse`（未闭合必失败）；要么**等流结束再解析**，要么解析**流式 JSON 片段**（如 `partial-json` / 逐字段增量渲染）。

### 12.9 AI 辅助开发的工程治理 ★★

**大白话**：AI 治理就四条线：准入（过 lint / tsc / 测试才能提交）、安全（公司代码和用户数据不能喂外部模型）、规范（把规则写进仓库让 AI 遵守）、可追溯（AI 参与的改动留说明）。最有效的一条红线是「**AI 只写实现，不动架构与公共抽象**」。

**四条治理线**：

| 维度                     | 做法                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------ |
| **准入**（代码质量）     | CR 卡点、提交前必须过 `eslint` / `tsc` / 单测；约定「**AI 只写实现，不动架构与公共抽象**」 |
| **数据安全**             | 公司代码/用户数据**不能**喂外部模型；私有化部署 / 内网网关 / 脱敏后再贴                    |
| **规范**（让 AI 更听话） | 项目级 prompt 模板（角色 + 约束 + 少样本 + 输出格式），团队共享 `.rules` / `AGENTS.md`     |
| **可追溯**               | AI 参与的改动要留说明（commit / PR 描述），便于 review 与回溯                              |

**为什么要「AI 只写实现」**：架构与公共抽象是长期成本，被模型"顺手优化"后很难发现，且破坏一致性；把它划成**人工专属区**是实践中最有效的一条红线。

**追问点**：

- 你怎么衡量 AI 提效？→ 别只看「写得快」；看**返工率、缺陷率、CR 意见数、上线事故**，防止「生成得快、修得更慢」。
- 怎么让 AI 遵守项目约定？→ 把约定**写进仓库**（`AGENTS.md` / 规则文件）+ 代码里给参照实现，比每次口头嘱咐有效。

### 12.10 LLM 基础概念速答 ★

**大白话**：这一页是概念速答，不求深、能一句话说清就行：Token 是模型眼里的最小文本单位；上下文窗口是「一次能看多少」；Temperature 是随机性；Embedding 是把文本变向量用来算相似度；RAG 是先查资料再回答；幻觉是模型一本正经地编。

| 概念                 | 一句话                                                                   |
| -------------------- | ------------------------------------------------------------------------ |
| Token                | 模型处理的最小文本单元，中文约 1 字 ≈ 1~2 token（因模型而异）            |
| 上下文窗口           | 单次能「看到」的最大 token 数，超了必须裁剪或摘要                        |
| Temperature          | 采样随机性，0 更确定，1 更发散                                           |
| Embedding            | 把文本向量化，用于相似度检索（RAG 的基础）                               |
| RAG                  | 检索增强：先查知识库，把相关片段塞进上下文再让模型回答                   |
| Function Calling     | 模型输出结构化调用意图，由外部执行后把结果回传                           |
| Agent                | 让模型多轮自主决策 + 调工具完成任务                                      |
| 幻觉                 | 模型编造看似合理但错误的内容，必须靠引用/工具/校验兜底                   |
| 预训练 / 微调        | 前者是通用底子，后者用领域数据「教」它说行话（成本高，非必要不用）       |
| 推理模型（思考模式） | 先输出思维链再给答案，适合复杂推理；但**更慢更贵**，且思考内容通常不回传 |
| 流式 vs 非流式       | 流式首字快、体验好；非流式能拿完整结构，适合短任务/需要整体解析的场景    |

**追问点**：`temperature = 0` 就一定可复现吗？→ 更确定，但受硬件并行、浮点误差影响仍**不保证**完全一致；要严格一致得靠缓存或固定种子（很多 API 不暴露）。

### 12.11 浏览器端 AI（加分项）★★★

**大白话**：浏览器里跑 AI 是可行的（`transformers.js`、`onnxruntime-web` + WebGPU），但必须放 Web Worker，不然主线程直接卡死；模型文件几十 MB 要缓存起来并给进度条。它真正的价值是「数据不出本地」和离线可用，性能是次要的 —— 所以生产里还是服务端推理更常见。

**可行路径**：

- **`transformers.js`**：在浏览器直接跑 HuggingFace 模型（文本分类、翻译、小模型推理、向量化）。
- **`onnxruntime-web` + WebGPU**：用 GPU 加速推理；不支持时降级 **WASM**（CPU）。
- **Web Worker**：模型推理**必须放 Worker**，否则主线程卡死、页面无响应（对应 1.5 的"长任务阻塞"）。
- **缓存**：模型文件几十 MB，用 `CacheStorage` / IndexedDB 缓存，避免重复下载；首次加载要给进度条。
- **适用场景**：**隐私敏感**（数据不出端）、**离线可用**、简单分类 / OCR / 向量检索。

**追问点**：

- 为什么生产里少用？→ 模型体积大、首屏加载慢、浏览器兼容与算力差异大；更常见的是**服务端推理 + 前端流式消费**。
- 浏览器端 AI 的最大价值是什么？→ **数据不出本地**（合规/隐私场景），以及断网可用；性能是次要考量。

### 12.12 前端 AI 应用高频代码题（可运行实现）

**大白话**：这几段是「能直接跑的实现」：打字机效果分真流式（来一块追加一块）和假流式（后端一次性返回、前端自己补动画）；对话流要能打断，并且只在用户没往上翻的时候才自动滚到底，别抢用户的滚动。

**① 打字机效果（真流式 vs 假流式）**

```ts
// 真流式：拿到一块就直接追加，不做额外定时器
function append(chunk: string) {
  content.value += chunk;
}

// 假流式（后端一次性返回，前端补效果）—— 面试官问「只有整段返回怎么办」
async function typewriter(text: string, el: HTMLElement, speed = 20) {
  for (const ch of text) {
    el.textContent += ch;
    await new Promise((r) => setTimeout(r, speed));
  }
}
```

**② 可打断 + 自动滚动的完整对话流**

```ts
async function chat(input: string) {
  stop(); // 先停上一条
  controller = new AbortController();
  const msg = reactive({
    role: "assistant",
    content: "",
    status: "generating",
  });

  try {
    await streamChat(
      input,
      (c) => {
        msg.content += c;
        scrollToBottom(); // 注意：只在用户未手动上滑时自动置底
      },
      controller.signal,
    );
    msg.status = "done";
  } catch (e: any) {
    if (e.name === "AbortError") msg.status = "stopped";
    else {
      msg.status = "error";
      Message.error("生成失败");
    }
  }
}

function scrollToBottom() {
  const el = listRef.value;
  if (!el) return;
  const nearBottom = el.scrollHeight - el.scrollTop - el.clientHeight < 80;
  if (nearBottom) el.scrollTop = el.scrollHeight; // 用户上滑看历史时别抢滚动
}
```

**④ 会话历史裁剪**

### 12.13 前端 AI 健壮性：超时 / 重试 / 限流 / 降级 ★★★

**结论**：AI 接口**慢、贵、可能失败**，前端必须当「不可靠依赖」来设计。

**大白话**：AI 接口慢、贵、还容易挂，前端就得按「不可靠的东西」来设计：首字迟迟不来要有超时；流断了要保留已收到的内容并给重试；429 要提示冷却而不是傻等；被风控拦了要如实告诉用户原因。重试不能简单循环 —— 要退避，而且只重试「可重试」的错误。

| 问题             | 表现               | 前端对策                                                   |
| ---------------- | ------------------ | ---------------------------------------------------------- |
| **首字节超时**   | 迟迟不吐第一个字   | 单独设**首包超时**（如 15s），超时给提示/重试，别干等      |
| **中途断流**     | 流进行到一半连接断 | 保留已收内容 + 「继续生成/重试」按钮；按 `seq` 支持续写    |
| **限流 429**     | 请求太频繁         | 展示排队/冷却倒计时，禁用发送按钮，指数退避重试            |
| **内容安全拦截** | 命中风控           | 把拦截原因**如实展示**，别当普通错误吞掉                   |
| **模型报错 5xx** | 上游不稳定         | 可重试的错误做**有限次**重试（带退避），不可重试的立刻提示 |

```ts
// 带首包超时的流式请求：核心是「两个信号量合并」
const timeoutCtrl = new AbortController();
const timer = setTimeout(
  () =>
    timeoutCtrl.abort(new DOMException("first-byte timeout", "TimeoutError")),
  15000,
);
// 收到第一块数据就 clearTimeout(timer)
```

**追问点**：重试为什么不能简单 `for` 循环？→ ① 要**退避**（避免放大上游故障）；② 要区分**可重试**（超时/5xx/429）与**不可重试**（400 参数错/内容拦截），否则越重试越糟；③ 流式请求重试会**重复计费**，要谨慎。

### 12.14 Prompt 与上下文工程速答 ★★

**结论**：面试里「怎么让模型输出稳定」是高频题，答**结构 + 约束 + 少样本 + 校验**四件事。

**大白话**：想让模型输出稳定，就四招：把角色和任务边界写清楚；要求结构化输出（能上 JSON Schema 就别靠文笔描述）；给 1～3 个示例；返回之后必做校验。核心心法是 —— **永远不要无条件相信模型返回的东西**。

| 手段                   | 说明                                                                            |
| ---------------------- | ------------------------------------------------------------------------------- |
| **角色与目标**         | `system` 里定角色、任务边界、输出对象（「你是一个出题助手，只输出 JSON」）      |
| **结构化输出**         | 明确字段与类型；能约束就上 **JSON Schema / function calling**，比靠文笔描述靠谱 |
| **少样本（Few-shot）** | 给 1-3 个「输入 → 期望输出」示例，比纯规则更稳                                  |
| **思维链（CoT）**      | 复杂推理要求「先分析再结论」，或让它分步输出                                    |
| **约束与拒答**         | 明确「不知道就说不知道」、禁止编造；降低幻觉                                    |
| **校验兜底**           | 返回后**必做** JSON 解析 + schema 校验，失败走重试/降级，别直接信模型           |

**追问点**：对话越长越容易「遗忘/跑偏」怎么办？→ ① 关键约束**每轮都带**（别只放第一轮）；② 超长历史做**摘要压缩**；③ 把稳定的规则前置到 `system`，把易变信息放在最新一轮。

### 13.1 Java 集合与基础 ★★

**① ArrayList / LinkedList / HashMap**

**大白话**：选集合看「你要频繁干什么」：查得多用 `ArrayList`，头尾增删多才用 `LinkedList`（实际很少用），要按键取值用 `HashMap`。`HashMap` 底层是「数组 + 链表 + 红黑树」：hash 定到哪个桶，桶里太长（≥ 8 且数组 ≥ 64）就转红黑树。

| 集合         | 结构                 | 随机访问  | 增删                 | 备注                             |
| ------------ | -------------------- | --------- | -------------------- | -------------------------------- |
| `ArrayList`  | 动态数组             | O(1)      | 尾部 O(1)，中间 O(n) | 扩容 **1.5 倍**                  |
| `LinkedList` | 双向链表             | O(n)      | 头尾 O(1)            | 实际很少用（缓存不友好）         |
| `HashMap`    | 数组 + 链表 + 红黑树 | O(1) 平均 | —                    | 扩容 **2 倍**，负载因子 **0.75** |

**HashMap 关键细节**：

- 定位桶：`(n - 1) & hash`（要求容量是 2 的幂，等价取模但更快）。
- 链表长度 **≥ 8 且数组长度 ≥ 64** 才树化；退化为链表的阈值是 **6**（留 7 作为缓冲，防止抖动）。
- 默认容量 16，**扩容后元素要么留在原位，要么移动 `oldCap`**（这是 2 倍扩容的巧思）。
- **JDK 7 头插法导致并发扩容可能成环**；JDK 8 改成尾插，但**仍非线程安全**。

**追问点**：为什么负载因子是 0.75？→ 空间与查询时间的折中（泊松分布下冲突概率）。

---

**② `String` 不可变与常量池**

**大白话**：`String` 一旦创建就不能改，所以能安全共享、能当 `HashMap` 的 key、天生线程安全。要拼字符串用 `StringBuilder`；`StringBuffer` 每个方法都加了 `synchronized`，现在基本没必要用。

- `String` 用 `final char[]`（JDK 9+ 是 `byte[]` + coder 压缩），**不可变** → 可安全共享、作 `HashMap` key、天然线程安全。
- 字符串常量池 **JDK 7 起从方法区移到堆**；`intern()` 会返回池中引用。
- 拼接用 `StringBuilder`；`StringBuffer` 方法加 `synchronized`，已很少用。

---

**③ `==` / `equals` / `hashCode`**

**大白话**：这三个要一起看：`equals` 说相等，`hashCode` 就必须也相等 —— 否则对象放进 `HashMap` 后会「取不出来」（hash 落到别的桶去了）。反过来 `hashCode` 相同不代表 `equals` 相等，那只是撞桶了。

**契约**：`equals` 相等 → `hashCode` 必须相等；`hashCode` 相等 `equals` 不一定相等。
**违反契约的后果**：对象放进 `HashMap`/`HashSet` 后**取不出来**（hash 落到不同桶）。

---

**④ 泛型擦除 ★★**

**大白话**：泛型只是给编译器看的，编译完就被「擦掉」了 —— 运行时 `List<String>` 和 `List<Integer>` 是同一个类。所以不能 `new T[]`、不能 `instanceof List<String>`。这么做是为了兼容泛型出现之前（Java 5 之前）的老代码。

**结论**：Java 泛型是**编译期**特性，运行时被擦除为原始类型（`List<String>` → `List`）。

- 所以不能 `new T[]`、不能 `instanceof List<String>`；为兼容老代码（泛型 Java 5 才引入）。
- 好处：`List<String>` 和 `List<Integer>` 运行时是同一个类。

---

**⑤ 单例的 5 种写法 ★★**

**大白话**：日常记住这一种就够：**静态内部类**（懒加载 + 线程安全，还不用加锁）。如果非要写 DCL，`instance` 必须加 `volatile` —— 否则别的线程可能拿到一个「造了一半」的对象（引用有了，内容还没初始化）。

```java
// 静态内部类：懒加载 + 线程安全 + 无锁（推荐）
public class Singleton {
    private Singleton() {}
    private static class Holder { static final Singleton INSTANCE = new Singleton(); }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}

// DCL：注意 volatile，否则可能拿到「半初始化」对象
public class Singleton2 {
    private static volatile Singleton2 instance;
    public static Singleton2 getInstance() {
        if (instance == null) {
            synchronized (Singleton2.class) {
                if (instance == null) instance = new Singleton2();
            }
        }
        return instance;
    }
}
```

**追问点**：DCL 为什么必须 `volatile`？→ 禁止 `new` 的「分配内存 → 初始化 → 赋值引用」指令重排，避免其他线程读到引用非 null 但对象未初始化完。

### 13.2 Java 并发 ★★★

**① `synchronized` 与锁升级**

**大白话**：`synchronized` 的锁会「看竞争情况自动升级」：没人抢时最轻（偏向锁，JDK 15 起已废弃）→ 有人抢就 CAS 自旋 → 抢得狠了才让线程真正挂起（重量级锁）。只能升级不能降级，而且是可重入的。

| 状态          | 说明                                                             |
| ------------- | ---------------------------------------------------------------- |
| 无锁 → 偏向锁 | 同一线程反复进入，只记线程 ID（**JDK 15 已废弃，JDK 18+ 移除**） |
| 轻量级锁      | CAS 自旋抢锁，适合竞争少                                         |
| 重量级锁      | 依赖 OS 的 `Monitor`，线程阻塞挂起                               |

> ⚠️ **JDK 21 已移除偏向锁**（JEP 374 起逐步弃用）。答「JDK 8 有偏向锁、JDK 21 已移除」比背老八股更显真实。

- 原理：对象头 Mark Word + Monitor 对象（`_owner`/`_entryList`/`_waitSet`）。
- 锁只能**升级不能降级**；`synchronized` 有**可重入**性。

**② `volatile` ★★**

**大白话**：`volatile` 管两件事：一个线程改的值别的线程立刻能看到、禁止指令重排。但它**不管原子性**，所以 `i++` 就算加了 `volatile` 也不安全（得用 `AtomicInteger` 或加锁）。

- 保证**可见性**（写立即刷回主存、读从主存读）与**禁止指令重排**；**不保证原子性**（`i++` 仍不安全）。
- 底层：内存屏障（LoadLoad/StoreStore 等）。
- 经典用法：DCL 单例、状态标志位。

**③ CAS 与 ABA ★★★**

**大白话**：CAS 就是「先比一下，没变我再改」的原子操作，失败了就重试。它有三个毛病：ABA（值被别人改了一圈又改回来，你察觉不到，要加版本号）；一直失败会空转费 CPU；一次只能保证一个变量的原子操作。

- CAS = `compareAndSwap`，靠 CPU 原子指令；失败自旋重试。
- **三个问题**：ABA（用 `AtomicStampedReference` 加版本号解决）、自旋开销大、只能保证**一个变量**原子（多个用 `AtomicReference`）。
- `AtomicInteger` / `LongAdder`（高并发下 `LongAdder` 分段累加更优）。

**④ 线程池 ★★★**

**大白话**：线程池接活的顺序是：核心线程没满 → 开核心线程；满了 → 排队；队列也满了 → 开临时线程；再满 → 触发拒绝策略。记住这条顺序，比背七个参数名有用得多。另外别用 `Executors.newFixedThreadPool` —— 它的队列是无界的，任务堆多了直接 OOM。

```java
new ThreadPoolExecutor(
    2,                                    // corePoolSize
    4,                                    // maximumPoolSize
    60L, TimeUnit.SECONDS,                // keepAliveTime
    new ArrayBlockingQueue<>(100),        // workQueue
    Executors.defaultThreadFactory(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝策略
);
```

**执行流程**：核心线程未满 → 建核心线程；满了 → 入队列；队列满 → 建非核心线程；**再满 → 触发拒绝策略**。

**四种拒绝策略**：`AbortPolicy`（默认，抛异常）、`CallerRunsPolicy`（调用者执行，**天然的背压**）、`DiscardPolicy`（静默丢）、`DiscardOldestPolicy`（丢最老）。

**为什么不用 `Executors.newFixedThreadPool`？** → 它用**无界队列**（`LinkedBlockingQueue`），任务堆积会导致 **OOM**；`newCachedThreadPool` 最大线程数为 `Integer.MAX_VALUE`，可能创建海量线程。**必须手动 `new ThreadPoolExecutor`**。

**追问点**：线程池参数怎么定？→ CPU 密集 ≈ 核数 + 1；IO 密集可放大 2 倍或用 `动态调参`；核心指标看**队列长度与拒绝次数**。

**⑤ ThreadLocal ★★★**

**大白话**：`ThreadLocal` 是「每个线程自己的一份变量」。坑在内存泄漏：key 是弱引用会被回收，value 却还挂在 Map 上没人管，所以用完**必须**在 `finally` 里 `remove()`。线程池下更要清，不然下一个任务会读到上一个人留下的数据。

- 原理：每个 `Thread` 持有 `ThreadLocalMap`，key 是 `ThreadLocal`（**弱引用**），value 强引用。
- **内存泄漏**：key 弱引用被回收后，value 成「key 为 null 的强引用」无法回收 → **必须 `try/finally` 里 `remove()`**。
- 线程池下会**串数据**（线程复用），更要清理。
- 跨线程传递：`InheritableThreadLocal`（只在线程创建时继承，线程池失效）→ 阿里 `TransmittableThreadLocal`。

**⑥ AQS 与 `ReentrantLock` ★★★**

**大白话**：AQS 可以理解成「一个状态位 + 一个排队队列」，抢锁就是抢这个状态位，抢不到就去排队等着。`ReentrantLock` 比 `synchronized` 多出来的能力：可设公平、可中断、可超时、能配多个 `Condition`；代价是必须自己 `unlock()`。

- AQS = `volatile int state` + **CLH 双向队列**，`ReentrantLock` 通过 CAS 改 state 抢锁。
- `ReentrantLock` vs `synchronized`：**公平锁可选、可中断、可超时、可多条件（`Condition`）**；但必须手动 `unlock()`。

**⑦ `CompletableFuture` ★★**

**大白话**：`CompletableFuture` 用来「把几个互不依赖的请求并行发出去再合并结果」（比如同时查两个接口）。注意它默认用的是公共线程池，生产上一定要传自己的线程池，否则不同业务会互相抢线程、互相拖死。

```java
CompletableFuture
  .supplyAsync(() -> queryA())
  .thenCombine(CompletableFuture.supplyAsync(() -> queryB()), (a, b) -> merge(a, b))
  .exceptionally(e -> fallback())
  .join();
```

**追问点**：默认线程池是 `ForkJoinPool.commonPool()`，**生产必须传自定义线程池**，否则不同业务互相阻塞。

### 13.3 JVM 基础 ★★

**① 内存区域**

**大白话**：JVM 内存分「线程私有」和「线程共享」两类：私有的（程序计数器、虚拟机栈、本地方法栈）跟着线程走；共享的是堆和方法区，其中方法区从 JDK 8 起叫「元空间」，用的是本地内存而不是 JVM 堆。

| 区域            | 线程     | 说明                                                          |
| --------------- | -------- | ------------------------------------------------------------- |
| 程序计数器      | 私有     | 唯一不会 OOM 的区域                                           |
| 虚拟机栈        | 私有     | 栈帧 = 局部变量表 + 操作数栈；`StackOverflowError` 多来自递归 |
| 本地方法栈      | 私有     | native                                                        |
| 堆              | **共享** | 对象实例；GC 主战场                                           |
| 方法区 / 元空间 | 共享     | **JDK 8 起用元空间（本地内存）替代永久代**                    |
| 直接内存        | —        | NIO `DirectByteBuffer`                                        |

**② 对象创建与 GC**

**大白话**：GC 判断垃圾的标准不是「有没有人引用我」，而是「从 GC Roots（栈里的局部变量、静态变量等）出发能不能走到我」—— 走不到就是垃圾。新对象一般先放在 Eden，活过几轮 GC 才慢慢挪到老年代。

- 分配：**TLAB**（线程本地分配缓冲，避免竞争）→ 指针碰撞。
- **可达性分析**：从 **GC Roots**（栈中局部变量、静态变量、常量、JNI 引用）出发，不可达即回收。
- 分代：新生代（Eden + 两个 Survivor，默认 `8:1:1`）+ 老年代。
- 对象晋升老年代：年龄达 15、`Survivor` 装不下、大对象直接进老年代。
- 引用类型：强 / 软（内存不足时回收）/ 弱（下次 GC 必回收）/ 虚。

**③ 垃圾回收器**

**大白话**：回收器的发展主线就一句话 ——「停顿越来越短」：Serial / ParNew 是分代时代的老家伙；CMS 追求低停顿但有内存碎片；G1 是 JDK 9 之后的默认（按 Region 划分、停顿可预测）；ZGC 是为了在大堆下也几乎不停顿。

| 回收器           | 特点                                                    |
| ---------------- | ------------------------------------------------------- |
| Serial / ParNew  | 单线程 / 多线程，分代                                   |
| CMS              | 并发标记清除，追求**低停顿**，有碎片问题（JDK 14 移除） |
| **G1**           | **JDK 9+ 默认**，Region 划分，可预测停顿模型            |
| ZGC / Shenandoah | 超低停顿（< 10ms），大堆首选                            |

**④ 类加载与双亲委派 ★★★**

**大白话**：双亲委派就是「要加载一个类，先让爸爸试，爸爸不行自己再上」。好处是自己写的 `java.lang.String` 永远顶不掉 JDK 的（安全），也避免重复加载。SPI、Tomcat 这类需要「反过来」的场景，就会去打破它。

`加载 → 验证 → 准备 → 解析 → 初始化`。

**双亲委派**：类加载请求先交给父加载器（`Bootstrap → Extension/Platform → Application`），父加载不了才自己加载。

- **好处**：避免核心类被篡改（自定义 `java.lang.String` 加载不到）、避免重复加载。
- **打破场景**：SPI（`ServiceLoader`、JDBC 驱动）、Tomcat 的 WebApp 隔离、OSGi、热部署。

**追问点**：`Class.forName` 与 `ClassLoader.loadClass` 的区别？→ 前者会触发初始化，后者不会。

### 13.4 Spring / Spring Boot ★★★

**① IoC 与 Bean 生命周期 ★★**

**大白话**：Bean 的一生：先 new 出来 → 注入依赖 → 跑各种 Aware / 初始化回调 → **在这一步被 AOP 包成代理** → 使用 → 销毁。记住「AOP 代理是在初始化之后生成的」这句，很多问题（比如循环依赖为什么非要三级缓存）都从这儿来。

**Bean 生命周期**：实例化 → **属性注入** → `BeanNameAware`/`BeanFactoryAware` → `BeanPostProcessor.postProcessBeforeInitialization` → `@PostConstruct` → `InitializingBean.afterPropertiesSet` → 自定义 `init-method` → `BeanPostProcessor.postProcessAfterInitialization`（**AOP 代理在此生成**） → 使用 → `@PreDestroy` → `DisposableBean.destroy`。

**② 循环依赖与三级缓存 ★★★**

**大白话**：A 依赖 B、B 又依赖 A，怎么办？先把「造了一半的 A」提前放出来给 B 用 —— 这就是三级缓存的意义。三个限制要记住：构造器注入的循环依赖救不了（对象还没造出来）；`prototype` 的救不了；三级缓存的真正目的不是「解耦」，而是保证 AOP 代理前后是同一个对象。

| 缓存 | 名称                    | 作用                 |
| ---- | ----------------------- | -------------------- |
| 一级 | `singletonObjects`      | 成品 Bean            |
| 二级 | `earlySingletonObjects` | 半成品（早期引用）   |
| 三级 | `singletonFactories`    | 工厂（用于生成代理） |

**流程**：A 依赖 B，B 依赖 A → 创建 A 时把 A 的工厂放三级缓存 → 创建 B 时从三级缓存取 A 的**早期引用**注入 → B 完成 → A 完成。

**三个关键限制**：

1. **构造器注入的循环依赖无法解决**（实例都没创建出来）；
2. `prototype` 作用域的循环依赖无法解决；
3. **三级缓存的真正意义不是「解耦」而是保证 AOP 代理对象一致** —— 若只用二级缓存，A 被注入的是原始对象，最终暴露的却是代理对象，两者不一致。

**③ AOP 原理 ★★**

**大白话**：AOP 就是「不修改原代码，在方法前后插一段逻辑」。实现方式是动态代理：目标类有接口就用 JDK 代理，没接口就生成子类（CGLIB）。所以 `final` 类、`final` 方法包不了。

- **JDK 动态代理**：目标类**实现了接口**时使用，基于 `InvocationHandler`。
- **CGLIB**：无接口时使用，**生成子类**覆写方法（Spring Boot 默认 `proxyTargetClass = true`，优先 CGLIB）。
- 限制：`final` 类/方法不能被 CGLIB 代理。

**④ `@Transactional` 失效场景 ★★★（高频！）**

**大白话**：`@Transactional` 是靠代理生效的，所以一旦「绕过了代理」就失效 —— 最常见的就是同一个类里 `this.otherMethod()` 自己调自己。另外两个大坑：异常被自己 `catch` 吞了（事务管理器根本不知道出了错）；默认只回滚运行时异常，受检异常要写 `rollbackFor = Exception.class`。

| 失效原因              | 说明                                                                                               |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| **同类内自调用**      | `this.method()` 不走代理，注解无效                                                                 |
| 方法**非 public**     | Spring AOP 不代理非 public 方法                                                                    |
| **异常被 catch 吞掉** | 事务管理器感知不到                                                                                 |
| **异常类型不匹配**    | 默认只回滚 `RuntimeException` / `Error`，**受检异常不回滚** → 要写 `rollbackFor = Exception.class` |
| 多线程                | 子线程不在同一事务上下文                                                                           |
| 代理未生效            | 类没被 Spring 管理、`@Transactional` 加在接口上但用了 CGLIB                                        |

**传播行为**（常用 3 个）：

| 传播               | 语义                                                             |
| ------------------ | ---------------------------------------------------------------- |
| `REQUIRED`（默认） | 有事务就加入，没有就新建                                         |
| `REQUIRES_NEW`     | **总是新建**，挂起外层；外层回滚不影响内层（**日志、审计必用**） |
| `NESTED`           | 嵌套事务（保存点），内层回滚不影响外层                           |

**追问点**：`REQUIRES_NEW` 与 `NESTED` 的区别？→ 前者是**独立物理事务**（挂起外层），后者是同一事务内的**保存点**（回滚到保存点，外层仍可提交）。

**⑤ Spring Boot 自动配置原理 ★★★**

**大白话**：自动配置就是「约定优于配置」：启动时读一个固定的清单文件（`AutoConfiguration.imports`），把里面列的配置类逐个试一遍，每个类上都写着「满足条件才生效」（比如类路径里有某个 jar 才生效）。你自己定义的 Bean 优先 —— 有 `@ConditionalOnMissingBean` 主动让位。

1. `@SpringBootApplication` = `@SpringBootConfiguration` + `@ComponentScan` + **`@EnableAutoConfiguration`**。
2. `@EnableAutoConfiguration` 通过 `@Import(AutoConfigurationImportSelector.class)` 读取
   **`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`**
   （Spring Boot 2.7 之前是 `spring.factories`）。
3. 每个自动配置类上挂**条件注解**：`@ConditionalOnClass` / `@ConditionalOnMissingBean` / `@ConditionalOnProperty`，
   满足条件才生效。
4. 用户自定义 Bean 优先（`@ConditionalOnMissingBean` 让位）。

**⑥ Spring MVC 请求流程 ★★**

**大白话**：请求先到 `DispatcherServlet`（总调度），它去找「这个 URL 该谁处理」（`HandlerMapping`），再让适配器去调你的 Controller，同时负责把请求参数解析成对象、把返回值序列化成 JSON。

`DispatcherServlet` → `HandlerMapping` 找 handler → `HandlerAdapter` 调用 → 参数解析（`ArgumentResolver`）→ 执行 Controller → `HttpMessageConverter` 序列化 → `ViewResolver` / `@ResponseBody` 直接返回。

**⑦ 过滤器 / 拦截器 / AOP ★★**

**大白话**：三者的区别就是「站的位置不同」：`Filter` 在最外面（还没进 Spring MVC），拿不到什么 Bean；`Interceptor` 在 Spring MVC 里（能注入 Bean，适合鉴权、日志）；AOP 管得最小，只管某一个方法。

|               | 作用范围     | 能否拿 Bean        | 时机                        |
| ------------- | ------------ | ------------------ | --------------------------- |
| `Filter`      | Servlet 容器 | 难（依赖注入受限） | 进入 DispatcherServlet 之前 |
| `Interceptor` | Spring MVC   | 可以               | handler 前后                |
| `AOP`         | 方法级       | 可以               | 方法调用前后                |

**追问点**：跨域、编码、请求日志放哪？→ 跨域/编码用 `Filter`；鉴权、日志用 `Interceptor`；业务日志用 AOP。

### 13.5 MyBatis / MyBatis-Plus ★★

**① `#{}` 与 `${}` ★★★**

**大白话**：`#{}` 是参数占位符，走预编译，参数被当成「值」，天然防注入；`${}` 是把内容直接拼进 SQL，能把 SQL 片段塞进来，所以只有 `order by` 这种没法预编译的地方才用，而且必须做白名单校验。

|       | 原理                                     | 安全                                                                      |
| ----- | ---------------------------------------- | ------------------------------------------------------------------------- |
| `#{}` | 预编译占位符 `?`，走 `PreparedStatement` | **防 SQL 注入**                                                           |
| `${}` | 字符串直接拼接                           | **有注入风险**，只用于 `order by ${col}` 等无法预编译处（且要白名单校验） |

**② 一级 / 二级缓存**

**大白话**：一级缓存是「同一个 `SqlSession` 里查过的先记着」（默认开，一有增删改就清空）；二级缓存是跨 `SqlSession` 的（默认关，容易脏读，分布式下别用 —— 要缓存就上 Redis 更稳）。

- **一级缓存**：`SqlSession` 级别，**默认开**；同 session 内相同查询命中缓存。**执行 update/delete 或 `sqlSession.clearCache()` 会清空**。
- **二级缓存**：`Mapper` / `namespace` 级别，需 `@CacheNamespace` 或 `<cache/>` 显式开启；**跨 session 共享**，容易脏读，分布式下慎用（建议直接用 Redis）。

**③ MyBatis-Plus 实践（咱们项目在用）**

**大白话**：MP 的价值是把单表 CRUD 全替你写了。几个容易忘的配置：分页必须注册拦截器（不注册，`Page` 查询会当没分页）；逻辑删除靠 `@TableLogic`（删除变成 UPDATE，要留意唯一索引冲突）；创建 / 更新时间用 `MetaObjectHandler` 自动填。

- **分页**：需注册 `MybatisPlusInterceptor` + `PaginationInnerInterceptor`，否则 `Page` 查询不分页。
- **逻辑删除**：`@TableLogic`，删除变 `UPDATE ... SET deleted = 1`；**全局配置要加 `select` 时自动过滤**。
- **乐观锁**：`@Version`，更新时带版本条件，`affectedRows = 0` 即冲突。
- **自动填充**：`MetaObjectHandler` 填充 `createTime / updateTime`。
- **`LambdaQueryWrapper`**：方法引用写法（`Student::getName`），比字符串字段名安全、IDE 可重构。

**④ N+1 问题 ★★**

**大白话**：N+1 就是「查一次列表，再为每一行各查一次详情」，十条数据发十一条 SQL。解法是 `JOIN` 一次查完，或者先 `IN` 批量查出来再在内存里按 key 分组拼上 —— 千万别在循环里发 SQL。

**现象**：查 1 次主表 → 循环查 N 次子表（1 + N 次 SQL）。
**解法**：用 `JOIN` 一次查完、或 `IN` 批量查询后在内存里聚合（`Map` 分桶）。**别在循环里发 SQL**。

**追问点**：

- 逻辑删除有什么坑？→ 加了 `deleted` 标记后，**唯一索引会与已删除数据冲突**（同一名字删了又建会撞索引）；解法是把唯一索引改成「唯一索引 + `deleted` 列」的联合索引，或删除时把 `deleted` 置为主键值。
- `#{}` 为什么能防注入？→ 走 `PreparedStatement` 预编译，参数被当**值**处理而不是 SQL 片段。

### 13.6 MySQL ★★★

**① 索引：B+ 树 ★★**

**大白话**：MySQL 用 B+ 树做索引是因为它「矮胖」：非叶子节点只存 key，扇出大，三层就能覆盖千万级数据，磁盘 IO 少。二级索引的叶子存的是主键值，所以查非索引字段要「回表」再查一次；要查的字段全在索引里（覆盖索引）就不用回表。

**为什么用 B+ 树？** 三层即可存千万级数据（非叶子节点只存键，扇出大）→ 磁盘 IO 少；叶子节点**双向链表**，范围查询高效。

- **聚簇索引**：主键索引，叶子节点**存整行数据**（InnoDB 表就是聚簇索引组织表）。
- **非聚簇（二级）索引**：叶子存**主键值** → 查非索引列要**回表**。
- **覆盖索引**：查询列全在索引里，无需回表（`explain` 的 `Extra = Using index`）。

**索引失效场景（高频）**：

```sql
-- 1. 函数/运算作用于索引列
WHERE DATE(create_time) = '2026-01-01'   -- ✗
WHERE create_time >= '2026-01-01' AND create_time < '2026-01-02'  -- ✓

-- 2. 隐式类型转换（varchar 列传数字）
WHERE phone = 13800000000    -- ✗  应为 phone = '13800000000'

-- 3. 前导模糊
WHERE name LIKE '%张'        -- ✗   LIKE '张%' 可以

-- 4. 不满足最左前缀
-- 索引 (a, b, c)，WHERE b = 1 用不上

-- 5. OR 连接非索引列

-- 6. 范围条件之后的列失效（a 用范围，后面的 b、c 用不上索引）
```

**② 事务与 MVCC ★★★**

**大白话**：MVCC 让「读」和「写」不打架：读的时候不加锁，而是按 `ReadView` 去看历史版本（快照读）。默认隔离级别 RR 下，快照读把大部分幻读挡掉了，但 `SELECT ... FOR UPDATE` 这种当前读还得靠间隙锁来防止插入。

- **ACID**：原子性（undo log）、一致性、隔离性、持久性（redo log + WAL）。
- **隔离级别**：读未提交 / 读已提交（RC）/ **可重复读（RR，MySQL 默认）** / 串行化。
- **MVCC**：`undo log` 版本链 + `ReadView`（`m_ids` / `min_trx_id` / `max_trx_id` / `creator_trx_id`），实现**快照读不加锁**。
- RR 下靠 **`next-key lock`（记录锁 + 间隙锁）** 解决幻读；RC 下只加记录锁。

**追问点**：为什么 RR 下仍需间隙锁？→ 快照读靠 MVCC，但当前读（`SELECT ... FOR UPDATE`）必须靠锁防幻读。

**③ 锁**

**大白话**：InnoDB 默认加的是行锁，但**前提是走了索引** —— 没走索引就会退化成锁全表，这是生产事故高发区。死锁的排查入口是 `SHOW ENGINE INNODB STATUS` 里的 `LATEST DETECTED DEADLOCK`。

- 行锁（InnoDB） vs 表锁（MyISAM）；意向锁（表级，标记「表里有行锁」）。
- **加锁前提：走索引**，否则**行锁升级为表锁**。
- 死锁：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`；避免方式：**按固定顺序访问资源、缩小事务范围、减少交叉更新**。

**④ `explain` 关键字段 ★★**

**大白话**：`explain` 先看 `type`（有没有走索引，出现 `ALL` 就要警惕），再看 `key`（实际用了哪个索引）、`rows`（大概扫多少行），最后看 `Extra`：出现 `Using filesort` / `Using temporary` 就该优化了。

| 字段    | 关注点                                                                       |
| ------- | ---------------------------------------------------------------------------- |
| `type`  | **system > const > eq_ref > ref > range > index > ALL**；出现 `ALL` 要警惕   |
| `key`   | 实际使用的索引                                                               |
| `rows`  | 预估扫描行数                                                                 |
| `Extra` | `Using index`（覆盖索引，好）/ `Using filesort`、`Using temporary`（需优化） |

**⑤ 深分页优化 ★★**

**大白话**：`LIMIT 1000000, 20` 慢的原因不是只取 20 条，而是「前面 100 万行也要扫出来再丢掉」。解法两条：用游标（`WHERE id > 上次最后一条的 id`），或者先用子查询走索引把这 20 个 id 捞出来，再关联回表取全字段。

```sql
-- ✗ 慢：扫 100 万行再丢 100 万行
SELECT * FROM lesson ORDER BY id LIMIT 1000000, 20;

-- ✓ 游标 / 延迟关联
SELECT * FROM lesson WHERE id > 1000000 ORDER BY id LIMIT 20;
SELECT l.* FROM lesson l
JOIN (SELECT id FROM lesson ORDER BY id LIMIT 1000000, 20) t ON l.id = t.id;
```

### 13.7 Redis 与分布式（了解即可，但必被问）★★

**① 缓存三大问题 ★★★**

**大白话**：三个问题的区别在「打的是哪一环」：穿透 = 查压根不存在的数据（缓存和 DB 都没有，每次都怼到 DB）；击穿 = 一个热点 key 恰好过期，瞬间的请求全压上 DB；雪崩 = 一大批 key 同时过期。对策也对得上：布隆过滤器 / 缓存空值、互斥锁重建、TTL 加随机值。

| 问题     | 现象                           | 解法                                       |
| -------- | ------------------------------ | ------------------------------------------ |
| **穿透** | 查不存在的数据，绕过缓存打 DB  | 布隆过滤器、缓存空值（短 TTL）             |
| **击穿** | 热点 key 过期瞬间大量请求      | 互斥锁重建、逻辑过期（不设 TTL，异步续期） |
| **雪崩** | 大量 key 同时过期 / Redis 宕机 | TTL 加随机值、多级缓存、限流降级           |

**② 分布式锁 ★★★**

**大白话**：加锁必须一条命令搞定（`SET key value NX PX 30000`）—— 拆成 SETNX + EXPIRE 两步，就可能在中间挂掉、导致锁永远不释放。释放时必须用唯一 value 校验后再删（用 Lua 保证原子），否则可能删掉别人的锁。

```java
// 错误写法：SETNX + EXPIRE 不是原子操作
// 正确：SET key value NX PX 30000
// 释放：必须校验 value（唯一值），否则可能删掉别人的锁 —— 用 Lua 保证原子
```

**要点**：① `SET NX PX` 一条命令保证原子；② value 存**唯一标识**，Lua 脚本校验后再删；③ 业务超时用**看门狗自动续期**（Redisson）；④ 主从切换会丢锁 → Redlock（有争议）或直接上 ZooKeeper/etcd。

**③ 幂等设计 ★★**

**大白话**：幂等就是「同一个请求来多次，结果一样」。常用手段按省事程度排：唯一索引兜底（最省事也最可靠）→ Token 一次性校验 → Redis SETNX 去重 → 状态机（只有合法状态才允许流转）。

`唯一索引` 兜底 / `Token` 机制（先取后验，一次性）/ `Redis SETNX` 去重 / 状态机（只有 `UNTAKEN → NORMAL` 合法）/ 数据库乐观锁。

**追问点**：

- 缓存与数据库怎么保持一致？→ 常用「**先更新 DB，再删缓存**」（Cache-Aside），并给缓存设过期兜底；严格一致要上**延迟双删**或订阅 binlog（Canal）。别用「更新 DB + 更新缓存」（并发下易脏）。
- 分布式锁为什么必须校验 value？→ 否则 A 的锁超时释放后，B 拿到锁，A 执行完又把 B 的锁删了 —— **删错别人的锁**。

### 13.8 手写 / 编码题 ★★

**① 线程交替打印（生产者-消费者）**

**大白话**：交替打印的套路是「不是我的轮次就 `wait`，打印完 `notifyAll` 叫醒别人」。关键细节：判断轮次要用 `while` 而不是 `if` —— 被唤醒后要重新检查条件，防止虚假唤醒。

```java
class Printer {
    private int state = 1;
    private final int max = 10;

    synchronized void print(int target, String name) throws InterruptedException {
        for (int i = 0; i < max; i++) {
            while (state % 3 != target) wait();      // 不是我的轮次就等
            System.out.println(name);
            state++;
            notifyAll();
        }
    }
}
```

**② LRU（`LinkedHashMap` 一行搞定）**

**大白话**：Java 里 LRU 不用自己写：`LinkedHashMap` 构造时传 `accessOrder = true`（按访问顺序排），再重写 `removeEldestEntry` 说一句「超过容量就删最老的」就行了。

```java
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LRUCache(int capacity) {
        super(capacity, 0.75f, true);   // accessOrder = true
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}
```

**③ 反转链表**

**大白话**：反转链表就是三个指针来回倒：`prev` 记住前一个、`next` 先存住后面的、然后把当前节点指回 `prev`，最后整体往前挪一格。

```java
ListNode reverse(ListNode head) {
    ListNode prev = null;
    while (head != null) {
        ListNode next = head.next;
        head.next = prev;
        prev = head;
        head = next;
    }
    return prev;
}
```

**④ 其他常考**：快排 / 归并、二分查找、统计出现次数最多的字符、字符串去重、两个有序数组合并、`Stream` 分组统计。

**大白话**：这一串是「经典老题」清单，面试前顺手过一遍就行，重点是能手写快排 / 归并和二分，别在边界条件（空数组、只有一个元素）上翻车。

### 13.9 Spring Boot 工程实践（面试爱问「你项目怎么分层」）★★

**① 统一返回体 + 全局异常**

**大白话**：统一返回体 = 全站接口都返 `{code, message, data}` 三件套，前端只认这一套。全局异常处理负责「把各种异常翻译成这个格式」：业务异常给可读文案，未知异常兜底 500，而且**不要**把堆栈返给前端。

```java
// 统一返回：code / message / data —— 前端只认这一套
public record Result<T>(int code, String message, T data) {
    public static <T> Result<T> ok(T data) { return new Result<>(0, "success", data); }
    public static <T> Result<T> fail(int code, String msg) { return new Result<>(code, msg, null); }
}

// 全局异常处理：业务异常给「可读文案」，未知异常兜底 500，别把堆栈暴露给前端
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BizException.class)
    public Result<Void> handleBiz(BizException e) { return Result.fail(e.getCode(), e.getMessage()); }

    @ExceptionHandler(MethodArgumentNotValidException.class)   // @Valid 校验失败
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldError().getDefaultMessage();
        return Result.fail(400, msg);
    }

    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception e) { log.error("系统异常", e); return Result.fail(500, "系统繁忙"); }
}
```

**② 参数校验（把校验写在入口）**

**大白话**：参数校验用注解声明（`@NotNull`、`@Min` 这些），Controller 上加 `@Valid` 就自动生效，比在方法体里手写一堆 `if` 干净得多，错误信息也能统一处理。

```java
public record LessonCreateDTO(
    @NotNull Long studentId,
    @NotBlank String date,
    @Min(1) @Max(12) Integer slotNo   // 用注解声明约束，Controller 上加 @Valid
) {}
```

**③ 事务边界（易错）**

**大白话**：事务加在 Service 的 `public` 方法上（Controller 不写事务），而且事务里别做远程调用或耗时操作 —— 事务开着的时候锁一直不放，很容易拖垮并发。

- `@Transactional` **加在 Service 的 public 方法**上；Controller 不写事务。
- 事务里**别做远程调用/耗时操作**（长事务锁表）。
- 需要「日志/审计不受主事务回滚影响」时用 `REQUIRES_NEW`。

**④ 日志规范**

**大白话**：打日志用占位符 `{}`，别用字符串拼 —— 拼的话即使这条日志不输出，字符串也已经算过一遍了。级别别乱用：`error` 只给需要人介入的，`info` 给关键业务节点；密码、token、完整手机号一律不打。

- 用 SLF4J + 占位符：`log.info("排课失败 studentId={} date={}", id, date)`（**不要**字符串拼 `+`）。
- 分级：`error` 只给「需要人介入」的问题，`warn` 给可恢复异常，`info` 给关键业务节点，`debug` 排查用。
- **禁止**打印敏感信息（密码、完整手机号、token）。

**⑤ 分层与 DTO 转换**

**大白话**：分层就是「Controller 只收参和包装返回，Service 管业务和事务，Mapper 只管 SQL」。对外返回用 VO 不用 Entity：Entity 带着内部字段（逻辑删除标记等），直接返会暴露出去，而且表结构一改接口就跟着变。

```
Controller（收参、@Valid、调 Service、包 Result）
  → Service（业务规则、事务、编排）
    → Mapper（SQL）
DTO ↔ Entity ↔ VO 用 MapStruct / 手写转换，别把 Entity 直接返给前端（会暴露内部字段）。
```

**追问点**：为什么要用 VO 而不是直接返 Entity？→ ① 隐藏内部字段（如逻辑删除标志、密码）；② 接口字段可独立演进，不受表结构变更影响；③ 可以拼装多个来源的数据。

**⑥ 接口幂等（下单/提交类必问）**：唯一索引兜底 + Token 机制（先取后验、一次性） + 乐观锁（`@Version`）。

**大白话**：下单、提交这类接口必须防重复。最省事的兜底是唯一索引（重复插直接失败）；再严一点用一次性 Token，或者乐观锁（`@Version`，更新时带版本条件，影响行数为 0 就说明被别人改过了）。

### 附录 0.5、先扫清四个名词：LLM / RAG / Agent / Skill

> 这四个词是现在 AI 圈的「普通话」。先别背定义，把「它到底解决什么问题」记住，剩下的自然能串起来。

**① LLM（大语言模型）= 一个「只会接话」的大脑**

- **一句话**：给它一段文字，它**预测下一个字**；一个字一个字往外蹦，蹦多了就像在回答你。
- **大白话**：它像一个**读过海量文本的「续写高手」**——你给上文，它给下文。它不查资料、不记事、不算数，全靠「见过的文本里，接下来通常写什么」。
- **必须知道的四个特点**：
  1. **不知道你的私事**：没训过你的数据，除非你在提示词里告诉它；
  2. **知识有截止日期**：训练完就冻结了，之后的新事它不知道；
  3. **会一本正经地胡说**（幻觉）：因为它的目标是「写得像人话」，不是「说得对」；
  4. **本身没有记忆**：每次对话对它都是第一次，所谓「记得上下文」是你每次都把历史带上。
- **代表**：GPT、Claude、DeepSeek、通义千问、Llama。你项目里接的 `deepseek-flash` 就是。

**② RAG（检索增强生成）= 给大脑配一个「开卷考试的抽屉」**

- **一句话**：**先去你的资料里查，再把查到的内容塞进提示词，让模型照着答。**
- **大白话**：LLM 是**闭卷考试**（凭记忆答，所以会瞎编）；RAG 是**开卷考试**——先翻书找到相关那几页，再照着回答。**「书」就是你的资料**（知识库、数据库、文档、试卷题库……）。
- **它解决三个死结**：
  1. 模型不知道你的私有知识 → 查给它；
  2. 模型知识过期 → 每次都查最新的；
  3. 模型爱编 → 要求它「只依据查到的内容回答」，并**给出引用出处**。
- **流程（背这五个词就够）**：**切分 → 向量化 → 检索 → 重排 → 拼进提示词生成**。
  - **切分**：把长文档切成小段（chunk）；
  - **向量化**：把每段文字变成一串数字（embedding），语义越近的数字越近；
  - **检索**：把用户问题也变成向量，找最像的几段；
  - **重排**：再精挑一遍，把最相关的排到最前；
  - **生成**：把这几段 + 问题一起交给 LLM，让它「照着这段答」。
- **一句话对比**：**微调 = 让模型「记住」；RAG = 让模型「查得到」。** 私域知识优先用 RAG（更新快、成本低、可溯源）。

**③ Agent（智能体）= 给大脑装上「手脚」**

- **一句话**：让模型不只说话，还能自己决定**「调什么工具、分几步做」**，直到把事办完。
- **大白话**：光有 LLM 是个**只会动嘴的顾问**；Agent 是**给它配了手脚和工具箱的员工**——它能自己判断「这事该查数据库还是该发通知」，调完看结果，再决定下一步。
- **核心循环**：**想（Reason）→ 做（Act，调工具）→ 看（Observe 结果）→ 再想**，转几圈直到任务完成。这就是 **ReAct** 模式。
- **三件套**：
  - **工具（Tools / Function Calling）**：先告诉模型「你能用的函数有哪些」，模型按约定格式输出「我要调这个、参数是这些」，**真正执行的是你的代码**；
  - **规划（Planning）**：把大任务拆成小步骤，按序或并行执行；
  - **记忆（Memory）**：短期（本次对话）+ 长期（存下来的事实 / 偏好）。
- **例子**：你说「帮我查这周谁缺课，并给家长发消息」→ Agent 自己调「查课表接口」→ 调「发消息接口」→ 汇报结果。全程你只说了一句话。
- **一句话**：**LLM 负责「想」，工具负责「做」，Agent 负责「把两者串成一个闭环」。**

**④ Skill（技能）= 打包好的「一套干活流程」**

- **一句话**：把一个特定任务的做法、步骤、规范、脚本**打成一个「包」**，Agent 遇到对应任务时按需取用。
- **大白话**：Agent 是员工，**Skill 就是岗位操作手册**——「做 PPT 的标准流程」「审代码的检查清单」。员工遇到这种活就翻出那本手册照着做，不用每次从头教。
- **和 Agent 的分工**：**Agent 决定「做什么」，Skill 规定「这类事该怎么做」**。前者是通用的「大脑 + 手脚」，后者是**领域经验的固化**。
- **一个 Skill 里通常有**：触发条件（什么时候用）、步骤说明、可复用的脚本 / 模板、注意事项。
- **为什么需要它**：不重复造轮子、把老手的经验沉淀下来、让 Agent 的表现更稳定可预期。
- **你已经在用**：本机的 `ts-code-review`、`vue-standard`、`pdf`、`pptx` 都是 Skill；把它们「装」进对话，AI 就按那套规范干活。
- **顺带记住 MCP**：工具怎么接进模型是有标准的，**MCP（Model Context Protocol）** 就是这套「通用插座」——按它做一次，各种模型 / 客户端都能插上你的工具。

**四者关系，背下这一句就够**

> **LLM 是大脑；RAG 是给它开卷考的资料抽屉；Agent 是给它装上的手脚；Skill 是发给它的岗位手册。**
>
> 只调模型 = 用大脑裸奔；加检索 = 开卷考试；加工具 + 循环 = 会干活的 Agent；把流程固化成手册 = Skill。
> 落地顺序也照这个来：**先会用 LLM → 再上 RAG → 再包成 Agent → 最后把重复流程沉淀成 Skill。**

### 附录 4、深度学习（核心中的核心）

- **神经网络基础**：感知机、多层感知机（MLP）、激活函数（ReLU / GELU / Sigmoid）、前向与反向传播、参数初始化（Xavier / He）、归一化（BatchNorm / LayerNorm）、残差连接。
- **训练技巧**：优化器选择、学习率 warmup + cosine 衰减、梯度裁剪、Dropout、权重衰减、混合精度（AMP）、梯度累积（显存不够时「假装」大 batch）。
- **CNN**：卷积 / 池化 / 步长 / 填充 / 感受野、经典网络演进（LeNet → AlexNet → VGG → **ResNet** → EfficientNet）、视觉三大任务（分类 / 检测 / 分割）。
- **序列模型**：RNN → LSTM → GRU、Seq2Seq、**注意力机制的由来**、梯度消失是怎么出现的。
- **Transformer（重中之重）**：Self-Attention 的 Q / K / V 计算、Multi-Head、位置编码（绝对 / 相对 / **RoPE**）、Encoder-Decoder 结构、pre-LN 与 post-LN、FFN、复杂度 O(n²)、**KV Cache**、FlashAttention 的思路。
- **生成模型**：AutoEncoder / VAE、GAN、**扩散模型**（DDPM → 潜空间扩散 → Stable Diffusion 原理）、流模型。
- **自监督与表征学习**：对比学习（SimCLR / MoCo）、**CLIP**（图文对齐，理解多模态的起点）、掩码预训练（BERT / MAE）。
- **大白话**：**Transformer 是当今一切大模型的地基**。至少要能手推一遍「一个词是怎么注意到其他词的」，并说清 KV Cache 为什么能加速 —— 这两点在面试和实战里都用得上。

### 附录 5、大语言模型（LLM）原理

- **发展脉络**：Word2Vec / GloVe（词向量）→ RNN → Transformer → **BERT（擅长理解）/ GPT（擅长生成）** 两条路线 → 规模化出现「涌现」。
- **分词**：BPE / WordPiece / SentencePiece；建立 Token 直觉（一个汉字大约 0.6~1.5 个 token）；为什么模型数不清字母。
- **架构细节**：Decoder-only、因果掩码、RoPE、GQA / MQA、MoE（混合专家）、上下文窗口怎么扩长。
- **训练三阶段（必须背下来）**：
  1. **预训练**：海量文本做「预测下一个 token」，产出基座模型；Scaling Law 讲规模与能力的关系。
  2. **指令微调 SFT**：用「指令 - 回答」数据让模型听懂人话。
  3. **对齐 RLHF**：训奖励模型 + PPO；简化方案 **DPO / ORPO**（现在更主流）。
- **推理与采样**：贪心 / Beam Search、温度、Top-k、Top-p、重复惩罚；**思维链 CoT**；推理模型（reasoning）为什么「想得久」。
- **效率与压缩**：量化（INT8 / INT4 / GPTQ / AWQ）、蒸馏、剪枝、**LoRA / QLoRA**、推理引擎（vLLM / PagedAttention / TGI / Ollama）。
- **评测**：困惑度（PPL）、通用基准（MMLU / GSM8K / HumanEval）、人工评测与 Arena 对战。
- **大白话**：这一章是「为什么现在的 AI 会这样」的解释器。**记住三阶段（预训练 → SFT → 对齐）以及 KV Cache、LoRA 这几个词，就已经超过大部分只会调接口的人。**

### 附录 6、大模型应用工程（最实用、最快见效）

- **Prompt 工程**：角色 / 指令 / 上下文 / 输出格式四要素；few-shot 示例；**思维链 CoT**；ReAct（思考 - 行动 - 观察循环）；结构化输出（JSON Schema / 函数签名）；**提示注入**怎么防。
- **向量与检索**：Embedding 模型怎么选、余弦相似度、向量库（FAISS / Milvus / pgvector）、文本切分策略（按标题 / 定长 / 重叠）、**混合检索**（BM25 关键词 + 向量）、重排（Rerank）。
- **RAG（必学）**：全链路 = 索引 → 检索 → 重排 → 拼上下文 → 生成 → 引用溯源；常见失败（召回不到 / 幻觉 / 上下文超长 / 多跳问题）；怎么评估（忠实度、相关性、答案正确率）。
- **Agent / 工具调用**：Function Calling 原理、工具怎么设计、任务规划、记忆（短期 / 长期）、多智能体协作、**MCP 协议**（把工具接进模型的标准方式）。
- **微调实践**：先想清楚「Prompt 能不能解决 / RAG 够不够」，都不行才微调；**LoRA / QLoRA 实操**、数据构造与配比、训练后如何评估。
- **前后端落地（你的强项）**：SSE / `fetch` + `ReadableStream` 流式渲染、首包超时、限流与降级、并发去重、**语义缓存**（相似问题直接命中）、token 记账与成本控制、可观测性（日志 / trace）。
- **护栏与安全**：离线评测集、A/B 实验、幻觉检测、内容安全、提示注入防护、隐私脱敏。
- **大白话**：**这一层是「能换钱」的一层**，面试 AI 岗问得最多的也是它 —— RAG 怎么搭、Agent 怎么做、流式怎么写、成本怎么控。

### 附录 6.5、大模型开发知识点补遗（实战手册）

> 附录 6 讲的是「要会什么」，这里补的是**真上手写代码时会遇到的知识点**。按「调用 → 提示 → 上下文 → 检索 → 智能体 → 微调 → 推理 → 上线」八层排，每层都是能直接背、直接用的话。

**A. 调用层：一次请求里到底有什么**

- **消息角色**：`system`（人设与规则，最先、最强约束）、`user`（用户输入）、`assistant`（模型历史回复）、`tool`（工具返回结果）。多轮对话就是把历史消息**按顺序整个发过去**——模型本身不存记忆。
- **采样参数**（决定「怎么选下一个字」）：
  - `temperature` 温度：越低越稳、越高越发散。**要准确用 0~0.3，要创意用 0.7~1.0**；
  - `top_p` / `top_k`：只在概率最高的候选里挑（核采样 / 前 k 个）；
  - `max_tokens`：输出上限，**不设容易烧钱、设小了会被截断**；
  - `stop`：遇到指定串就停；
  - `frequency_penalty` / `presence_penalty`：压重复；
  - `seed`：想复现结果就固定随机种子；
  - **思考型模型的额外项**：`reasoning_effort`（思考深度），开思考后同样内容更贵更慢。
- **Token 与计费**：**输入便宜、输出贵**（通常差 3~4 倍）；中文大概 1 个字 0.6~1.5 token；**上下文 = 输入 + 输出**，两个都算钱、都占窗口。
- **提示缓存（Prompt / Context Caching）**：重复的前缀（长 system、长文档）缓存后**输入价大幅打折**，是最简单的省钱手段。
- **流式协议**：服务端用 **SSE** 推 `data:` 分片，每片带一小段增量文本（delta）+ 结束原因 `finish_reason`；前端用 `fetch` + `ReadableStream` 读，注意**多字节字符可能被切在半路**（`decode(stream:true)`）和**残行缓冲**。

**B. 提示工程进阶**

- **把话说死的四件套**：角色（你是谁）、任务（做什么）、约束（不许做什么）、输出格式（长什么样）。四样写全，效果提升最明显。
- **few-shot**：给 1~5 个范例最划算；**范例的顺序和格式会影响结果**，范例要和你想要的输出**长一模一样**。
- **CoT 思维链**：「先分析再回答」或直接给带推理的范例，复杂推理题提升明显。
- **Self-Consistency**：同一问题采样多次，取多数答案，换准确率换成本。
- **Reflexion / 自我反思**：让模型先输出，再自己检查、修正一版。
- **结构化输出**：优先用 **JSON mode / Function Calling / JSON Schema**，而不是「靠提示词求它输出 JSON」；拿到结果**一定要校验，失败就带着报错重试一次**（parse → validate → repair）。
- **提示注入（Prompt Injection）**：用户输入里塞「忽略以上指令」就能越狱。**直接注入**来自用户，**间接注入**藏在被检索的文档 / 网页里，危害更大。防御：把外部内容当**数据**而不是指令、用分隔符包裹、最小权限、输出侧过滤。

**C. 上下文工程（Context Engineering）**

- **窗口大 ≠ 效果好**：模型对**中间位置**的内容注意力弱（lost-in-the-middle），塞太满还会「上下文腐化」（context rot）导致变笨。
- **原则：只放必要证据**。宁可用检索挑出 3~5 段最相关的，也不要一股脑塞 10 万字。
- **压缩手段**：历史摘要（滚动总结）、只保留最近 N 轮 + 关键事实、把长文抽成结构化要点。
- **长上下文 vs RAG 怎么选**：一次性读完能装下 + 内容固定 → 直接塞；**资料量大、要更新、要溯源 → RAG**。实践中常**两者结合**（RAG 定位 + 长上下文精读）。

**D. RAG 进阶**

- **检索**：**混合检索**（BM25 关键词 + 向量语义）通常比纯向量稳；多路召回再融合；用元数据（时间 / 学生 / 知识点）做过滤。
- **查询侧优化**：用户问题太短就**改写扩写**；多查询（一个问句拆成几条去查）；**HyDE**（先让模型编一个假答案再拿它去检索）；多轮对话要做**指代消解**（把「他」还原成具体的人）。
- **切分**：定长（简单但会切断语义）、递归（按段落 / 标题层级）、语义切分；**父子块**（小块检索、大块喂给模型）、**句子窗口**（命中一句扩到前后几句）。
- **重排（Rerank）**：先粗召回 20~50 条，再用 cross-encoder 精排出 Top 3~5，**性价比很高的一步**。
- **进阶形态**：GraphRAG（把知识建成图谱，适合「跨文档关联、多跳」问题）、多模态 RAG（图文混检）。
- **RAG 评估**（记住 RAGAS 四个指标）：**忠实度**（答的是不是都来自材料）、**答案相关性**、**上下文精度**、**上下文召回**。分开评「检索」和「生成」，才能定位是哪一环坏了。

**E. Agent 进阶**

- **四种常见编排**：ReAct（边想边做）、Plan-and-Execute（先列计划再执行）、Reflection（做失败自我修正）、Orchestrator-Worker（主智能体拆活给子智能体）。
- **工具设计原则**：**少而精**（别一次塞 30 个工具，模型会选错）、名字自解释、参数简单扁平、**错误信息要写成给人看的话**（模型是读了错误才知道怎么改）、写操作要**幂等**。
- **循环控制**：设 `max_steps` 与**预算上限**、检测死循环、关键操作加 **Human-in-the-loop** 确认。
- **记忆分层**：短期（当前对话）、工作记忆（本次任务的中间结果）、长期（向量库 / 结构化画像）。记忆要解决**写什么、何时写、冲突了听谁的**。
- **生态**：**MCP** 是工具接入的标准协议；Computer Use（让模型操作浏览器 / 桌面）是新方向但还脆弱。
- **大白话**：Agent 的坑不在「会不会调工具」，而在**它调错了你不一定知道**——所以可观测性与步数 / 预算护栏是刚需。

**F. 微调与对齐**

- **先问自己三遍**：Prompt 能不能解决？RAG 够不够？——**都不行才微调**。
- **微调的症状匹配**：要改**风格 / 格式 / 领域术语 / 固定工序** → SFT；要调**偏好与语气** → DPO / 偏好对齐；要灌**知识** → 优先 RAG（微调灌知识又贵又难更新）。
- **SFT 数据**：格式 `instruction / input / output`；**质量 > 数量**（几百上千条高质量就能出效果）、去重、覆盖边界情况、配比均衡。
- **LoRA / QLoRA 超参直觉**：`rank`（低秩维度，8~64 常用）、`alpha`（缩放，常取 rank 的 1~2 倍）、`target_modules`（挂到哪些层）、学习率比全量微调大一个量级。
- **要防**：灾难性遗忘（微调后通用能力下降 → 混入通用数据、只训少量步数）；**微调完一定要做「能力回退检查」**。
- **其他手段**：继续预训练（灌领域语料）、蒸馏（大模型教小模型）。

**G. 推理与性能（自己部署才需要）**

- **KV Cache**：把历史 token 的中间结果缓存下来，生成新 token 时不用重算 —— **自回归加速的根本**。
- **PagedAttention / 连续批处理**：把显存按页管理 + 动态拼批，vLLM 靠这两个把吞吐拉高。
- **投机解码**：小模型先猜、大模型一次校验，等于「批量改卷」。
- **量化**：INT8 / INT4 / GPTQ / AWQ / GGUF，**用一点精度换显存和速度**，部署侧的常规操作。
- **并行**：TP（张量并行）、PP（流水线并行）、EP（专家并行，MoE 用）。
- **引擎选型**：vLLM / TGI（吞吐优先）、Ollama（本地跑着玩）、TensorRT-LLM（极致性能）。

**H. 评测、安全与上线**

- **评测怎么做**：建**离线评测集**（覆盖正常 + 边界 + 恶意）→ 跑指标 → **LLM-as-judge 打分（但要知道它有偏好偏差，比如偏爱长答案）** → 线上 A/B → 把它变成**回归测试**，每次改 Prompt / 换模型都跑一遍。
- **防幻觉的手段**：RAG 提供依据 + **强制引用出处** + 低温度 + 结构化输出 + 关键结论用工具 / 规则二次校验 + 答不了就说「不知道」。
- **安全清单**：提示注入防护、越狱检测、**PII 脱敏**、权限最小化（工具只给必要权限）、输出内容过滤、操作审计日志。
- **上线必备**：
  - **超时与重试**：首包超时单独设；重试要**指数退避 + 幂等键**（别把「已扣款」重试成两次）；
  - **限流与配额**：按用户 / 按 key 限速，防被打爆或烧钱；
  - **降级**：主模型挂了切备用模型，再不行走规则 / 友好提示；
  - **灰度与版本化**：Prompt 也要版本管理，可回滚。
- **可观测性**：全链路 trace（一次请求 → 多次模型调用 → 工具调用）、**token / 延迟 / 成本三个指标必采**。
- **缓存**：精确缓存（同问题同参数）+ **语义缓存**（相似问题直接命中，省 token 又提速）。
- **模型路由**：简单问题走小模型 / 规则，难题才升级大模型，**成本和延迟都能砍一半**。

**I. 面试高频问法（可以直接背这六组）**

| 问题 | 答题骨架 |
|---|---|
| 怎么防幻觉？ | RAG 给依据 → 强制引用 → 低温度 → 结构化输出 → 工具校验 → 允许说「不知道」 |
| 长文档怎么处理？ | 切分 → 检索召回 → 重排 → 只放必要证据 → 需要时叠加摘要与长上下文精读 |

| 怎么评测上线效果？ | 离线评测集 + LLM-as-judge + 线上 A/B + 回归测试 + 人工抽检 |

### 附录 9、几条避坑建议

- **别只收藏不跑代码**：收藏夹里的教程一文不值，跑通的那个才是你的。
- **别一上来死磕数学到放弃**：边做边补，卡住了再回头补对应那块公式。
- **别只做应用不懂原理，也别只啃原理不落地**：前者容易被问穿，后者做不出东西。
- **从一个端到端小项目开始**：比如给自己的备课排课系统加一个「能读知识库的 AI 助教」，比刷十个教程都管用。
- **复现 > 教程，写笔记 > 只看**：能用大白话讲给别人听，才算真懂。
- **没显卡别硬撑**：先用 Colab / Kaggle 免费额度或按需云租卡，跑通再说。
