# 前后端接口联调协作（frontend-api-sync）

后端与前端是**两个独立 git 仓**（本仓是后端），本 skill 负责接口契约在两端之间**同步、核对、排查**。

| 本 skill 管 | 本 skill 不管 |
| --- | --- |
| 接口契约（URL / Method / 出入参 / 返回语义）的两端同步 | 前端页面 UI、交互、组件库用法（归前端自己的规范与 skill） |
| 契约一致性核对、联调报错归属判定 | 后端业务实现本身（归 `energy-sdd-workflow` + `tiansu-ddd`） |
| 前端类型/请求/mock 层随契约改动 | 前端工程搭建、依赖升级、构建发布 |

> **本 skill 最重要的一条**：**未经用户同意，不改前端任何一行代码。** 探查（读、grep）不受限，写必须过第五节的征询门。

## 一、首次配置：前端工程路径（P0，必须先做）

| 项 | 值 |
| --- | --- |
| 配置文件 | **后端仓根** `.frontend-project`（与 `.scaffold-sync` 同惯例，**不进 git**） |
| 内容格式 | 一行一个前端工程：`<路径>`，或 `别名 <路径>`；**第一行 = 默认工程**。空行与 `#` 注释忽略 |
| 示例 | `energy-vpp-web D:/workspace/company/virtual-power-plant/energy-vpp-web` |

**第 1 次使用（文件不存在）**：

1. **先探测候选**，不要凭空问：扫描后端仓的**同级目录**，挑出「含 `package.json` + `src/` 」的目录作为候选。
2. 用 `AskUserQuestion` 让用户确认：候选目录（通常 1-3 个）各作一个选项，用户也可用 Other 直接给绝对路径。
3. **校验**：路径存在、含 `package.json`；读 `package.json` 的 `scripts`，记录可用的验证命令（见第七节）。
4. 写入 `.frontend-project`，并向用户**回显确认**（写了哪个路径、识别到什么验证命令）。
5. 顺手确认 `.gitignore` 是否已忽略 `.frontend-project`，没有则**先问用户**再加。

**后续使用**：直接读配置，**不再重复询问**。

**失效处理**：路径不存在 / 已挪走 → **重新走上面的询问流程**并更新文件，不要猜、不要降级成"跳过前端同步"。

**硬性**：

- 禁止把本地路径写进 `AGENTS.md` / `CLAUDE.md` 等**入 git 的规范文件**（路径是本地环境信息，写进去会互相覆盖）。
- 禁止仅凭"同级目录看起来像前端"就直接改代码——必须先经用户确认。
- 多个前端工程时，先按第一行（默认）处理；若目标模块只在另一工程里出现，**明确告知用户你改的是哪个工程**。

## 二、什么情况触发本 skill

| 侧 | 触发事件 |
| --- | --- |
| 后端侧（**编码前**） | 设计阶段已定契约口径、要改**既有**接口、或一处改动会让前端多个页面/多个接口一起动 → 走第三节「变更预告模式」 |
| 后端侧（编码后） | 新增/删除/改名接口；URL 或 Method 变化；请求或响应 DTO 字段增删改（名/类型/必填）；返回**语义**变化（分页↔全量、覆盖式、排序、空值口径）；枚举取值变化；错误提示文案变化 |
| 前端侧 | 联调报错（字段取不到、类型不对、404）；前端问"这个接口现在是什么契约"；前端说"后端改了没告诉我" |
| 用户显式 | "同步前端" / "前端要跟着改吗" / "帮我改前端" / "联调一下这个接口" |

## 三、变更预告模式（后端编码之前）

**目的**：在**后端动手改契约之前**，把"打算怎么改"先给前端过一遍。返工的最大来源不是"改了没同步"，而是"写完才说"——字段命名、接口粒度、返回语义一旦落进代码再改，两端都要返工；在设计阶段改口径几乎零成本。

| 项 | 说明 |
| --- | --- |
| 何时启用 | 设计阶段（`docs/{模块}/design.md` 接口表刚产出）、要改**既有**接口、一处改动会让前端多个页面动、用户说"这改动可能要前端配合" |
| 真相来源 | 此时 DTO 尚未落地，真相是 **design.md 的接口表 + 本次需求的字段口径**；必须标注「草案，可能变」，不能假装已定 |
| 何时不用 | 纯新增接口、只加可选字段、纯后端内部重构（契约不变）→ 直接编码，改完按同步流程报一次即可 |

**产出「契约预告单」（比变更清单更早、更粗、可商量）**：

| 接口 | 计划变化 | 前端预计要改点 | 兼容性 | 是否已定 |
| --- | --- | --- | --- | --- |
| `POST /sites/xxx` | 弹框右侧改调新接口 `/sites/deviceSelected`（全量不分页） | `apis/site/index.ts` 换 url；右侧列表改数据源 | 破坏 | 草案 |

**问什么**（此阶段**不是**问"要不要改前端"——还没得改）：

1. **口径能不能接受**：字段命名、类型、必填与否、返回语义（分页 / 全量 / 覆盖式）。
2. **怎么调更顺手**：需不需要额外回显字段、批量还是单条、能不能合并或拆分接口——**这是提出来的最佳时机**，代码落地后就不好动了。
3. **要不要 mock 先行**：后端未就绪时，前端是否先按草案造 mock 并行开发。

**规则**：

- 一次一批：同一需求的接口合并成一张预告单，不逐个问。
- 只预告**破坏项与语义项**；纯新增可选字段不必预告。
- **预告 ≠ 授权改前端**：预告只是提前对齐口径，真正改前端仍须过第五节的征询门。
- 预告结论**回写 `design.md` 的接口表**，别停在对话里；编码完成后按「契约变更清单 → 征询门 → 前端同步」正常走一遍（已预告的项不再重复问口径，只确认是否动手改）。

## 四、先产出「契约变更清单」（改任何代码之前）

**真相来源 = 后端 Controller + DTO 源码**（`*-api` 模块的 `client/**/XxxRequestDTO`、`XxxResponseDTO`、`adapter/web/**/XxxController`）。

> 文档（`docs/**/design.md`、接口文档）是**参考**、可能滞后；以 DTO 源码为准，改完再回写文档。

清单（每次同步先产出这张表，给用户看）：

| 接口 | 变化类型 | 后端新契约 | 前端需改点（文件 + 行为） | 兼容性 |
| --- | --- | --- | --- | --- |
| `POST /sites/deviceSelected` | 新增接口 | body `{siteId, campusIds}` → `[{deviceId,deviceCode,deviceName,deviceType,deviceTypeName,ratedPower,ratedPowerUnit}]` | 新增 `apis/site/index.ts` 请求函数 + `index.api.ts` 类型；弹框右侧由 `devicePage` 改调本接口 | 破坏（旧用法数据不全） |

**兼容性判定**：

- **兼容**（前端可不动）：新增**可选**字段、新增接口、错误文案微调。
- **破坏**（前端必须跟）：删字段、改字段名、改类型、新增强制必填、分页↔全量、返回结构层级变化、URL 变化、**同名字段语义变化**。
- 破坏项**必须**在清单里显式标出，不能混在兼容项里一句带过。

## 五、征询门（本 skill 的核心动作）

**默认动作 = 报告 + 询问，不擅自改前端。**

1. **一批一次问**：同一批改动（同一次后端迭代 / 同一个需求）**合并成一次** `AskUserQuestion`，不要把 5 个接口问 5 遍。
2. 选项固定三档：

| 选项 | 含义 |
| --- | --- |
| **① 现在就同步前端（推荐）** | 按第六节的默认档位改，改到前端类型检查通过为止 |
| **② 只出清单，我自己改** | 只交付第四节的清单（含文件路径与具体改法），不碰前端代码 |
| **③ 暂不处理** | 记为待办，明确告知"前端当前会编译不过/运行期取不到值"的风险 |

3. **问之前必须先给清单**：用户要看到"哪个接口、变成什么、前端哪个文件要动"才能决定。只问"要不要改前端"是无效询问。
4. **不重复问**：
   - 用户本次任务里已明确说"同时改前端""前后端一起改" → 视为已授权，直接进第六节，改完再报告。
   - 用户选了 ①，该批改动内的后续小修（同批接口的编译错误修复）**不再问**。
   - 出了这批改动范围（新接口、新页面）→ 重新问。
5. 用户选 ② / ③ 时，**不得**顺手改前端"反正就一行"。

## 六、前端同步执行（获准后）

### 6.1 先读前端自己的规范

改前端前**先加载前端工程的规范**，按下面的顺序读：

| 读什么 | 在哪 | 用来定什么 |
| --- | --- | --- |
| 工程规范 | 前端工程 `AGENTS.md` / `CLAUDE.md` | 强制前置依赖、验证命令、工作流门禁 |
| 编码规范 | `.ai-knowledge/FRONTEND_CODING_STANDARDS.md`（**最高优先级**） | 命名、缩进、注释、样式、字号 token |
| **组件使用说明** | **组件库 skill：`tiansupowers` 插件里的 `ts-components`，或用 `tsweb setup --client <client> --mode skill` 部署进工程后的 `ts-web`**（同一份内容的两种装法，包装 `tsweb` CLI 的离线元数据） | **组件的 Props / Slots / Events / Demo 示例 / 代码生成规范** |
| 流程门禁 | `tiansupowers` 的流程类 skill（`ts-requirement` / `ts-design` / `ts-design-review` / `ts-implement` / `ts-code-review` 等） | 需求 → 设计 → 评审 → 编码 → 审查 |

**前端规范优先于本 skill 的描述**——本 skill 只负责"改什么"，"怎么写"听前端的。

**涉及组件时必须查真实文档，禁止凭记忆编造**：按 `ts-components` skill 的流程查——`tsweb info <组件名> --format json` 取 Props/Slots/Events，`tsweb demo <组件名> --format json` 取官方示例，必要时 `tsweb doc <组件名> --format json` 取全量 API。`.ai-knowledge` 里的编码规范只管"怎么写"、不含组件 API，别指望从那里拿组件用法。**文档只描述 API、不描述运行期行为时**（例如 `v-model` 与 `data` 的联动关系），回退去读组件源码把语义定死，不要凭印象推断。

### 6.2 落点定位（通用模型 → 实际工程自适应）

先按下面的**通用模型**找位置；找不到时（工程结构不同）**grep 现有接口路径或字段名**定位，再按实际结构落，不要硬套目录名。

| 层 | 典型落点（Vue3 + TS 脚手架实测） | 改什么 |
| --- | --- | --- |
| ① 类型 | `src/apis/{模块}/index.api.ts` | 出入参 interface 的字段、类型、可选性、注释 |
| ② 请求 | `src/apis/{模块}/index.ts` | 请求函数：`url`、`method`、`data`、返回泛型 |
| ③ Mock | `src/mock/modules/{模块}.ts` | 同路径 mock 的字段与结构（本地联调的数据源，**不同步 = 联调假象**） |
| ④ 消费方 | `src/views/**`、`src/composables/**`、`src/hooks/**` | 字段引用、默认值、空值兜底、展示分支 |
| ⑤ 全局类型 | `src/apis/types.ts` | 公共包装类型（`CommonResponseType`、分页结构），**只在包装契约变时动** |

### 6.3 默认档位（用户已确认）：分级改，改到能编译为止

1. 先改 **① 类型 → ② 请求 → ③ Mock**。
2. 若**只改这三层就能通过类型检查** → 到此为止，报告并停。
3. 若字段被**删除 / 改名 / 类型变更**，消费方必然引用不到 → **继续改 ④ 消费方**（否则前端编译不过或运行期取不到值）。
4. **换接口 ≠ 换 URL**：新旧接口的**数据源口径**可能不同（分页 ↔ 全量、全集 ↔ 已排除、单表 ↔ 关联拼接），消费方喂给组件/循环的那份数据集可能要**整个重装**，不能只替换 `url` 字符串。动手前先确认目标组件对入参集合的**运行期语义**（例：穿梭框右区是拿 `data` 过滤 `v-model`，键在 `v-model` 里但不在 `data` 里就两边都渲染不出来；右区数据源已排除被占用项时，必须与已选项求并集回填 `data`）——否则会留下"接口调通了、界面空着"的隐性破坏，类型检查也发现不了。

    > 判断信号：新接口的**返回语义**与旧接口不一致（见第四节兼容性判定里的"分页↔全量"），或旧调用是为绕开某个限制而写的（如"一次取全、不做分页交互"）→ 消费方数据源基本上要重装。
5. 到 ④ 为止。**不改 UI 结构、不改交互、不改样式、不重构无关代码**；确实需要页面行为变更（如换接口导致交互要改）→ **停下来问用户**。

### 6.4 前端硬性约束

- 不 `npm install` / 不升级依赖 / 不跑 `build`、`dev`（除非用户明确要求）。
- 不 `git commit`、不 `git push`（前端仓尤其）。
- 不改与本次契约无关的文件；不顺手格式化整个文件。
- 前端仓的本地改动若已存在（`git status` 有脏文件）→ **先看一眼、别覆盖用户正在改的东西**。

## 七、验证闭环

| 侧 | 步骤 | 命令 / 方式 |
| --- | --- | --- |
| 后端 | 编译 + 单测 | 按 `energy-sdd-workflow`：`mvn -o clean compile -q` → `mvn test -q` |
| 后端 | API 实测 | 起服务调被改接口（环境不可达时**明确标注未验证**，不谎报） |
| 前端 | **类型检查（必须）** | 取前端 `package.json` scripts，通常是 `npm run ts-check`（`vue-tsc --noEmit`） |
| 前端 | lint（改动文件） | 通常是 `npm run lint:html -- <改动文件>`；无该脚本则跳过并说明 |
| 前端 | 目视联调 | **交给用户**（起 dev 服务 + 走页面），AI 不代替用户验收界面 |

完成后报告：**改了什么（两端文件清单）、验证通过什么、什么没验证**。三样都要，缺"没验证的"就是谎报。

## 八、反向流程：前端联调发现问题

1. **先判归属**，不要默认是后端错：对照 `*-api` 的 DTO + Controller 源码，核对字段名/类型/包装/是否为空。
2. **是后端问题**（契约与文档/前端预期不符、历史 bug）→ 告知用户，按 `energy-sdd-workflow` 改后端（含单测与文档同步），改完回到第四节重新产出变更清单。
3. **不是后端问题**（前端取错字段、类型断言错、mock 没更新、URL 前缀拼错）→ 给出**前端文件 + 原因 + 建议改法**，不擅自改后端。
4. **禁止**为了让前端跑通而擅自给后端接口加冗余字段、放宽校验、改返回语义——契约不能迁就调用方。确实需要变更 → 走正常的契约变更 + 征询门。

## 九、契约一致性红线（联调自查清单）

每次同步/排查逐条过，这是"绝大部分联调问题"的根因表：

| # | 红线 | 说明 |
| --- | --- | --- |
| 1 | **URL 与前缀** | 本地前端请求**相对路径**（如 `/sites/page`），由 vite proxy 转发；部署环境 nginx 会多拼 `/energy/{服务}-api`。**前端不得硬编码服务前缀**，后端代码也不感知该前缀 |
| 2 | **统一包装** | `{ errcode, errmsg, data }`；**`errcode === '200'` 为成功**（`Result.success` → `"200"`；`Result.unifiedSuccess` 才是 `"0"`，本仓未用）；`ResultHandler` 自动包装，后端**不手动包 Result**——前端解包方式不能改 |
| 3 | **分页结构** | 入参 `pageNum/pageSize/orders`，返回 `CommonPage{pageNum,pageSize,total,pages,list}`；字段名与前端对齐，**不可改成 `records`/`items`** |
| 4 | **ID 精度** | 后端 ID 是 **53bit / 16 位** 雪花（JS 安全范围内）。前端若把 ID 当 `number` 传递需确认未被 `JSON.parse` 截断；**超过 2^53 的值必须走字符串** |
| 5 | **时间格式** | 统一 `yyyy-MM-dd HH:mm:ss` 字符串（或 DTO 显式约定）；前端不做隐式 `new Date(数字)` |
| 6 | **枚举取值** | 后端**业务状态**（如站点 运行中/检修/已退役）是 Java 枚举；**选项集**走字典表。前端联合字面量必须与后端取值逐一对齐（含 `'1'/'2'/'3'` 这类字符串码） |
| 7 | **字段命名** | 一律 camelCase，**逐字一致**；警惕近似陷阱（`siteName` vs `name`、`deviceCount` vs `deviceNum`、`aggregationTypes` vs `aggregationType`、`totalAggCapacity` vs `ratedPowerTotal`、`ratedPower` vs `installedCapacity`） |
| 8 | **空值口径** | 明确 null / 空数组 / 空字符串 / 不返回的语义；后端降级时**返回空字段而非报错**（如外部查询失败的实时字段），前端必须容错 |
| 9 | **必填与校验文案** | 后端 `@NotNull`/`@Valid` 拦下的字段，前端必须传；失败文案来自 `errmsg`，**前端直接展示、不自行造错误码**（后端只有文案、不定义业务错误码） |
| 10 | **语义陷阱** | 接口的**行为语义**要和前端理解一致：覆盖式提交（提交集 = 最终结果集，前端必须交全量、不能交增量）、排序口径（如表格一律 `update_time` 降序）、幂等性、批量接口的部分失败行为 |
| 11 | **多消费方** | 一个接口可能被多个页面/组件消费。改契约前**先 grep 出全部消费方**，别只改一处（后端加字段安全，删/改字段必须列全） |
| 12 | **Feign 内部调用** | 内部 Feign 调用带 `ts-request` 头、**跳过 Result 包装**（返回原始对象）。前后端联调口径与内部调用不同，别混 |

## 十、交付与记录

- **跨端变更清单**（第四节的表 + 前端实际改动文件 + 验证结果）作为本次同步的交付物，给用户 review。
- **后端文档同步**：接口变化须回写 `docs/{模块}/design.md` 的接口表 / 改动点，以及 `docs/{模块}.md`（如涉及）；接口文档目录若存在（`docs/api/{模块}.md`）一并对齐。
- **接口归属跨模块迁移**时按 `energy-sdd-workflow` 第六节「多文档联动」处理三处文档。
- **不自动提交**：两端都由用户 review 后各自提交（后端提交信息按根规范的 `type: 描述` 约定）。

## 硬性约束

- **未经用户同意不改前端**；探查可以，写不行（第五节的征询门是本 skill 的立身之本）
- 改前端前先读**前端自己的规范**，写法听前端的，本 skill 只管改什么
- 契约真相以 **DTO + Controller 源码**为准，不以文档/口头为准；文档只能事后同步
- 不擅自改后端契约去迁就前端；不为了让前端跑通而放宽后端校验
- 不带"未验证"的结论交付：验证不了的必须写明未验证
- 不装依赖、不升级、不跑构建、不自动提交
