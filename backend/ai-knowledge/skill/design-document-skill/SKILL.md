# 技术设计文档（按 PRD 拆分：设计文档 + 版本级接口文档 + 版本级表文档）

## 1. 输出产物

### 1.1 产物路径、目录说明

> 设计阶段在 `doc-repo/design/{版本}/` 产出（**`{版本}` 目录名即版本号，版本号必须通过与用户对话确认后使用，禁止自行推断**）：
>
> ```
> doc-repo/design/{版本}/
> ├── design-{PRD标题1}.md                  ← 1 份 PRD = 1 份设计文档
> ├── design-{PRD标题2}.md                  ← 多份 PRD 就多份设计
> ├── 接口设计文档.md                        ← 版本级 1 份，本版本全部设计共用
> └── 数据库设计文档.md                      ← 版本级 1 份，本版本全部设计共用
> ```

**各产物详情**：

**（1）`design-{PRD标题}.md`**（**文件名不带需求编码**）

- **份数**：每份 PRD 一份（多份 PRD 就多份设计文档，各自独立评审）。
- **角色**：**设计文档**——本 PRD 的唯一主文档 + 评审门。
- **内容**：**1 需求清单**（表格式：序号 / 需求编码 / 需求描述）；**2 开发设计**（每条需求一个独立小节，小节内固定 2.N.1 功能说明 / 2.N.2 接口清单 / 2.N.3 表结构设计（表名 + 用途 + 新增/改动）/ 2.N.4 外部依赖 / 2.N.5 历史数据处理，末尾追加全局枚举值说明）；**3 附录**（外部文件目录，API 设计、数据库设计可点击跳转）。
- **生成参照（强制）**：产出本设计文档时**必须参照示例 [`examples/design-设备版本管理.md`](./examples/design-设备版本管理.md)**，照抄其**章节结构、内容粒度与写法**（示例 = 唯一的格式基准）。

**（2）`接口设计文档.md`**

- **份数**：版本级 1 份（本版本全部设计共用）。
- **角色**：**接口文档**。
- **内容**：**1 接口设计**（正文**一个接口一个小节**，按全局接口编码 `api-X` 连续排列，**不按需求 / 模块分组**）→ 每个接口一小节 `### 1.N api-X {接口名}`（`1.N` = 本档内顺序号，从 `1.1` 起自增），节内固定五段：**（1）接口路径 /（2）请求参数 /（3）返回数据 /（4）失败提示 /（5）实现说明（调用场景 + 实现方式）**，其中请求参数与返回数据各含**字段明细（缩进树，含嵌套层级）+ JSON 示例**。
- **生成参照（强制）**：产出本接口文档时**必须参照示例 [`examples/接口设计文档.md`](./examples/接口设计文档.md)**，照抄其**章节结构、内容粒度与写法**（示例 = 唯一的格式基准）。

**（3）`数据库设计文档.md`**

- **份数**：版本级 1 份（本版本全部设计共用）。
- **角色**：**数据库表设计文档**。
- **内容**：**1 数据库表设计**；**子章节标题即表名**（固定 `### 1.N `{表名}``，N 按表出现顺序递增，**不按 PRD / 需求分组**），每张表固定三段：**（1）表名 /（2）字段表 /（3）sql脚本（新建表 `CREATE TABLE IF NOT EXISTS`，存量表 `ALTER`，新增字段带 `ADD COLUMN IF NOT EXISTS`）**；表以表名定位、跨文档引用一律写表名；DDL 脚本归用户维护。
- **生成参照（强制）**：产出本表设计文档时**必须参照示例 [`examples/数据库设计文档.md`](./examples/数据库设计文档.md)**，照抄其**章节结构、内容粒度与写法**（示例 = 唯一的格式基准）。

**对应关系（严格）**：

1. **一份 PRD = 一份设计文档**：设计严格对应 PRD，**不合并、不跨 PRD 写**。一个版本下 PRD 可能是 1 份、也可能多份，多份 PRD 就产出多份设计文档（各自独立评审）。
2. **一份 PRD 内可有多个需求**：PRD 里识别出几条需求，该设计文档第 2 章就有几个需求小节（2.1 ~ 2.N），**几对几、不增不减**，第 1 章需求清单与本处**序号一一对应**。
3. **需求编码必须体现在设计文档**：**需求编码 = PRD 的需求单编码，一份 PRD 只有一个**（如 `IEMS-Scrum-85851`）——同一 PRD 下的各需求**共用同一编码**，设计文档需在**文档头表 + 第 1 章需求清单 + 第 2 章每个需求小节头**三处体现，且**三处写同一个值**；区分同一 PRD 内的不同需求靠**序号与需求标题**，不靠需求编码。PRD 未提供编码时三处统一写「待补」。
4. **接口文档与数据库表文档独立于设计**：`接口设计文档.md` / `数据库设计文档.md` **是版本级的、各只有 1 份**，被本版本**全部设计共用**；`接口设计文档.md` 正文**一个接口一个小节**（`### 1.N api-X {接口名}`，`1.N` = 本档内顺序号，按全局接口编码 `api-X` 连续排列，**不按需求 / 模块分组**），`数据库设计文档.md` 正文**按表分节**（子章节标题即表名，与设计文档 2.N.3 表清单对齐）。

**评审门**：评审人**逐份评审** `design-{PRD标题}.md`（`接口设计文档.md` / `数据库设计文档.md` 是主文档的配套明细，按文中指引跳转抽查，不单独评审）；评审不通过不得进入任务拆解。
**真相源与同步**：每份设计文档是**本 PRD 方案**的唯一真相源；`接口设计文档.md` / `数据库设计文档.md` 只做明细展开，**不得引入设计文档里没有的新决策**。任何修改**先改设计文档**，再同步到明细文件的**对应设计的对应小节**（按接口序号 `api-N` / 表名对齐）。

### 1.2 三份文件的边界（什么写在哪）

| 内容 | 归属 |
| --- | --- |
| 需求编码（PRD）、需求清单（**与产品设计文档中的需求清单逐条映射**） | 设计文档：文档头表 + 第 1 章「需求清单」+ 第 2 章各需求小节头 |
| 功能意图、范围外、核心逻辑、关键约束 | 设计文档 2.N.1 功能说明 |
| 接口清单（序号 / 接口编码（链接直达 `接口设计文档.md` 对应接口小节） / 接口路由 / 接口说明） | 设计文档 2.N.2 接口清单 |
| 逐接口「调用场景 + 实现方式」（工程落地路径） | `接口设计文档.md` 各接口小节（`api-X` 小节） |
| 接口请求参数 / 返回数据**字段明细（含嵌套）** + JSON 示例 + 失败提示 | `接口设计文档.md` |
| 表清单与用途（索引，不写字段） | 设计文档 2.N.3 表结构设计 |
| 表的完整字段 / 类型 / 必填 / 索引 + 建表、ALTER 语句 | `数据库设计文档.md` |
| 对外接口诉求（Feign）与前置依赖、历史数据处理 | 设计文档（挂在所属需求小节下；**不含**中间件与前端页面依赖） |
| 状态机 / 枚举 / 字典码值（全局） | 设计文档「2 开发设计」末节「枚举值说明（全局）」 |
| 外部文件目录（配套文件与跳转链接） | 设计文档第 3 章「附录」 |

> **需求清单映射（强制）**：设计文档第 1 章「需求清单」（序号 / 需求编码（PRD） / 需求描述）**逐条映射自产品设计文档中的需求清单**——**同序、同编码、同数量**，不新增、不合并、不改写描述口径；产品设计文档未给需求编码时写「待补」。`接口设计文档.md` 正文**一个接口一个小节**（按全局接口编码 `api-X` 连续排列，**不按需求 / 模块分组**）；`数据库设计文档.md` 正文**按表分节**，表名与设计文档 2.N.3 表清单一致。

**接口序号（强制）**：

- 全部接口在 `接口设计文档.md` 中按**全局连续序号**编号，从 `api-1` 起、跨设计跨模块一路向下（本版本 `api-1` ~ `api-N`，后续新增 PRD 接着往下编），**全局唯一、不复用、不按模块重新起编**。
- 接口小节标题固定写法：`### 1.N api-X {接口名}`——**章节号 `1.N`（本档内顺序号，从 `1.1` 起自增）与接口编码 `api-X` 前置到标题开头**，**标题本身即锚点**；不按需求 / 模块分组、也不另埋 `<a id>`。
- **任何文档（设计文档 / `数据库设计文档.md` / 规格 / 其他设计）引用接口一律写接口编码**，如「见 `api-1`」「复用 `api-5`」；**禁止用章节名或章节号引用接口**（如「见 1.1.2」「见 §1.1」——章节号不是接口的定位标识，接口编码才是）。
- 序号一经分配不再变更；接口删除后其序号空置，**不回收给新接口**。

- **不写**：类与包设计、方法签名、代码骨架、实现顺序、AI 编码交接包——这些由开发时按 `tiansu-ddd` / `tiansu-java-standards` 等编码规范逐步落地，不进设计文档。
- **不重复**：统一返回信封、传参方式（header / body）、分页命名、字段命名等全项目约定不在设计文档重复，见工作区规范。
- **不设「通用约定」章节**：文档只写本功能特有内容。
- **不跨 PRD 汇总**：接口 / 表只在**自己所属设计（PRD）**的明细下写；`接口设计文档.md` / `数据库设计文档.md` 也不得把某份设计的接口 / 表挪到别份设计名下。

## 2. 开发设计文档

> **生成参照（强制）**：产出开发设计文档时**必须参照示例 [`examples/design-设备版本管理.md`](./examples/design-设备版本管理.md)** 生成，**照抄其章节结构、内容粒度与写法**（示例 = 唯一的格式基准）。

```
# {PRD 标题} 设计文档
{文档头表：需求编码 / 需求标题 / PRD 来源 / 关联规格 / 版本日期 / 状态 / 版本级配套文档}

1. 需求清单              ← 索引章，表格式：序号 / 需求编码（PRD） / 需求描述
2. 开发设计
   2.1 {需求一}          ← 小节头标注本 PRD 的需求编码
       2.1.1 功能说明
       2.1.2 接口清单
       2.1.3 表结构设计
       2.1.4 外部依赖
       2.1.5 历史数据处理
   2.2 {需求二}
       ...
   2.{N+1} 枚举值说明（全局）
3. 附录
   3.1 外部文件目录      ← API 设计 / 数据库设计可点击跳转
```

- **第 1 章「需求清单」**：从 PRD 识别出的需求清单，**表格式**，列固定为 **序号 / 需求编码（PRD） / 需求描述**三列；序号从 1 连续递增，且**与第 2 章小节号一一对应**（第 N 条需求 = 2.N 小节，供评审人从需求单直达设计小节）。**需求编码从 PRD 读取、一份 PRD 只有一个**（格式如 `IEMS-Scrum-85851`），**本表各行写同一个值**，PRD 未提供时写「待补」。本章只做索引：**不写需求正文、不写验收标准**。
- **第 2 章「开发设计」**：**每条需求一个独立小节**（小节号 2.N，与第 1 章序号对齐），**小节头必须标注本 PRD 的需求编码**；小节内五个子节**标题固定、不增不减、顺序不变**，不涉及的小节写「无」，保证结构一致、可扫读。一条需求 = 一个可评审、可独立验收的最小闭环。
- 需求划分与编号一旦确定，**设计文档 / `接口设计文档.md` / `数据库设计文档.md` 共用同一套**：设计文档小节 2.N.2 接口清单的「**接口编码**」列直接填 `接口设计文档.md` 的全局序号（`api-N`），与 `接口设计文档.md` 中的接口小节**一一对应、数量一致**；「序号」列只是本表内**自增**的行号（1、2、3…，不含 `api-` 前缀）；设计文档自身不再另起一套「1.2.1」式编号。
- **2.N.2 的「接口编码」列必须是可点击链接**：写成 `[`api-N`](./接口设计文档.md#1N-api-N-{接口名})`（`#` 后为接口小节标题 slug = 标题小写、空格转 `-`、标点剔除；如标题 `### 1.1 api-1 创建导入批次并登记文件清单` → 链接 `#11-api-1-创建导入批次并登记文件清单`），评审人点接口编码即可跳到该接口的请求参数 / 返回数据 / 失败提示 / 实现说明（`接口设计文档.md` 侧标题锚点如何生成见 §3）。**接口清单不展示失败提示**（失败提示只在 `接口设计文档.md` 对应接口小节内写）。
- **枚举值说明（全局）**：作为第 2 章的**最后一节**（编号 2.{需求数 + 1}，**不是一条需求**）追加在全部需求小节之后。
- **第 3 章「附录」**：**外部文件目录**，逐行列出本设计的配套外部文件（`接口设计文档.md`、`数据库设计文档.md`、PRD 来源等）及其内容说明，并给出**可点击跳转的相对链接**（如 `[接口设计文档.md](./接口设计文档.md)`）。

## 3. 接口设计文档

> **生成参照（强制）**：产出接口设计文档时**必须参照示例 [`examples/接口设计文档.md`](./examples/接口设计文档.md)** 生成，**照抄其章节结构、内容粒度与写法**（示例 = 唯一的格式基准）。

````md
# {版本} 接口设计文档

> 本版本**全部设计共用这一份**接口文档。
> **需求归属**：本档接口对应设计文档需求 `IEMS-Scrum-85851`（{PRD 标题一}）等，接口 `api-1` ~ `api-N`。
> **接口分组（强制）**：正文**一个接口一个小节**（`### 1.N api-X {接口名}`，`1.N` = 本档内接口顺序号，从 `1.1` 起自增，与全局接口编码 `api-X` 按序一一对应），**不按需求 / 模块分组**。
> **接口序号约定（强制）**：全部接口在本档内**全局连续编号 `api-1` ~ `api-N`**（从 `api-1` 起，跨设计、跨模块连续，后续新增 PRD 接着往下编）。接口小节标题一律写 `### 1.N api-X {接口名}`——**章节号 + 接口编码前置在标题开头**（`1.N` = 顺序号，`X` = 全局接口编码），**标题本身即锚点，不再另埋 `<a id>`**。设计文档 2.N.2 接口清单等处按 `[`api-X`](./接口设计文档.md#1N-api-X-{接口名})`（`1N` 与 `X` 同值，如标题 `### 1.1 api-1 创建导入批次并登记文件清单` → 链接 `#11-api-1-创建导入批次并登记文件清单`）点击直达本小节，`#` 后为标题 slug（= 标题文字小写、空格转 `-`、标点剔除，章节号里的 `.` 被剔除故 `1.1` → `11`）。**任何文档引用接口一律写接口编码**（如「见 `api-1`」），**禁止用章节名/章节号引用**。
> 每个接口小节固定五段：**（1）接口路径 /（2）请求参数 /（3）返回数据 /（4）失败提示 /（5）实现说明**；其中请求参数与返回数据各含**字段明细（缩进树，含嵌套层级）+ JSON 示例**。业务规则与设计决策仍在设计文档，逐接口的落地路径写在本档。

## 1. 接口设计

### 1.1 api-1 {接口名}

**（1）接口路径**：`POST /xxx`

**（2）请求参数**

```json
{"projectCode": "9112001(广元市中心医院)"}
```

- `projectCode`（String，必填）项目编码

**（3）返回数据**

```json
{"success": true, "data": {"versions": [{"id": 9001, "deviceCount": 1000}]}}
```

- `versions[]`（Array）版本卡列表（按构建时间倒序）
  - `id`（Long）版本 ID
  - `deviceCount`（Integer）设备回路总数

**（4）失败提示**：{errmsg 文案；无则写「无」}

**（5）实现说明**

- **调用场景**：{前端什么时候调它，如「进入页面 / 刷新 / 任务完成后自动切新版本」}
- **实现方式**：{查哪张表、什么条件与排序、怎么聚合；调哪个 Feign；同步还是异步；事务边界、幂等与去重怎么做；关键口径与算法步骤指向哪里}

### 1.2 api-2 {接口名}

（同上：接口路径 → 请求参数 → 返回数据 → 失败提示 → 实现说明）

---

### 1.3 api-3 {接口名}

（同上；后续接口依次为 `api-4`、`api-5`……，**接口小节仍写 `### 1.N api-X {接口名}`，章节号 `1.N` 从 `1.1` 起自增、接口编码不按 PRD / 章节重新起编、不按需求分组**）
````

- **一个接口一个小节**：正文按章节号 `1.N`（从 `1.1` 起自增）+ 全局接口编码 `api-X` 连续排列，**不按需求 / 模块分组**；接口与设计文档需求小节（`2.N`）的归属靠**接口编码**与文首「需求归属」说明对齐，**不另设需求分组标题**。
- **接口小节标题固定**：`### 1.N api-X {接口名}`——**章节号 `1.N`（本档内顺序号，从 `1.1` 起自增）与接口编码前置到标题开头**（`X` = 全局接口编码，不再写 `1.N.M` 式小节号）、**标题本身即锚点**；**每条接口五段齐全、顺序固定、不增不减**，不涉及写「无」但**不删段**。
- **（1）接口路径**只写「`{METHOD} {path}`」一行，**不写**域名、网关前缀、鉴权 header。
- **（2）请求参数 /（3）返回数据 —— 字段明细写法（强制）**：
  - 一律用「**缩进树**」表达层级：`-` 列表表示字段，**缩进 2 空格 = 下一层级**；数组字段名带 `[]`（如 `records[]`），其元素字段写下一层；必填 / 默认值 / 枚举写在括号里，如 `` `projectCode`（String，必填）项目编码 ``；**禁止** `records[].sampleCount`、`a.b.c` 这类把整条路径塞进一个字段名的写法。
  - 请求参数与返回数据**同一种写法**（都用缩进树），字段再多也**不用表格**。
  - 每个接口**必须给一段 JSON 示例**（贴近真实值）；**字段口径以缩进树为准**，JSON 示例不得与树冲突。
- **（4）失败提示**只写**本接口特有的业务提示文案**（如「开始日期不得晚于结束日期」）；无则写「无」；**不写**通用错误码、HTTP 状态码、统一异常处理。
- **（5）实现说明**只写两块：**调用场景**（前端什么时候调它：进入页面 / 刷新 / 任务完成后自动切新版本）+ **实现方式**（查哪张表、什么条件与排序、怎么聚合；调哪个 Feign；同步还是异步；事务边界、幂等与去重怎么做）。**不重复**设计文档 2.N.1 的业务规则，**不写**类名 / 方法签名 / 代码骨架。
- **锚点（强制）**：接口小节**标题即锚点**——标题写 `### 1.N api-X {接口名}`（**章节号与接口编码前置在标题开头**），靠 Markdown 渲染器自动生成的**标题 slug** 定位，**不再另埋 `<a id>`**（自定义 id 会被 GitLab 等渲染器的 HTML 清洗剥离、跨文件也不滚动定位；标题 slug 各渲染器一致、跨文件可真正跳转）。设计文档 2.N.2 接口清单等处按 `[`api-X`](./接口设计文档.md#1X-api-X-{接口名})` 点击直达本小节（`#` 后为标题 slug = 标题文字小写、空格转 `-`、标点剔除，章节号里的 `.` 被剔除，故 `### 1.1 api-1 {接口名}` → 链接 `#11-api-1-{接口名}`）。
- **引用接口一律写接口编码**：任何文档（设计文档 / `数据库设计文档.md` / 规格 / 其他设计）引接口写「见 `api-1`」「复用 `api-5`」，**禁止用章节名或章节号引用**（接口编码才是接口的唯一引用标识）。
- **增量追加规则（版本内新增 PRD / 新增需求时如何续编）**：
  - 接口编码**接着往下编**（`api-N+1` 起）——**不按 PRD / 章节重新起编、不回收删除留下的空号**；本档**不新增分组层**，新接口一律在本档末尾**追加接口小节**。
  - **同一份 PRD** 追加新需求 → **直接在本档末尾追加接口小节**（接口编码仍接着编）；**新 PRD** 同理（只在其设计文档里新开需求小节 `2.N`，本档仍只追加接口小节）；已有接口小节**不重排、不改动**。
  - **示例**：本版本已有 `design-设备版本管理.md`（需求编码 `IEMS-Scrum-1`，识别出 2 条需求，接口 `api-1` ~ `api-4`）。此时新增第二份 PRD「账单导入」（需求编码 `IEMS-Scrum-2`，2 条需求、3 个接口）：新接口从 **`api-5`** 起（`api-5` ~ `api-7`），在本档末尾接着写 `### 1.5 api-5 {接口名}` ……（章节号紧接着 `1.4` 续编），已有 `api-1` ~ `api-4` 小节不动。
- **不写**：业务规则与设计决策（属设计文档 2.N.1）、表字段与 DDL（属 `数据库设计文档.md`）、类与包设计 / 方法签名 / 代码骨架 / 实现顺序、全项目通用约定（统一返回信封、传参方式、分页命名、字段命名）。
- **不引入**：设计文档里没有的新决策——本档只做明细展开，方案有变**先改设计文档**，再同步本档**对应设计的对应接口小节**（按接口序号 `api-N` 对齐）。

## 4. 数据库设计文档

> **生成参照（强制）**：产出数据库设计文档时**必须参照示例 [`examples/数据库设计文档.md`](./examples/数据库设计文档.md)** 生成，**照抄其章节结构、内容粒度与写法**（示例 = 唯一的格式基准）。
> **可复制骨架见 §7.2（模板正文）**，本节只讲结构与规则。

- **文档结构**：正文只有一个一级章节 **1 数据库表设计**，其下**按表分节**——**子章节标题即表名**（固定 `### 1.N `{表名}``，N 按表出现顺序递增）；多份设计（PRD）**共用本档**，**不按 PRD / 需求分组**。
- **表以表名定位**：**任何文档引用表一律写「见 `数据库设计文档.md` 表 `{表名}`」**（如「见 `数据库设计文档.md` 表 `dev_version`」），**禁止用章节名 / 章节号引用表**；表名必须与设计文档 2.N.3 表清单**一一对应**。
- **每张表固定三段**：**（1）表名 /（2）字段表 /（3）sql脚本**——三段齐全、顺序固定、**不增不减**。（1）写该表的中文名（与建表语句 `COMMENT` 一致），存量表注明「存量表」；（3）新建表写 `CREATE TABLE IF NOT EXISTS`、存量表写 `ALTER`，语句与字段表**逐字段一致**（字段名、类型、必填、注释、索引）。存量表只写**本次变更字段 + ALTER**，并注明完整字段见既有表定义。
- **脚本幂等（强制）**：**建表**一律写 `CREATE TABLE IF NOT EXISTS`（仅当表不存在时才创建）；**新增字段**一律写 `ALTER TABLE {表名} ADD COLUMN IF NOT EXISTS ...`（仅当字段不存在时才新增）——建表语句与新增字段语句都必须带 `IF NOT EXISTS`，保证脚本可重复执行、不报错。
- **字段命名（强制）**：字段名**禁止以 `Is` 开头**（含驼峰 `isXxx` 与下划线 `is_xxx` 两种写法，如 `isDelete` / `is_delete` 均不允许）；布尔 / 开关语义字段改用 `_flag` / `_status` 一类后缀表达（如 `link_status`）。
- **跨需求 / 跨设计共用的表只写一次**：表在**首次出现处写全**，其它处写「见 `数据库设计文档.md` 表 `{表名}`」，不重复展开。
- **公共字段固定四列**：`id` + `create_time` + `update_time` + `row_update_time`，逐表照抄、**不得增删**；**禁止**出现 `create_by` / `update_by` / `delete_flag`；业务字段只写本表特有的。
- **索引命名与脚本归档**：唯一键 `uk_{表名}_{字段}`、普通索引 `idx_{表名}_{字段}`；正式脚本 `resources/db/*.sql` **由用户维护**，本档语句是**设计稿**，不得擅自新增 / 修改脚本，须经用户确认后归档到对应版本脚本。
- **不写**：业务规则与设计决策（属设计文档 2.N.1）、接口路径与请求 / 返回字段（属 `接口设计文档.md`）、类与包设计 / 方法签名 / 代码骨架 / 实现顺序、全项目通用约定。
- **不引入**：设计文档里没有的新决策——本档只做明细展开，方案有变**先改设计文档**，再同步本档**对应表小节**（按表名对齐）。

## 5. 关联性红线

> 评审人的着力点是「这个功能怎么做」，因此**接口、表、依赖必须挂在它所属的需求小节下**。

1. **禁止全局汇总**：接口不集中到文末一张大表，表清单与依赖同理——否则无法判断某接口为谁服务、某表被谁写入。
2. **跨需求共用**：接口 / 表 / 依赖在**首个使用的小节写全**，其它小节只写一行「见 `api-N`」（表写「见 `数据库设计文档.md` 表 `{表名}`」），不重复展开。
3. **一个接口只属于一条需求**：确属共用时按上一条引用；禁止同一接口在两个需求小节各写一份。
4. **跨文件引用一律用序号 / 表名**：引接口写「见 `api-N`」（**禁止写「见 2.1.2」「见 2.3.1」等章节号**）；引表写「见 `数据库设计文档.md` 表 `{表名}`」（**禁止对表编小节号**，表名本身即唯一定位符）。多份设计共用一份明细文档，**引用必须带接口序号或表名**，否则无法定位。

## 6. 可读性红线

1. **一个单元格只放一个含义**：禁止用 `/` 把多个字段堆进一个单元格。
2. **需求清单只做索引**：第 1 章列固定为「序号 / 需求编码（PRD） / 需求描述」三列，**不写需求正文、不写验收标准**；第 2 章需求小节头只标注需求编码与标题，需求内容写在该小节的 2.N.1 功能说明。
3. **清单表只写清单**：接口清单表（2.N.2）列固定为「序号 / 接口编码 / 接口路由 / 接口说明」四列（**「序号」列填本表内自增行号 1、2、3…；「接口编码」列填 `接口设计文档.md` 的 `api-N` 且做成可点击链接 `[`api-N`](./接口设计文档.md#1N-api-N-{接口名})` 直达该接口小节**），**不放任何入参、出参字段，也不展示失败提示**；表清单表（2.N.3）只放「表名 / 用途 / 本次变更」三列，「本次变更」列取值**只有三种**：`新增`（本节首次建表）/ `改动`（本节给既有表加改字段）/ `见 `数据库设计文档.md` 表 `{表名}``（本需求只读他用的表，已在首次使用的需求小节写全，按「跨需求共用」规则只留引用）；本需求完全不涉及表时整节写「无」，仍保留表格表头。
4. **禁止重抄**：`接口设计文档.md` 已经写的字段明细与实现说明、`数据库设计文档.md` 已经写的表字段，设计文档**不再重抄一遍**——同一内容写两处必然脱节。
5. **接口实现说明集中在 `接口设计文档.md`**：逐接口的「调用场景」（什么时候被调）与「实现方式」（查哪张表 / 调哪个服务 / 同步还是异步 / 事务与幂等边界）写在 `接口设计文档.md` 的接口小节里，**与功能说明的业务规则不重复**，设计文档**不再写实现说明**。
6. **一行一事、能表格就表格**；禁止长句套长句、禁止一行写 3 件事。
