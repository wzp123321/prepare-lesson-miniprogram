# SDD 工作流（Spec-Driven Development）

> 文档先行。所有新功能开发必须遵循：**需求澄清 → 规格文档 → 设计文档 → 任务拆解 → 实现 → 自测验证 → 文档同步**。
> 本 skill 只承载**工作流**。项目特有铁律（数据库、枚举、批量入库、接口规范等）与编码规范见工作区规则文件，开发时另行引用。

### 各步骤产出物一览（承接上下文）

| 步骤 | 产出物 | 承接上下文的方式 |
| --- | --- | --- |
| 需求澄清 | 无独立文档 | 已确认的假设/约束显式记录到 spec 或任务上下文 |
| 规格文档 | `docs/{功能或版本}/spec-{PRD标题}.md`（**文件名不带需求编码**；+ 模块索引 `README.md`） | 业务契约（范围/边界/验收标准），供用户评审；**一份 PRD 一份** |
| 设计文档 | `docs/{功能或版本}/design-{PRD标题}.md`（**文件名不带需求编码**；+ 版本级共用 `api.md`、`database.md`） | **一份 PRD 一份设计**；顶部**需求清单**（PRD 需求编码 ↔ 功能模块 ↔ **接口序号区间** 索引）+ **按功能模块成章**（功能说明 / 接口清单 / 接口实现说明（只写指针）/ 表结构设计 / 外部依赖 / 历史数据处理）+ 文末全局枚举值说明，**章头标注本 PRD 的需求编码**；**接口出入参字段明细、示例、调用场景与实现在版本级 `api.md`（接口全局序号 `api-N`），表字段明细在版本级 `database.md`**，主文档只留清单与引用 |
| 任务拆解 | `checklist.md` + `tasks.md` | 每任务对应 design 一个改动点，粒度 = 最小可验证改动 |
| 实现 | 代码 + 单测 | 按 tasks 落地；复杂决策记录到项目记忆 |
| 自测验证 | 自测结果汇总 | 每任务完成即验，是进入下一任务的门槛 |
| 文档同步 | 更新状态标记、勾全 checklist | 让文档反映最终实现，闭环给下个功能 |

> 不是每步都写大文档：澄清与自测的产出是轻量记录；实体文档只有 **按 PRD 拆分的 spec / design**（`spec-{PRD标题}.md` / `design-{PRD标题}.md`，**文件名均不带需求编码**）+ 版本级共用的 `api.md` / `database.md` / checklist+tasks，外加版本目录的 `README.md` 文档索引，逐层引用、逐层收窄。这是"小步快跑"的核心——文档链轻量衔接 + 任务拆小 + 随做随验，上下文跨会话不丢。

## 一、需求澄清 | P0

- 需求不明确时，**必须先通过 AskUserQuestion 与用户澄清**（目标、范围、边界、验收标准），禁止猜测后直接写代码；
- 已确认的假设与约束**显式记录**到规格文档或任务上下文，避免后续遗忘。

## 二、规格文档（业务契约）| P0

- **按 PRD 拆分**：一个版本下的 PRD 可能一份、也可能多份，**一份 PRD 一份规格文档**，命名 `spec-{PRD标题}.md`（**文件名不带需求编码**），统一放在 `docs/{功能或版本}/` 下；PRD 里的**需求编码**（如 `IEMS-Scrum-85851`）必须写进规格文档与后续设计文档，作为需求追溯锚点；
- 涉及 **2+ 页面或 3+ 接口**的新功能，必须先编写规格文档 `docs/{功能或版本}/spec-{PRD标题}.md`；
- **触发判断不只看接口/页面数量**：功能复杂度高（多张表、跨年分表、动态 SQL、备份/恢复、多数据源跨库）或依赖链长（3+ 文件/服务/表）时，即使 1 页 1 接口也必须先写规格文档；
- 规格文档回答「做什么（What）」，是给用户确认的业务契约，应包含：背景与目标、首期范围/暂不纳入、数据流、边界条件、验收标准；
- 文档状态标记：`草稿 / 已确认 / 开发中 / 已上线`；
- 每个功能模块用 `README.md` 作为文档索引（参考 `docs/energy-anomaly-center/README.md`）。

### 规格评审门 | P0

- `spec.md` 写完后，**必须先提交用户人工审核**，确认通过后才可进入设计文档与实现；
- **需求即使描述得再清晰也必须过这道门**：spec 可能对需求理解有偏差（字段口径、边界、展示形式），实现前发现成本远低于实现后返工；
- 审核通过后：文档状态标记更新为「已确认」，**用户批准后自动开始实现，不再二次打断**；
- 审核不通过：按用户反馈修订规格文档后重新提交审核，禁止带着未确认的规格进入实现。

### 设计文档（技术方案）| P1

> 规格评审通过后、任务拆解之前，用 **design-document-skill** 在 `docs/{功能或版本}/` 产出**每份 PRD 一份设计文档**，加上**版本级共用的一份接口文档与一份数据库表文档**。

**对应关系（严格，不可跨 PRD 合并）**：

```
docs/{功能或版本}/
├── spec-{PRD标题1}.md                        ← PRD 1 的规格（文件名不带需求编码）
├── design-{PRD标题1}.md                      ← PRD 1 的设计（1 份 PRD = 1 份设计）
├── spec-{PRD标题2}.md                        ← PRD 2 的规格
├── design-{PRD标题2}.md                      ← PRD 2 的设计
├── api.md                                    ← 版本级 1 份，本版本全部设计共用
└── database.md                               ← 版本级 1 份，本版本全部设计共用
```

- **1 份 PRD = 1 份设计文档**：设计严格对应 PRD，不合并、不跨 PRD 写；**PRD 里的需求编码必须体现在设计文档**（文档头 + 顶部需求清单章 + 功能模块章头）；
- **1 份 PRD 内可有多个功能模块**：PRD 里有几个功能模块，该设计文档里就有几个功能模块章，**几对几、不增不减**；
- **接口文档与数据库表文档独立且版本级唯一**：本版本多份设计**共用 1 份 `api.md` + 1 份 `database.md`**，两份内部按「设计（PRD）」分章，章内再按功能模块分节；
- **评审**：逐份评审各自的 `design-{PRD标题}.md`；`api.md` / `database.md` 是配套明细，不单独评审。

**设计文档内部（每份 `design-{PRD标题}.md`）**：

- **设计文档 `design-{PRD标题}.md`（本 PRD 的唯一真相源 + 评审门）**：文档头之后先写**「需求清单」索引章**（非功能模块、不参与编号）——逐行列出需求编码 / 需求标题 / 本 PRD 的功能模块 / 章节号 / **接口序号区间**，**需求编码从 PRD 读取**（格式如 `IEMS-Scrum-85851`）；**按功能模块成章**，一章 = 一个可评审、可独立验收的最小闭环，与 `spec.md` 功能划分一致，**每章章头标注本 PRD 的需求编码**；每章固定六节——1.1 功能说明 / 1.2 接口清单 / 1.3 接口实现说明 / 1.4 表结构设计 / 1.5 外部依赖 / 1.6 历史数据处理，下一模块序号递增；文末追加**全局「枚举值说明」**一章（状态机 / 枚举 / 字典码值的简要说明，编号接在功能模块之后）。**接口、表、依赖必须挂在所属功能模块下**（禁止文末全局接口/表/依赖清单），单元格只放一个含义；**1.2 只写接口清单**（序号（`api-N`）/ 接口 / 用途 / 失败提示 4 列）与指向 `api.md` 的指引，**不写入参、出参字段**；**1.3 只留序号指针**（调用场景 + 实现方式已集中在 `api.md` 对应接口小节，本文件不展开），不重复 1.1 的业务规则；**1.4 只留表清单与引用**（表名 / 粒度 / 用途 / 详见 `database.md` 表 `{表名}`），字段明细在 `database.md`；**不写「通用约定」章节**（统一返回信封、传参方式、分页与字段命名等全项目约定不在本文档重复）；**禁止 HTML 折叠标签**（Trae / VS Code 预览不支持 `<details>`，会显示成字面量，用标题分节即可）；每个模块 ≤ 2 页，**禁止类与包设计、代码骨架、实现顺序**（这些由开发时按 `tiansu-ddd` 等编码规范落地）；未通过评审不得进入任务拆解；
- **配套明细 `api.md` / `database.md`（版本级唯一，主文档的展开，不单独评审）**：一级分章 = **设计（PRD）**（章内标注该设计的需求编码与文件名），章内按功能模块分节；`api.md` 逐接口写**入参 / 出参字段明细**（缩进树表达嵌套层级）**＋ JSON 示例 + 失败提示 + 「调用场景 + 实现方式」**，接口按**全局连续序号 `api-N`（从 `api-1` 起）**编号，与对应设计的 1.2 清单**一一对应**（清单有、这里必须有，序号与数量一致），**引用接口一律写序号**；`database.md` 逐表写**完整字段 / 类型 / 必填 / 说明 / 唯一键与索引**，并给出**建表语句（CREATE TABLE）与变更语句（ALTER，新建表写「无」）**，表名与对应设计的 1.4 表清单一一对应；两份**不得引入设计文档里没有的新决策**，任何修改**先改设计文档、再同步对应小节**（见「六、文档同步」）；
- **简单功能可从简**：1 页 1 接口且无表结构变更的（仅 1 个模块），设计文档只写 1.1 功能说明 / 1.2 接口清单 / 1.3 接口实现说明，1.4 ~ 1.6 与文末枚举值说明写「无」；无表变更时可不出 `database.md`，`api.md` 也可并入设计文档的接口小节，改动点在 tasks.md 内写清即可；
- 涉及 **表结构变更 / 跨模块多服务改动** 时，须将表结构设计与影响面同步用户确认后再实现；
- 与规格文档的分工：**spec 给用户确认业务（范围/边界/验收标准），设计文档给用户评审方案（功能/逻辑/接口清单与实现方式/表清单），`api.md` / `database.md` 给开发与 AI 施工（出入参字段明细与示例 / 表字段明细）**，三者并存于 `docs/{功能或版本}/`。

## 三、任务拆解 | P0

> 规格评审（P0）通过、设计文档（如需要）完成后，再进行任务拆解。

- `checklist.md`：验收点清单，写用户可验证的行为标准；
- `tasks.md`：实现任务拆解，**粒度 = 一个可独立验证的最小改动**（编译 + 自测通过即算完成）；
- 开发过程中用 `TodoWrite` 跟踪任务进度，与 tasks.md 保持一致。

## 四、实现 | P0

- 按 tasks.md 顺序逐个实现，粒度 = 一个可独立验证的最小改动；
- 每个任务完成 → 进入五「自测验证」→ 通过后勾选 checklist 对应项；
- 复杂功能的实现决策（架构调整、策略选择、踩坑教训）记录到项目记忆。

## 五、自测验证 | P0

> 执行细则见文末「代码修改后自测验证规范」。自测是**每个任务的完成门槛**，不是流程末尾一次性动作。

- **随做随验**：每个任务完成必须自测通过，才可进入下一个任务，禁止带着未自测的代码继续开发；
- 自测闭环固定为三步，缺一步不算闭环：`mvn -o clean compile -q` → `mvn test -q`（新增逻辑必须有对应单测）→ API 调用验证；
- 全部任务完成后，做一轮整体回归验证（启动 + 主链路走查），确认无遗漏边界场景；
- 自测通过后方可告知用户"修改完成，自测通过"。

## 六、文档同步 | P0

- 代码与规格文档必须保持一致；**需求变更先更新规格文档，再改代码**；
- **以设计文档为准**：`design-{PRD标题}.md` 是本 PRD 技术方案的**唯一真相源**；版本级 `api.md` / `database.md` 是它的**明细展开**，不得引入设计文档里没有的新决策；
- **方向恒定单向：设计文档 → `api.md` / `database.md`**。任何修改都**先改设计文档**，再同步到明细文件对应设计的对应小节（禁止只改其中一份导致脱节）；
- **须同步的内容**：接口增删（1.2 清单的编号 / 接口 / 用途 / 失败提示 → 同步 `api.md` 该设计章下的接口小节）、表清单与字段（1.4 → `database.md`）、外部依赖、历史数据处理、1.1 核心逻辑、1.3 实现方式、文末枚举值说明、**顶部需求清单与模块章头的需求编码**；
- **同步后核对**：功能模块数、接口数量与编号（设计文档 1.2 清单 ↔ `api.md` 该设计章下的接口小节，数量与编号一一对应）、表清单与表名（设计文档 1.4 ↔ `database.md`）、关键阈值口径一致；**版本内新增/删除 PRD 时**，同步增删设计文档并在 `api.md` / `database.md` 的「设计索引」中增删对应章节；若变更动到**已评审过的接口或表**，须在设计文档对应处标注「契约变更」，并在自测汇报时提示用户复核；
- 功能完成/上线后，更新文档状态标记，勾选全部 checklist，不留悬空验收点。

## 七、探索型开发（数据/需求不清晰场景）| P0

> 适用于需求依赖真实数据、无法预先写清验收标准的场景（如检测阈值、边界行为、修复策略规则）。
> 需求不清晰不是问题，**让 AI 在需求不清晰时进入"实现模式"才是返工源头**。

### 模式切换 | P0

- **探索模式**：需求未清晰时，AI **只回答数据问题、只输出分析结论，禁止写产品代码，一次只回答一个问题**；
- **实现模式**：数据事实确认后，按本规范 一~六 走完整 SDD 流程。

### 四条钳制（每轮对话自动执行）| P0

1. **探索时**：只输出分析结论，禁止写产品代码；跑出的结论**当场记录**到 `docs/{功能模块}/notes.md` 或项目记忆，否则下个会话 AI 会遗忘数据事实；
2. **实现前**：先列出该需求涉及的**所有文件/表/服务依赖链**，给用户确认后再动手，禁止只改主链路；
3. **实现后**：用 TRAE-code-review 自查，**列出已覆盖与未覆盖的边界场景**；
4. **清晰需求**必须给**结果级验收标准**："X 场景必须 Y，Z 场景必须不发生"，并要求 AI 自测。

### 关键约束 | P0

- 探索的产出物是**数据事实**（可验证结论），不是产品代码；
- 新会话开始处理本模块时，先读该模块的结论笔记（`docs/{功能模块}/notes.md`），避免"第一次看到数据"；
- 需求跨模块时，必须先在对话中确认依赖链（表/服务/前端文件），防止只改表面漏掉关联逻辑。

# 代码修改后自测验证规范 | P0

> 属于「五、自测验证」的执行细则。代码修改完成后，AI **必须自动执行自测验证**，不能依赖用户手动测试。

## 原则

代码修改完成后，AI **必须自动执行自测验证**，不能再依赖用户手动测试。自测通过后方可告知用户修改完成。

### 新增业务逻辑必须配套单元测试 | P0

- 任何新增/修改的**业务逻辑**（Service 层方法、工具类、校验、分支判断、边界处理等）必须在同一任务内编写对应的 JUnit 单元测试（JUnit5 + Mockito 纯单测，参照既有 `*Test.java` 风格），并跑通后视为完成；
- **自测 ≠ 只有 API 实测**：API 实测是黑盒验证，覆盖不了纯逻辑分支（分页越界修正、关键词 trim、跨年只查存在表、参数校验等），这些必须用单测固定；
- 缺少配套单测的任务视为**未完成**，禁止勾选 checklist 对应验收项；
- 自测闭环固定为三步，缺一步不算闭环：`mvn -o clean compile -q` → `mvn test -q`（新增逻辑必须有对应测试）→ API 调用验证。

## 后端自测流程

按以下顺序执行，任一环节失败则停止并报告问题：

| 步骤 | 命令/方式 | 说明 |
|------|-----------|------|
| 1. 编译检查 | `mvn -o clean compile -q` | **必须 `clean compile`（全量重编）**，增量编译可能漏报结构错误（缺 `}`、lambda 嵌套不匹配） |
| 2. 单元测试 | `mvn test -q`（仅改到哪测到哪） | 运行受影响模块的测试类 |
| 3. 日志检查 | 启动后拉 `backend/logs/app.log` | 确认无报错堆栈 |
| 4. API 调用验证 | 调用被修改的接口 | 验证返回结构和值符合预期（新接口验结构/状态码/必填字段，改逻辑验前后差异，异常场景传非法参数验错误信息） |

### 编译验证踩坑（2026-08-04 实例）

- `mvn -o compile` 是**增量编译**，可能漏报结构错误（缺 `}`、lambda 嵌套不匹配），启动时才暴露；
- 对策：任何改完代码后必须 `mvn -o clean compile -q`，不要用 `mvn -o compile`；大段代码改动逐个 `}` 配对检查；IDE 不报错 ≠ javac 不报错。

### API 报错诊断流程

按顺序排查：拉后端日志定位异常类型 → 读完整 Caused by 链 → 结合堆栈行号读源码判断根因 → 修复后重启验证。

**典型症状 → 根因对照**：

| 日志异常 | 常见根因 |
|----------|----------|
| `BadSqlGrammarException` / `Unknown column` | 代码引用了表中不存在的列（Entity/XML 新增但未建迁移） |
| `NoResourceFoundException` | 请求 URL 路径不对（缺 `/api/` 前缀或拼写错误） |
| `JsonParseException` / `JsonMappingException` | 请求 JSON 格式错误 / 字段类型不匹配 |
| `IllegalArgumentException` | 入参校验不通过（如必填字段为空） |
| `NullPointerException` | 查不到数据时未判空 |

排查到根因后，将结论与修复方案同步记录到当前任务上下文，避免重复排查。

## 自测完成后

1. 汇总自测结果（通过/失败及原因）
2. 全部通过 → 告知用户"修改完成，自测通过"
3. 有失败 → 修正后重新自测，直到全部通过
