# 更新脚手架（update-scaffold）

把脚手架仓（`energy_coding_template`）的最新编码规范与模板代码同步进当前业务仓。业务仓通常是**拷贝脚手架文件新建仓**，与脚手架**无共同 git 历史**，因此靠「同步锚点 + 分类处理」工作，不依赖 merge。

**设计原则（决定快慢）：只有「模板代码合入」需要 AI 逐个判断；规则文件按「先查本地改动 → 无改动直接整文件覆盖」处理，不做语义合并。**
首次按本版本同步时，规则文件可能需要一次「逐文件判定」；此后无本地改动的文件可整文件覆盖，更新速度显著提升。

## 关键常量

| 项 | 值 |
| --- | --- |
| 脚手架仓 URL | `http://192.168.20.76:8000/ENERGY_PBU/ENERGY_3X/server/energy_coding_template.git` |
| 首次同步默认起点 commitId | `328572423699b9b6c9c47d3279c8e0527a9675cf`（脚手架首次发布） |
| 同步状态文件 | 业务仓**根**目录 `.scaffold-sync`（内容仅一行：上次已同步的脚手架同步锚点） |
| 临时目录 | 系统临时目录下 `energy-scaffold-sync/`（**优先**，避免污染仓库）；若受限必须放仓内，用 `.scaffold-tmp/` 并确保**不会提交** |

## 文件分类（决定处理方式）

| 分类 | 路径 | 处理方式 |
| --- | --- | --- |
| **规则文件** | 根 `AGENTS.md` / `CLAUDE.md`；`backend/energy-template/AGENTS.md` / `CLAUDE.md`；`frontend/ts-agent-template/AGENTS.md` / `CLAUDE.md`；`backend/energy-template/ai-knowledge/skill/**`；`frontend/ts-agent-template/.ai-knowledge/**` | **直接覆盖**（先查本地改动，见第 2 步），AI 不做语义合并 |
| **模板代码** | `backend/energy-template/**`、`frontend/ts-agent-template/**` 中除上述规则文件以外的内容（pom / java / yml / 前端 src / 构建配置等） | **增量合入**（见第 3 步），需 AI 逐个判断，冲突先问用户 |
| **仓库级杂项** | `.gitignore`、`.vscode/**`、`README.md`、`.npmrc`、`.node-version` 等 | **默认不动**；仅当脚手架改动明确要求时，先征得用户同意再改 |

> 业务仓**自有的项目专用 skill**（脚手架里没有的同名目录）一律保留，不删除、不覆盖。

## 执行步骤（严格按序）

### 1. 获取脚手架最新代码

**方式 A — 有 git 权限（优先）**：

```bash
git clone --depth 1 <scaffold-url> <scaffold-dir>          # 只读使用，禁止提交进业务仓
git -C <scaffold-dir> log -1 --format="%H %ci %s"          # 记录同步终点 commitId
```

**方式 B — 用户没有 git 执行权限 / 网络不通**：

不要尝试重试或绕过。直接提示用户：

> 无法拉取脚手架仓，请自行下载脚手架代码后**提供本地路径**给我（目录或压缩包均可），我来做对比与合入。

- 用户给的是**目录** → 直接作为 `<scaffold-dir>`。
- 用户给的是**压缩包** → 解压到临时目录后作为 `<scaffold-dir>`。
- 无 git 时拿不到 commitId：向用户确认下载的**版本号 / 日期**，作为本次同步锚点（写入 `.scaffold-sync`，见第 5 步）。

> `<scaffold-dir>` 全程**只读使用**，禁止把其中任何内容直接提交进业务仓。

### 2. 规则文件：直接覆盖（先查本地改动）

**逐文件**执行，默认动作是「整文件覆盖」；只有检出本地改动时才需要 AI 介入。

**① 查本地改动（快速判定，按可用性降级）**：

| 判定手段 | 条件 | 结论 |
| --- | --- | --- |
| 业务仓 git 历史 | `git log --oneline -- <文件>` 显示该文件在业务仓「脚手架导入提交」之后无任何后续提交，且 `git diff <导入提交> -- <文件>` 为空 | 本地未改动 |
| 与「上次同步点」比 | 有 git 时，业务仓该文件与脚手架 `<startCommitId>` 版本一致 | 本地未改动 |
| 文本对比（兜底） | 上述都不可用时，直接逐文件对比业务仓 `<文件>` 与 `<scaffold-dir>/<同名文件>` | 差异仅出现在**已知定制值**位置 → 视为「仅定制值差异」 |

**② 按判定结果处理（三档）**：

1. **本地未改动** → **整文件直接覆盖**，不做任何语义分析（这是常态，也是提速关键）。
2. **仅定制值差异** → 用脚手架版本覆盖后，把业务仓原有的**定制值机械回填**到对应位置（包名 `com.tiansu.energy.xxx`、模块名 `energy-xxx`、表前缀 `{缩写}_`、库名 `nts-xxx`、端口、`spring.application.name`、Nacos 配置名、`artifactId` 等）。只做字符串替换，不改规范内容。
3. **存在实质差异**（本地自写规则、规范内容被改过） → **停下来问用户**，给 2-3 个可选方案（采用脚手架 / 保留本仓 / 覆盖+回填定制值），说明各自影响，等用户决定后再改。

**③ 双写约束**：覆盖后确保「**同一目录下 `AGENTS.md` 与 `CLAUDE.md` 内容完全一致**」；脚手架占位符（`yourproject`、`{Xxx}`、`energy-template` 等）**不得**覆盖本仓已具体化的值（属第 2 档「定制值回填」）。

### 3. 模板代码：增量合入（需 AI 判断）

**先看「脚手架改了什么」**：

```bash
# 有 git：只看起点之后的提交与 diff
git -C <scaffold-dir> log --oneline --no-merges <startCommitId>..HEAD
git -C <scaffold-dir> diff <startCommitId>..HEAD -- backend/energy-template frontend/ts-agent-template

# 无 git（用户提供代码）：拿不到历史，改为「业务仓当前文件」逐文件对比 <scaffold-dir> 同名文件，
# 无差异的直接跳过，只处理有差异的文件
```

再**逐处**判断（**不破坏现有代码**是前提）：

1. **本仓已是等价/更新内容** → 跳过（幂等，不重复合入）。
2. **本仓已自行修复同一问题**（内容等价、表述不同） → 视为已合入，**不报冲突**，以用户实际为准。
3. **差异很小**（仅措辞 / 格式 / 排版） → **以用户实际为准**，不覆盖。
4. **确属脚手架新增/修正，且与本仓不冲突** → 合入。
5. **与本仓现有代码冲突**（同一处被双方改过、或合入会破坏本仓业务逻辑） → **停下来问用户**，给出 2-3 个可选方案并说明影响，等用户决定后再改。

> 业务代码、SQL、私有配置（`application-*.yml` 等）**默认不动**；仅当脚手架改动明确要求时改，且必须先征得用户同意。

### 4. 输出 diff + 摘要（人工门禁）

- 输出 `git diff --stat` 与关键文件 diff。
- 摘要说明：**规则文件**覆盖了哪些（或跳过了哪些及原因）、**模板代码**合入了哪几处 / 跳过了哪几处及原因、保留了哪些定制、待用户确认项。
- **严禁自动 `git commit`**：等用户 review 通过后再提交。建议提交信息 `chore(scaffold): 同步脚手架规范 <锚点前7位>`。

### 5. 记录同步锚点

用户确认提交后，在业务仓根 `.scaffold-sync` 写入本次**同步锚点**：

- 有 git：写第 1 步记录的 `%H`（完整 commitId）。
- 无 git：写用户提供的版本号 / 日期（如 `2026-09-10`）。

下次同步即以此为新起点。

### 6. 删除临时目录

同步结束（含用户确认前中止）都要删除临时目录，确认 `git status` 中不残留脚手架代码：

```bash
rm -rf <scaffold-dir>
```

## 硬性约束

- 不把脚手架代码 / 临时目录提交进业务仓
- 规则文件默认整文件覆盖；**覆盖前必须先查本地改动**，检出实质差异时先问用户
- 定制值回填只做机械替换，不得改动规范内容
- 模板代码不破坏现有业务逻辑；涉及业务代码的改动必须先经用户同意
- 不自动提交；一切以 diff + 人工确认为准
- 用完必删临时目录

## 首次同步说明

业务仓 `.scaffold-sync` 不存在时：

- 有 git：起点为默认 commitId `328572423699b9b6c9c47d3279c8e0527a9675cf`，等价于「从脚手架首次发布至今的全部改动」都要过一遍；第 3 步只合入真正缺失/更新的模板代码。
- 无 git：没有起点可言，全部按「业务仓当前文件 vs 用户提供的最新脚手架」逐文件对比，无差异的跳过。
- 首次同步时规则文件通常都「有本地改动」（导入时已替换定制值），按第 2 步第 2 档「覆盖 + 定制值回填」处理；只有出现实质差异才问用户。
